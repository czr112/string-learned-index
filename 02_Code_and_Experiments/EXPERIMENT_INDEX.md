## 0. 阅读纪律（先看这一节）

1. **不要跨轮拼接绝对值。** 各轮的平台、编译器、预热与协议不同。**平台迁移本身就让绝对值不可比**：E8 的 v4 修订从 Windows 迁到 WSL2 后，同一份测量的绝对值高了约 34%–49%（E8 §5）。要跨轮看，只看**同一轮内部**的比值。
2. **每一轮都是自足的。** 结论只在"该轮的数据集、协议、样本量"内成立；轮次自己的 `RESULTS_EN.md` §"适用边界"列出该轮不能外推的部分。
3. **"通过正确性门"不等于"任意输入都正确"。** 早期轮次的环境**没有 sanitizer**（E5–E8 的 Windows 工具链与 WSL 侧都缺 ASan/UBSan），内存安全检查是**待补**项，不是已通过项。
4. **每轮的入口是 `RESULTS_EN.md`（结论）+ `LOG.md`（逐条过程、事故与更正）。** 更正大多追加在 `RESULTS_EN.md` 顶部而不改原文，**先读顶部的更正块**。
5. **E9 引入、E11 修复过一个扫描正确性缺陷**（多块组中间子块被清空时静默丢键）。读到 E9/E10 的扫描结论时注意这一点。

## 2. 三条线索怎么连起来

**构建成本**：E14 分解 → E15 去掉重复构建 → E16 去掉探针 → E17 同轮合计（**C/B 0.453×–0.526×**）→ E18 三段分解（构造仍占 66%–79%）→ E19/E20 复用组号。**最终仍慢于 ART（E20：1.34×–3.77×）。**

**查询成本**：E5（布局与 SIMD）→ E6（路由消融）→ E7（溢出查找策略）→ E8（容量分配）→ E9/E10（多块与访问代价交换）→ E11/E13（子块范围定位）→ E12（完整点查基线）→ **E21（冻结版本：胜有序数组、负于 ART）**。

**空间**：E8（容量重分配，溢出容器与后缀容量缩减）→ E22（更新负载下不复存在容量回退，代价改走溢出增长）→ **E24（两层分解：垃圾只在替换后出现；溢出容器元素余量 22%–30%；合法迁回几乎为零且卡在字节上）**。

**更新路径**：E24 量出 `update`／`erase` 走的是**慢路径**——这是 E25 的对象。**注意这一条的代价与布局退化是两件事**：E24 的 `update_only` 与 `initial` 逐位相同。

**维护**：E26 的 C1 证明**压缩的主要成本不在哈希**（哈希砍掉 2/3–19/20，时间只快 0.9%–6.7%）；C2 证明**压缩几乎从不促成触发它的那次放置**（0%–3.5%），跳过"腾不出足够字节"的那些是净收益。

**扫描**：E27 先测四项再选一项；**空组位图在本状态上没有目标**，改的是结果物化。

**长期替换下的空间（E28–E31，冻结之后）**：E28 诊断（**碎片，不是组预算**）→ E29 放宽触发（**能恢复空间、回不了本**，12 格一致更慢）→ E30 把判据的尺子直接测掉（**原地收紧 6–11 ns/记录，门槛 70 ns，机制被许可**）→ E31 实现并端到端对照（**开关默认关闭、冻结版本未改动**）。**这条线只做回收，不改模型、逻辑映射与主块预算。**

**本块空洞复用入口诊断（2026-09-27，只读，当前冻结默认配置，无计时）**：**按发生插入失败的目标块配对**统计「可用空洞尺寸」与「待写后缀长度」（全索引比较两张分布会把洞配给到不了它的请求而高估）。三个负载：**长期替换到 200%**、**纯插入**（载入偶数下标一半、插入奇数一半）、**打乱删除顺序的替换（W3，本轮新增的对照）**。

**处置：不进入，但理由与初版不同（经对抗性审查修订，确认 6 条、反驳 0 条）**——三条独立成立的理由：纯插入上无总体（死区恰为 0.0、槽位拒绝够不着）；**进入条件第二半不成立**（200% 处只搬 39.2–118.7 字节，且 53%–98% 的拒绝落在 0–1 条记录的块上）；晚期检查点上已有机制也被自己的 `n<2` 守卫挡住。**初版两处说法被推翻**：「repack 覆盖严格超集」由**缺失的 `n<2` 守卫**撑起（加上守卫后 `guarded` 200% 处只有 1.17%–28.87%，而 `hole` 是 91%–99%）；「死区永远是一段连续的洞」是 **W1 删除顺序的产物**——`erase_at` 从不写 `h.bottom`（低水位标记），补的 W3 对照把 `nholes≥2` 从 0.00% 抬到 8.79%／1.24%／33.89%，**「碎片元数据成本近零」随之作废**。**下一件该测的不是空洞表，而是 `repack_subblock` 的 `if (n < 2) return;`**——一行条件，正是挡掉那些拒绝的那句。**初版的装置缺陷**：事件上限曾是**进程级静态且从不重置**，W1 先吃光预算使**纯插入臂一行未记**而结构表仍被当总体发表；已改为每段重置并改用计数器。**两条口径**：「键序」不是这条判据的一部分（`Entry::offset` 无一处要求单调，读码确认）；发布配置里 `subblock_reclaim` 是 false，故三列匹配率都是**反事实对照**。**登记一条未解释的观察**：每块 repack 匹配率 ~98% vs 整组 compact 促成率 0.6%–3.3%（`compact_plan_rejected` 恒为 0，且 `compact_entered` 在闸门之前自增、不是「实际跑过的次数」）。详见 `RESULTS_HOLES_ENTRY.md`。


**分支 C 入口诊断（2026-09-24，只读，当前冻结默认配置，无计时）**：两个负载——**长期替换到 200%**（复现 E24 口径）与**净下降**（跨键空间**步长 4/2/1** 删除 ＋ 每 4 次删除插 1 条）。**计划 §6 的判据是两个量，本轮测出的两个量给出相反答案**：活跃数 vs 容器容量的差额**明确**（计划口径 **18.32%–30.99%**，E24 的 22%–30% 落在其中），但**再增长 ÷ 回落 = W1 88.13%–97.83%、W2 41.82%–49.48%**，即**回收不耐久**。拆成「从未用过」（`cap − high_water`，占 18.3%–31.0%）与「用过、现在没用」（`high_water − size`，占 **0.00%–5.26%**）之后，**中位容器在每一个检查点上都恰好回收 0.00%**，回落过的容器 `size/high_water` 均值仍有 **0.81–0.97**，**最大单容器可回收量 3–11 条记录**。**处置：只判了一半——「缩到当前活跃数」暂不进入原型**（回落之后 42%–98% 再增长，而回到旧峰值必然要重新扩容）；**「缩到历史峰值」尚未判定**（它回收的正是 Term A，而**回到旧峰值不需要重新扩容**，故本轮的 `regrowth` 比值**不能否定它**；代价是容器突破历史新高时的重分配，**只差一个计数器就能判定，不需要重跑本轮**）。**分支 C 整体不得标为「彻底关闭」。** 本轮同时推翻自己的三条说法（E24「22%–30% ⇒ 记录已减少但容器仍保留」的推断、设计里 A/B 的「可回收性」标注、W1「Term B 按构造恒为 0」的存量推元素），并修掉一个分析器缺陷（两个负载的 `frac` 约定方向相反，导致读取全零的 `before` 行）。**缩到历史峰值策略下的「新峰值事件率」明确未测，不当作已关闭。** 详见 `RESULTS_BRANCHC_ENTRY.md`。
