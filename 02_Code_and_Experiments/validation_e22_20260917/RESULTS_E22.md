# E22 结果：冻结索引在更新负载下的变化

日期：2026-09-17。目录：`validation_e22_20260917`（继承 E21）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**E21 确认了静态点查的位置。本轮问：随着索引被维护，那个位置如何移动——相对自身初始状态、相对 ART、以及重复前缀上的空间优势能保持多久。**

**本轮只观察，不改维护策略。**

---

## 0. 结论摘要

三类负载，**各自从相同的初始快照独立开始**：

| 负载 | 做什么 |
|---|---|
| **`update_only`** | **控制组**。全部键存在，只改值。**记录数、容量表、溢出数量必须不变** |
| `insert_only` | 插入确实不存在的新键，**锚定在真实键附近**使其散布在键空间上而非堆在末尾 |
| `replace` | 一个周期 = 一次删除 + 一次插入，**保持活跃记录数不变** |

### 四条结论

1. **控制组完全精确。** 三组数据上，记录数、溢出数、容量表、压缩、重建、分裂、空间**在每一步都不变**。这让其余结果可读——变化可以归给操作，不是归给测量。
2. **容量回退从未发生。** `rebuild` 是唯一会把区域换回统一默认容量的路径，而**这三类负载下一次都没有触发**（插入锚定真实键 → 前缀不变 → 不分裂）。**需求布局被保留，维护的代价走的是溢出增长这条通道。**
3. **重复前缀的空间优势**：只改值时**精确保持**；持续插入时**保持并扩大**（0.86× → 0.81×）；**删除后补入到 25% 时已经消失**（0.86× → **1.02×**）。
4. **维护成本明显高于 ART**：25% 检查点上，替换是 **5.7×–8.6×** 慢，插入 1.7×–3.3×，只改值 1.2×–2.8×。

> **查询成本的变化大多落在噪声里**：**同一份未改动的状态测 9 次，比值的离散中位 8%、最高 22%**。本轮**无法分辨**小的查询成本变化，因此不报"查询变慢了 X%"这类结论。

## 2. 结构指标（25% 检查点）

| 数据 | 负载 | 记录数 | 溢出 | 溢出占比 | 压缩 | 重建 | 分裂 | **回退区域** |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 混合字符串 | 插入 | 131,072 → 163,840 | 751 → **33,486** | **20.4%** | 531 | 0 | 0 | **0** |
| | 替换 | 131,072（稳定） | 751 → **12,877** | 9.8% | 1,131 | 0 | 0 | **0** |
| 重复前缀 | 插入 | 131,072 → 163,840 | 4,901 → **37,578** | **22.9%** | 2,168 | 0 | 0 | **0** |
| | 替换 | 131,072（稳定） | 4,901 → **36,178** | **27.6%** | 5,103 | 0 | 0 | **0** |
| 百万域名 | 插入 | 262,144 → 327,680 | 11,759 → **76,963** | **23.5%** | 1,901 | 0 | 0 | **0** |
| | 替换 | 262,144（稳定） | 11,759 → **39,817** | 15.2% | 4,065 | 0 | 0 | **0** |

**回退区域恒为 0**，因此**回退记录占比与回退查询占比也都是 0**。这两个量仍然记录——如果布局真的回退了，它们才是回答"多少数据、多少访问受影响"的量。**少量回退区域也可能承担大量访问，只数区域数量会漏掉。**

**退化通道是溢出**：插入到 25% 时溢出占记录数的 **20%–24%**；替换到 25% 时 **10%–28%**（重复前缀最重）。

## 3. 空间随时间（MB）

### 重复前缀上的优势能保持多久

E21 测得静止时原型比 ART **小 14%**。随负载推进：

| 负载 | 0% | 5% | 10% | 25% |
|---|---:|---:|---:|---:|
| `update_only` | **0.86×** | **0.86×** | **0.86×** | **0.86×** |
| `insert_only` | 0.86× | 0.84× | 0.83× | **0.81×** |
| `replace` | 0.86× | 0.88× | 0.91× | **1.02×** |

**只改值：精确保持**（两侧都不动）。**插入：保持并扩大**（都增长，原型更慢）。**替换：到 25% 时消失**——原型在长而 ART 持平，因为新插入的键落进溢出，被删掉的键留下的字节不会被回收。

另两个数据集上原型本来就比 ART 大（1.08×／1.38×），三种负载下都继续变大，谈不上优势保持。

## 5. 检查点上的查询成本与噪声地板

两套查询分开报告：

* **A：固定键序列**。同一访问需求，**真实答案按当前存活状态重算**，所以命中率会随替换推进而下降——它回答"**同一批需求是否变慢了**"。
* **B：重新生成为固定 50% 命中**，从当前存活键与已核验不存在的键生成——避免命中率变化掩盖布局变化。

**噪声地板**：0% 检查点是同一份未改动状态，被三个负载各测一次，**同一状态 9 次测量的离散中位 8%、最高 22%**。

| 数据 | 负载 | A 原型/ART（0%→25%） | A 命中率 | B 原型/ART（0%→25%） |
|---|---|---|---|---|
| 混合字符串 | 只改值 | 1.34 → 1.10 | 100% | 1.26 → 1.34 |
| | 插入 | 1.25 → 1.40 | 100% | 1.22 → 1.39 |
| | 替换 | 1.13 → 1.05 | 100% → 74.9% | 1.24 → 1.17 |
| 重复前缀 | 只改值 | 0.95 → 0.79 | 100% | 1.01 → 1.18 |
| | 插入 | 0.77 → 0.85 | 100% | 1.16 → 1.21 |
| | 替换 | 0.88 → **1.10** | 100% → 74.9% | 0.99 → 1.21 |
| 百万域名 | 只改值 | 1.63 → 1.55 | 100% | 1.64 → 1.59 |
| | 插入 | 1.82 → 1.72 | 100% | 1.61 → 1.63 |
| | 替换 | 1.64 → 1.58 | 100% → 74.7% | 1.46 → 1.56 |

**这些移动大多落在噪声地板之内或边缘**（例如只改值那一行结构完全没变，比值却在 0.95–1.18 之间晃）。**因此本轮不声称查询成本随负载发生了可分辨的变化。**

唯一在方向上有一定一致性的是**重复前缀的替换**：固定序列上原型从 0.88× 走到 1.10×，同时命中率从 100% 掉到 74.9%——即**同一批需求里未命中的比例升高，原型的相对位置随之变差**。但幅度只略高于噪声地板，**本轮只记录，不作为结论**。

## 6. 适用边界

1. **只观察，不改维护策略。** 本轮不提出也不实施任何维护改动。
2. **负载规模到初始键数的 25%。** 更大比例未测。
3. **插入锚定在真实键附近**，因此不触发前缀变化、不触发分裂。**其他分布（例如全部落在键空间一端、或集中在一个区域）会走不同的路径**，本轮没测——这恰恰是"容量回退"可能出现的条件。
4. **固定序列的命中率会随替换下降**（100% → 74.9%），所以 A 的后期数字里"未命中变多"与"布局变化"是混在一起的；这正是同时保留 B 的原因。
5. **噪声地板中位 8%、最高 22%**，限制本轮能分辨的查询成本变化。
6. **空间口径跨方法不可比**：原型用 `memory()`，ART 用包装分配器的**实时存活字节**。两者都不含分配器元数据、都不是 RSS。
7. **ART 只接受无 NUL 的 ASCII 键**，只在 ASCII 子集上被评估。
8. **`replace` 的操作数是周期数的两倍**，表中同时给出周期数与操作数。
9. **不与 E4 拼接**；**无 sanitizer**。
