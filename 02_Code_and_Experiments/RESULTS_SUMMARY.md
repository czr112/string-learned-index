## 3. 更新负载（E22）

三类负载各自从**相同的初始快照独立开始**；**只观察，不改维护策略**。

| 观察 | 结果 |
|---|---|
| **"只改值"控制组** | 记录数、溢出、容量表、压缩、重建、分裂、空间**每一步都不变**（完全精确） |
| **容量回退** | **从未发生**。`rebuild` 是唯一会换回统一默认容量的路径，三类负载一次都没触发 |
| **退化走哪条通道** | **溢出增长**：插入到 25% 时溢出占 **20.4%／22.9%／23.5%**；替换到 25% 时 **9.8%／27.6%／15.2%** |
| **重复前缀的空间优势**（原型 ÷ ART） | 只改值**精确保持 0.86×**；持续插入**保持并扩大**（0.86 → **0.81**）；**替换到 25% 时消失**（0.86 → **1.02**） |
| **维护成本**（25% 检查点，原型 ÷ ART） | 只改值 **1.24–2.77×**；插入 **1.65–3.32×**；**替换 5.73–8.56×** |
| **查询成本的变化** | **分辨不出来。** 同一份未改动状态测 9 次，比值离散**中位 8%、最高 22%**（结构完全没变的那一行，比值仍在 0.95–1.18 间晃） |

**因此 E22 不声称查询成本随负载发生了可分辨的变化。** 唯一方向上略有一致性的是重复前缀的替换，但幅度只略高于噪声地板，**只记录，不作为结论**。

### 3.1 更新操作本身走的是慢路径（E24，诊断轮，**不计时**）

E24 把 `update`／`erase` 实际走的东西数了出来。它们**没有**用 `find` 已有的**指纹 tag 过滤／长度预检／边界目录／溢出 Hybrid**，而是逐子块、逐条目做全字符串比较。

| 数据 | 来源 | `find`（比较次数／键） | `update` | 比值 |
|---|---|---:|---:|---:|
| 混合字符串 | 主块命中 | 1.27 | 70.4 | **55×** |
| | 溢出命中 | 1.67 | 216.2 | **130×** |
| | **未命中** | **0.004** | 141.8 | **34,155×** |
| 重复前缀 | 主块命中 | 1.57 | 145.6 | **93×** |
| | **未命中** | **0.012** | 286.6 | **23,957×** |
| 百万域名 | 主块命中 | 1.01 | 34.3 | **34×** |
| | **未命中** | **0.011** | 68.3 | **5,949×** |

**溢出命中不一律更贵**：重复前缀上它比主块命中还便宜（66.7 对 145.6）——**不能笼统说"溢出查找更慢"**。

**这个比值是"值得改"的理由，不是原因的解释。** 两次查找只让执行次数翻倍，解释不了 34,155× 的差距；同时至少还有"写路径完全绕过指纹过滤"和"`find` 未命中时分母接近 0"两个因素。**"`upsert` 重复查找"的直接证据是调用计数**（同一次 `upsert` 中实际执行了多少次查重、外层定位、模型预测、指纹计算）——本轮没有，并入 E25。

### 3.5 O1 溢出容器（稳定记录存储＋有序句柄；**E34，候选机制，开关默认关闭**）

**先测「搬的是什么」，因为这决定收益上限**（同一长期替换负载、200% 检查点、遍历活跃溢出容器）：

| 数据 | 记录对象 | 平均后缀长 | **SSO（≤15 B）占比** | 内联字符字节 | 堆上字符字节 |
|---|---:|---:|---:|---:|---:|
| 混合字符串 | 48 B | 81.6 | **0.0%** | 0 | 10,621,198 |
| 重复前缀 | 48 B | 80.3 | **0.0%** | 0 | 10,526,865 |
| 百万域名 | 48 B | 12.8 | 77.9% | 1,010,797 | 477,876 |

**搬动的是「字符串对象的 48 字节」，不是字符数据**——混合与重复前缀上**一条记录都没把字符内联在对象里**，那 10.5–11.6 MB 字符全在堆上、搬动时一个字节都不动。**只有百万域名以 SSO 为主，但内联字符也只占搬动字节的约 18%。** 所以 **O1 的搬动上限是 12×，与「字符内不内联」基本无关。**

| 验收项（E34，5 进程 × 3 数据集 × 2 模式 × 3 重复） | 结果 | 来源 |
|---|---|---|
| **搬移条目与字节** | erase 侧 **48 B → 4 B ＝ 12.0×，六格逐一成立**（重复前缀 839.3 MB → 69.9 MB、混合 425.9 → 35.5、百万域名 153.9 → 12.8）；**已存记录搬移恒为 0** | E34 诊断构建 |
| **完整删除、替换耗时** | `frac ≤ 1` **无变化**（\|比值−1\| ≤ 0.02，噪声底 1.02–1.43）；**`frac=2` 为 0.841–0.984，方向 3–5/5**——最强 重复前缀/grow **0.841（5/5）**、混合/grow **0.876（5/5）** | E34 `bench_long_o1` P1–P5 |
| **单操作尾延迟** | `frac=2`：混合 p99 **0.41–0.46（5/5）**、p99.9 **0.49–0.67（5/5）**；重复前缀 grow p99 0.572（5/5）；**百万域名 p99 与 p99.9 一格都没动**；`frac=1` 全无变化 | 同上（per-op 计时） |
| **插入** | 含在 `cum_ms` 内，插入为主的 `frac ≤ 1` 段**无回归** | 同上 |
| **点查** | **一致变慢 1.02–1.53**（方向几乎全 **0/5 或 1/5**），且**随溢出增长加剧**（百万域名 grow 1.040→1.221→1.362→1.525） | 同上 `query_ms` |
| **扫描** | 重复前缀 **+6.5%~+13.6%（六格全 0/5）**；百万域名 replace25 **略快 0.978–1.000**；混合基本持平；**`initial` 状态三格都 ≈1.000**（那时没有溢出，本该无差别） | E34 `bench_scan_s3` P1–P5 |
| **自有空间与临时峰值** | **收益不是代价**：总常驻 **−1.5%~−5.2%**，溢出部分 −9.7%~−13.6%，方向 **5/5**、**噪声底恰好 1.000**（内存是确定性量）；**store 高水位 ＝ 活跃数**，空闲链表把槽位全数回收、无空洞 | 同上 |
| 差分门是否空转 | 三数据集全 pass：比对 55.3 万／55.5 万／107.9 万条记录与 14.5 万／14.6 万／27.6 万次点查；**两臂溢出计数逐检查点相等**；句柄搬移 528,988／590,604／564,807，**记录搬移 0** | E34 `check_overflow_store` |

**适用边界（四条）**：① **收益只在溢出真正开始搬动之后**——100% 检查点逻辑搬移仅 956 条、200% 是 887 万条，**短跑（≤100% 替换）测不出任何差别**；② **百万域名形状基本不受益**（后缀短、容器小，总耗时只降 1.6%–3.2%、尾延迟不动）；③ **读路径一致受损**（点查 +2%~+53%、重复前缀扫描 +6.5%~+13.6%）；④ **点查回归的成因本轮未确认**——容器最小的百万域名受伤最重，与「ON 臂二分查找每步多一次间接」的朴素假设不符，**本报告不宣称成因**，要定论需专门诊断。

**判定**：**机制完全按预期、空间还更省，但不是净收益，不能进默认。** 建议在「有界迁回」之前先做**读路径修复原型**（给句柄数组内联 fence key，槽位 4 B → 8–12 B，让二分查找不再解引用 store），因为现在缺的**不是搬移**（已 12×、记录搬移已为 0），**而是读路径不被拖累**。**开关默认关闭，冻结的五个开关、构建路径、模型与主块预算均未改动。**

## 4. 范围扫描（E23）

语义：**从第一个 `key >= start` 的记录开始，按键序返回至多 `n` 条，形式为完整键值对。**

| 比值（原型 ÷ 全局有序数组，>1 表示原型更慢） | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| 区间（3 状态 × 3 长度） | 1.28×–1.91× | 1.49×–1.98× | 1.56×–2.34× |

- **27 个格子全部更慢**，比值区间 **1.28×–2.34×**。
- **方向在噪声之上**：三个进程分开看，**81 个比值没有一个低于 1.0**（最小 1.165）。而**格子之间比值的差别落在噪声里**（比值跨进程 max÷min 中位 1.11、最坏 1.56），**不作为结论**。
- **这是取舍，不是异常**：点查受益于快速缩小候选范围，扫描要连续输出多条记录。**扫描开销的具体来源尚未分解**（候选：跨组／跨子块／归并溢出记录／恢复完整键），**都未被本轮逐项测量**。**不能据此推导所有范围查询场景都会如此。**
- **ART 不进排名**：libart 无 seek-to-key 迭代器，全树遍历适配器慢 40×–3,823×，**那是适配器的成本**。该诊断**每格只有 64 次采样**，"每格 4,096 次"只指两个排名方案。

### 4.1 扫描的四项分解与一次改动（E27）

**先测四项再选一项**：起点定位 2.01–2.49 次/扫描（一次足够，**测了未改**）；**空组访问全部为 0 → 非空位图没有目标，跳过**；空子块跳过与归并比较都与返回记录数成正比；**结果分配 1.75–2.00 次/返回记录**。

**改动**：结果构造从"临时串＋拼接"改为预留后原地追加。

| 比值 | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| **S1 ÷ S0（扫描耗时）** | **0.758–0.937** | 同量级 | 同量级 |
| S1 ÷ 有序数组（n=1024，初始） | 1.455 | **1.296** | 2.128 |

**27 个格子全部同向，扫描降 6%–24%；仍慢于有序数组 1.30×–2.23。** **不与 E23 跨轮比值比较**——C2 改变了溢出分布。**不声称超过有序数组。**

## 6. 跨全部轮次的适用边界

1. **单机、单线程、共享主机**。并发扫描、游标复用、反向扫描、并发更新均**未测**。
2. **没有 sanitizer**：早期轮次的工具链缺 ASan/UBSan，**内存安全检查是待补项**，不是已通过项。
3. **"通过正确性门"限于该轮的测试覆盖**，不等于任意输入正确。E9 引入、E11 修复过一个**静默丢键**的扫描缺陷——这类缺陷正是靠后续轮次的门才暴露的。
4. **绝对耗时不可跨轮拼接**（平台迁移、协议与预热不同）；结论建立在**同轮比值**上。
5. **报告的是容量估计，不是 RSS**；分配器开销与字符串内联存储是否计入，**必须以该轮的口径说明为准**。
