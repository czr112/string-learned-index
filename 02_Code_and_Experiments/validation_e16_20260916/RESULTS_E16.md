# E16 结果：统计路径——不建探针也能算出分配器要的数

日期：2026-09-16（含计时构建分离的修订）。目录：`validation_e16_20260916`（继承 E15）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**E14 测出探针占一遍构建流程的 46%–50%，是最大的一项。E15 之后它仍未被动过。本轮把它去掉：不再为拿统计而完整建一个临时索引。**

> **修订（2026-09-16）**：首版把内存记账开在**正式计时**里，而旧探针的分配次数远多于新路径，因此那个仪器会**放大被测对象**。现在计时来自**不含任何包装与记账**的构建，内存由**单独的诊断构建**测量。§6 记录了这件事与它改变了什么。

---

## 0. 结论摘要

| 问题 | 答案 |
|---|---|
| 统计阶段快了多少？ | **降到 0.358×–0.725×** |
| 完整构建流程快了多少？ | **降到 0.737×–0.884×** |
| 结构变了吗？ | **没有**：布局摘要与 **E15 记录的摘要逐字符相同** |
| 统计本身对吗？ | **对**：**1,134,675** 个组统计**逐字段**比对，2700 组配置，0 处不符 |
| 统计阶段临时内存 | **38–44 MB → 2.1–2.3 MB**（约少 94%） |

**一句话**：分配器只需要四个每组的量，而为了这四个量，旧流水线建了一整个可查询的索引。现在改成按原放置顺序重放容量消耗——不分配块、不复制后缀、不建溢出容器。

**但完整流程只快 12%–26%，不是 2 倍**：构建本身没有变小，而且它现在是流程的大头。**本轮去掉的是探针，不是构建。**

## 1. 探针到底提供了什么（先定义，再动手）

对 `e9_alloc.hpp` 逐字段核查后，两个分配器**真正读取**的字段只有四个：

| 分配器 | 读取的 `GroupStats` 字段 |
|---|---|
| `demand_single` (D) | `primary_entries + overflow_entries`、`primary_bytes + overflow_bytes` |
| `demand_strict` (S) | 上面两组，外加**单独的 `primary_bytes`**，以及把 `overflow_entries` 当作候选排序的收益键 |

**一个都没有读到**：`free_entries`、`free_bytes`、`garbage_bytes`、`blocked_slots_only`、`blocked_bytes_only`、`blocked_both`、`oversized`、`fits_now`。

**关键点**：这四个量是在**默认容量（16 槽 × 1024 B）**下测出来的，所以它们**依赖主块与溢出的归属划分**——不是简单的按组总量。**因此轻量路径必须按原放置顺序重放容量消耗**，只是不必复制字符串或建立溢出容器。

---

## 2. 方法

### 2.1 改动

在 `index.hpp` 上加四处，**既有路径语义不变**：

1. **抽出三个共享推导**（`compute_prefix` / `suffix_bytes_of` / `derive_groups`），构造函数与轻量路径**用同一份公式**而不是各写一遍。构造函数内的计时分段保持原样（`prefix` / `model` / `suffix_scan` 三个相位粒度不变）。
2. **`Region::demand_profile(first, last, cfg)`**：重放 `insert_into` 的接受判定
   `count < slots && len <= bottom - start_of`，按全局有序顺序维护每组的 `(count, bottom)`。不分配块、不写后缀、不建溢出容器。每个键只留一个 `uint32_t`（组号，最高位标记是否进溢出），第二次遍历算溢出阻塞划分——**不需要重跑模型**。所有 `GroupStats` 字段都产出，不只是分配器读的那四个。
3. **`Index::demand_profile(pairs)`**：按 `bulk_load` 的分块切分，把每段以**指针区间**传给 `Region::demand_profile`，因此连每区域的 `vector<Pair>` 都不再物化。
4. **`Model::train` 增加指针区间重载**，原 vector 版本转发过去——**所有既有调用者的训练过程一字未变**。

**作用域**：只支持单块布局（探针就是这样）。多块配置**明确拒绝**（抛异常）而不是近似——那样 `put_primary` 会跨子块，重放还得模拟 M1 不变式。

### 2.2 三层验证

`check_e16_probe.cpp` 把轻量路径与**真实探针**对照三层：

| 层 | 比什么 |
|---|---|
| 统计 | **每个字段**（不只是分配器读的那四个）、每个组的每个 `GroupStats` |
| 方案 | D 与 S 容量方案逐元素，外加 S 分配器自己的决策日志（候选／资助／未资助／余量／削减） |
| 结构 | 两份方案各自建出的 D 与 S 索引，比结构摘要 |

配置覆盖统计所依赖的每一条轴：区域 32／64／2048、槽 1／2／16／48、块 256／1024／4096、负载 0.5／0.75、规范路由 Full／Interval／Residual、模型 Context16／Position16／Unigram，键集含空、单键、双键与全集。

**结果 `passed`：2700 组配置、1,134,675 个组统计逐字段比对、23,580 次方案核对、5,400 次结构核对，0 处不符。**

### 2.3 结构不变的跨轮证据

`bench_e16` 在每个进程内先比对两条统计路径建出的 S 与 D，**再报任何时间**。摘要是 **E15 的同一套 SHA-256 串行化**（含 FIPS 自检），因此可以直接与 **E15 记录的值**比：

| 数据 | 进程内一致 | 与 E15 记录的摘要相同 |
|---|---|---|
| 混合字符串 | 是 | **是** |
| 重复前缀 | 是 | **是** |
| 百万域名 | 是 | **是** |

**换掉探针之后，建出来的结构没有变。**

**摘要覆盖的边界与 E15 相同**（见 E15 §1.2）：覆盖区域划分、前缀、三张容量表、子块结构与每子块存储的键、边界目录、溢出条数、按扫描序的全部键值；**不覆盖**模型内部状态、块内空闲/垃圾字节分布、指纹标签、条目 `offset`/`length`、填充与对齐、地址。

完整表见 `E16_TABLES.md` §3。中位数（ms，5 进程，**干净构建**）：

| | 混合字符串 | 重复前缀 | 百万域名 |

| 统计：探针（完整构建） | 35.83 | 39.73 | 63.31 |

比值**同时给两种口径**（本项目已记录的失效模式，见 E15 §3b）：

| | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| 统计阶段，逐进程比值的中位数 | **0.725×** | **0.714×** | **0.358×** |

**为什么完整流程只快 12%–26%**：统计阶段确实少了 28%–64%，但构建没变，而且它现在是流程的大头。**这是本轮诚实的说法——去掉的是探针，不是构建。**

百万域名上的收益最大（统计 0.358×）：那里的探针要处理 262,144 个键、区域更多，而轻量路径不做任何块分配。

## 4. 临时内存峰值

统计阶段内的堆峰值，由**单独的诊断构建**（`bench_e16_mem`，`-DE16_MEM`）用 `--wrap` 包装 `malloc/calloc/realloc/aligned_alloc/posix_memalign/free` 实测（MB，3 次运行的中位数）：

| | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| 探针路径，峰值增量 | 38.34 | 44.04 | 38.28 |
| **轻量路径，峰值增量** | **2.24** | **2.13** | **2.31** |
| 校准：`probe.memory()` | 35.36 | 40.85 | 37.47 |
| 轻量 ÷ 探针 | **0.058×** | **0.048×** | **0.060×** |

这个数字应当读作「**已覆盖的分配接口下的请求堆字节峰值**」——不是 RSS，也不含分配器元数据。校准行说明两者同量级，是**一致性检查，不是"没有漏掉任何分配接口"的证明**。

**校准行不是装饰。** 只包装 `malloc` 时测得的探针峰值是 16.4 MB，而 `probe.memory()` 记账是 35.4 MB——**差了一半**。原因是区域存储来自 `::operator new(size, align_val_t)`，走的是**对齐分配**而不是 `malloc`。补上 `aligned_alloc` 与 `posix_memalign` 之后，实测峰值（38.3 MB）与记账（35.4 MB）同量级，这个数字才可信。

## 5. 为什么计时构建不带任何记账

首版把记账开在正式计时里（`acct::on = true` 从 main 第一行起，从不关闭）。**这恰好放大了本轮要证明其昂贵的那个路径**：探针的分配次数远多于统计路径（块区、溢出容器、每条溢出记录一个字符串），逐次记账的成本因此不成比例地落在它身上。

同一数据集上直接对照（干净构建 vs 诊断构建）：

| 数据 | 阶段 | 干净（ms） | 诊断（ms） | 诊断 ÷ 干净 |
|---|---|---:|---:|---:|
| 混合字符串 | 探针 | 35.83 | 40.90 | **1.142×** |
| 混合字符串 | `demand_profile` | 25.98 | 26.13 | 1.006× |
| 重复前缀 | 探针 | 39.73 | 40.73 | 1.025× |
| 重复前缀 | `demand_profile` | 28.75 | 27.97 | 0.973× |
| 百万域名 | 探针 | 63.31 | 60.83 | 0.961× |
| 百万域名 | `demand_profile` | 21.98 | 21.43 | 0.975× |

**如实读**：明显的一处在**混合字符串／探针 = 1.142×**，其余都在运行间噪声内。3 次诊断运行对 5 进程干净中位数**不足以给出一个膨胀系数**，本轮也不给。

**分离不依赖这个数字大不大。** 计时区里不该带成本随分配次数变化的记账——而被比较的两条路径在这个次数上差了几个数量级，这正是结果会对仪器敏感、且**敏感方向偏向美化改动**的原因。干净构建把这种依赖整个去掉，而不是寄望于它很小。

**§3 的每一个时间数字都来自没有任何包装、没有任何记账的构建。**

## 6. 修订记录（2026-09-16）

首版 `bench_e16` 只有单一构建，记账全程开启。审阅指出这可能放大旧路径，经核对**确实如此**。修订内容：

1. 拆成 `bench_e16`（干净，计时）与 `bench_e16_mem`（`-DE16_MEM`，内存诊断）两个目标；`tools_build.py` 只给后者加 `--wrap`。
2. 扫描只用干净构建（5 进程）；内存诊断单独跑 3 次／数据集，用 `MEM` 标签标记，**分析脚本按 `mem_build` 字段把它们挡在所有时间表之外**。
3. 数字随之更新：统计阶段由 0.661／0.684／0.355 变为 **0.725／0.714／0.358**，完整流程由 0.850／0.867／0.732 变为 **0.884／0.877／0.737**。**收益被首版高估了**，尤其混合数据集：那里的探针分配最多，被记账放大了 14%。
4. 内存数字不变（它本来就来自带记账的运行），但改由独立的诊断构建产出，并补上 §4 的口径说明。

| | 混合字符串 | 重复前缀 | 百万域名 |

| 统计（轻量） | 25.98 | 28.75 | 21.98 |

`place` 内部还没有分解。在动它之前需要先知道四段的占比：**组号与指纹计算／主块选择与容量检查／描述符移动与后缀复制／溢出容器插入与分配**。

**E14 的阶段比例可以指方向，但它来自旧运行与旧构建过程，不能当作当前路径的精确占比**——本轮的门已经确认阶段划分本身仍然成立（八项和 ÷ `ctor_total` 在 0.999 量级），但具体百分比需要在当前路径上重测。

## 8. 适用边界

1. **只支持单块布局。** `demand_profile` 对 `multiblock = true` 的配置**抛异常**，不近似。多块路径的统计仍需真实构建。
2. **只服务于"建一次、不再改"的探针用途。** 轻量路径重放的是**新建时的放置**。若探针在取统计前发生过增删，`garbage_bytes` 等字段会不同——门正是用"新建后立即取统计"这一情形验证的，与流水线的用法一致。**把它当成通用 `group_stats` 替代品是不成立的。**
3. **计时与内存来自两个不同构建**（§5）。时间数字不含任何记账；内存数字来自带包装的诊断构建，**不得用于任何时间比较**。
4. **内存是"已覆盖分配接口下的请求堆字节峰值"**，不是 RSS，不含分配器元数据；校准行是一致性检查，不是覆盖完备性的证明。
5. **摘要不是物理字节相等的证据**（§2.3，边界同 E15 §1.2）。
6. **绝对耗时跨进程漂移约 10%**；比值同时给出两种口径。
7. **各轮绝对值不可拼接**（E12–E16 机器状态不同）。
8. **不与 E4 拼接**（另一台机器、另一套 `-march`）；**无 sanitizer**（工具链与 WSL 侧均不可用）。
9. **本轮不涉及 ART**：`bench_e16` 不链接 `native.hpp`（它自带 `calloc`/`free` 包装，会与本轮的内存包装冲突）。ART 的对照数字以 E12／E15 为准。
