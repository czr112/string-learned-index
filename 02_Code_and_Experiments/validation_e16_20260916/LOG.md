## E16-1 步骤①：追踪统计依赖（2026-09-16）

对 `e9_alloc.hpp` 逐字段核查，两个分配器**真正读取**的字段只有四个：`primary_entries`、`primary_bytes`、`overflow_entries`、`overflow_bytes`（`demand_strict` 另外单独读 `primary_bytes`，并把 `overflow_entries` 当候选排序的收益键）。其余八个字段**一个都没被读**。

**但关键结论不是"只要总量就够"**：这四个量是在**默认容量（16 槽 × 1024 B）**下测出来的，因此**依赖主块与溢出的归属划分**。审阅指出的两条分支里，落在**需要重放放置顺序**的那一条——只是不必复制字符串或建立完整溢出容器。

## E16-2 步骤②③：轻量统计路径与逐组对照（2026-09-16）

### 改动

1. 抽出 `compute_prefix` / `suffix_bytes_of` / `derive_groups` 三个共享推导，构造函数与轻量路径**用同一份公式**。构造函数内的 E14 计时分段原样保留（`prefix` / `model` / `suffix_scan` 粒度不变）。
2. `Region::demand_profile`：重放 `insert_into` 的接受判定 `count < slots && len <= bottom - start_of`，按全局有序顺序维护每组的 `(count, bottom)`。每个键只留一个 `uint32_t`（组号，最高位标记溢出），第二遍算溢出阻塞划分——**不重跑模型**。所有 `GroupStats` 字段都产出，不只是那四个。
3. `Index::demand_profile`：按 `bulk_load` 分块，以**指针区间**传给 Region 版本，连每区域的 `vector<Pair>` 都不再物化。
4. `Model::train` 增加指针区间重载，vector 版本转发——既有调用者训练过程一字未变。

**作用域**：只支持单块布局。多块配置**抛异常拒绝**，不近似。

### 对照门

`check_e16_probe.cpp` 三层对照：统计（每字段）／方案（逐元素 + 分配器决策日志）／结构（摘要）。

**passed：2700 组配置、1,134,675 个组统计逐字段比对、23,580 次方案核对、5,400 次结构核对，0 处不符。**

配置覆盖区域 32/64/2048、槽 1/2/16/48、块 256/1024/4096、负载 0.5/0.75、路由 Full/Interval/Residual、模型 Context16/Position16/Unigram，键集含空／单键／双键／全集。

## E16-3 事故（2026-09-16）

1. **`Plan` 名字与 `e9alloc::Plan` 冲突**，`using namespace validation::e9alloc` 下二义。改名 `Pipeline`。**这是本项目第三次同类事故**（E10 的 `Metrics`、E12 的 `Query`）——在这个代码基里定义全局类型名必须先看 `validation` 与 `e9alloc` 两个命名空间。
2. **内存计数不成立**。`PeakScope` 只在被测阶段打开计数，但 `__wrap_free` 对**所有**释放做减法——于是释放作用域外分配的块会把计数拉成负数，"峰值"失去意义（它把**分配整块存储的探针路径报得比轻量路径还小**，一眼就是错的）。改为**全程计数**（main 第一行打开），`live` 才是真实净值。
3. **对齐分配没被包装。** 只包 `malloc/calloc/realloc/free` 时，探针路径峰值测得 16.4 MB，而 `probe.memory()` 记账是 35.4 MB——**差了整整一半**。原因是区域存储走 `::operator new(size, align_val_t)`，即**对齐分配**，不经过 `malloc`。补 `aligned_alloc` 与 `posix_memalign` 后实测 38.3 MB，与记账同量级。
   **是校准行抓到的**——没有"把实测峰值与原型自身的记账并排放"这一步，这个数字会以 16.4 vs 2.2（约 7 倍）的错误幅度被报出去，而真实的幅度是约 17 倍。
4. **分析脚本又混用了两种估计量。** 比值列用"逐进程比值的中位数"，而同表其余行是"各量的中位数"——两者不等。现**两种口径并列给出并逐行标注**（与 E15 §3b 的处理一致）。

## E16-5 结论与下一步（2026-09-16）

1. **探针已从流程中去掉**，且**结构逐字符不变**（跨轮摘要）、**统计逐字段相同**（113 万次比对）、**既有门输出不变**。
2. **收益如实报告**：统计阶段 0.355×–0.684×，完整流程 0.732×–0.867×，峰值内存约 0.05×。**"2 倍"这种说法在这一轮没有依据。**
3. **构建现在是流程的 63%–79%**，而 E14 已把它的内部拆开：`place` 占 Region 构造 45%–66%。

## E16-6 事故与修订：计时构建带了内存记账（2026-09-16，审阅后）

审阅指出一条实质问题：**报告说明了用包装分配函数测峰值，但没说清计时期间是否也在记账。**

核对结果：**是**。`acct::on = true` 写在 main 第一行且**从不关闭**，所以正式计时全程带着记账。**而这恰好放大了本轮要证明其昂贵的那个路径**——探针的分配次数远多于统计路径（块区、溢出容器、每条溢出记录一个字符串），逐次记账的成本不成比例地落在它身上。

### 处理

1. **拆成两个目标**：`bench_e16`（干净，零包装零记账，出计时）与 `bench_e16_mem`（`-DE16_MEM`，出内存）。`tools_build.py` 只给后者加 `--wrap`。
2. **扫描只用干净构建**（5 进程）；内存诊断单独跑 **3 次／数据集**，用 `MEM` 标签标记。**分析脚本按 `mem_build` 字段把它们挡在所有时间表之外**——不靠人记。
3. `E16_TABLES.md` 新增 §5，直接给出两种构建的对照表，并写明"§3 的每一个时间数字都来自没有任何包装、没有任何记账的构建"。

### 数字变化（这是本轮真正的修正）

| | 首版（带记账） | 修订后（干净） |
|---|---|---|
| 统计阶段 轻量÷探针 | 0.661／0.684／0.355 | **0.725／0.714／0.358** |
| 完整流程 轻量÷探针 | 0.850／0.867／0.732 | **0.884／0.877／0.737** |

**首版把收益高估了**，混合数据集上尤其明显：那里探针分配最多，被记账放大约 14%。

**如实读对照表**：明显的一处是 1.142×（混合／探针），其余在噪声内。3 次诊断运行对 5 进程干净中位数**不足以给出膨胀系数**，本轮不给。**分离不依赖它有多大**——计时区里不该带成本随分配次数变化的记账，而被比较的两条路径在这个次数上差几个数量级，**敏感方向恰好偏向美化改动**。干净构建把这种依赖整个去掉。

内存数字（38.3／44.0／38.3 MB → 2.2／2.1／2.3 MB）**不变**——它本来就来自带记账的运行，现在改由独立的诊断构建产出。口径补明为「**已覆盖分配接口下的请求堆字节峰值**」，并写明校准行是一致性检查、不是覆盖完备性的证明。
