# E10 查询访问成本诊断：D / M / S

日期：2026-09-16。目录：`validation_e10_20260916`（继承 E9→E8→…→E3）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0。

**本轮只做诊断**：不改分配方案，不计时，不给出加速结论。要回答的是 E9 留下的问题——**多块减少溢出之后，是否只是把溢出扫描换成了子块遍历？**

---

## 0. 结论摘要

**是交换，而且交换比按数据集差异很大。**

| 数据 | 溢出探测 D→M | 子块访问 D→M | SIMD 批次 D→M | 逻辑比较字节 D→M |
|---|---|---|---|---|
| 混合字符串 | 5.14 → **0.30**（−94%） | 1.00 → 2.97 | 1.95 → 7.69 | 109.6 → **43.5** |
| 重复前缀 | 7.79 → **0.56**（−93%） | 1.00 → 5.04 | 2.82 → 14.51 | 191.1 → **44.1** |
| 百万域名 | 10.95 → **0.05**（−99.5%） | 1.00 → **1.69** | 2.21 → 3.91 | 9.9 → 6.1 |

- **域名上交换明显划算**：子块遍历只增 1.7 倍，溢出探测降 99.5%。
- **重复前缀上代价最高**：子块遍历增 5 倍、SIMD 批次增 5.1 倍，换回 93% 的探测减少。
- 混合居中。

**而且代价并不是均匀分摊的**（§3.3）：D 中由主块命中的查询在 M 下几乎不受影响（子块访问 1.00→1.02），代价全部落在**原本要查溢出区的两类查询**上。这正是设计意图，不是意外。

**另外发现一项此前没注意到的收益**：逻辑比较字节同步大幅下降（重复前缀 191→44，混合 110→44）。原因见 §4。

---

## 1. 方法

**构建**：D、M、S 三种布局由 E9 的分配器构建（`e9_alloc.hpp`，从 `bench_e9.cpp` 原样抽出，**未做任何改动**）。同一份键集、同一模型、同一逻辑组号、同一指纹与 Hybrid 阈值（取自 E7 的冻结文件）。

**查询**：**一条共享查询序列**（131,072 条，50% 命中，未命中键在计时外核实不存在），三种布局逐条跑同一批查询。

**核对**：逐条比较 `found/value`。**不要求命中来源相同**——同一个键在 D 中命中溢出区、在 S 中已进入主块，这正是布局改变的结果，也是本轮要观察的对象。

**计数**：全部加在真实查询路径上（`index.hpp` 的 `find_impl`），记录实际执行次数，不按组大小估算。

| 指标 | 口径 |
|---|---|
| 子块访问 | 查询实际进入的子块数；**空子块也计**（块头被读取）；分配了但没访问的不计 |
| SIMD 批次 | 实际执行的向量标签比较次数（`_mm_cmpeq_epi8`） |
| tag 候选 | 经有效槽掩码处理后的指纹匹配数量 |
| 主块比较 / 溢出比较 | 实际调用精确比较的次数，分别计 |
| 溢出进入 | 是否真的进入了溢出容器查找 |
| 溢出探测 | 线性或二分实际检查的记录数（`overflow_checks` 的既有语义） |
| 逻辑比较字节 | memcmp 首次相异即停走过的字节数；**不是内存流量或缓存行读取量** |

前缀不匹配而提前返回的查询，所有计数为零。

## 3. 固定队列：按 D 的来源分组

各布局各自的"主块命中平均成本"比较的可能不是同一批键，所以这一张按**查询在 D 中的来源**分组，再看同一批查询在各布局中的成本。

### 3.3 读法

**代价高度集中在两类查询上**：

- **D 中主块命中的查询**：在 M 下几乎不受影响（子块访问 1.00→1.02～1.10）。这些键本来就在稀疏组里，组没有多块。
- **D 中溢出命中的查询**：子块访问涨到 2.8–5.5 倍，但溢出探测降 1–3 个数量级。**这就是多块把它们搬进主块的直接代价与收益。**
- **未命中查询**：子块访问涨到 1.9–6.4 倍，溢出探测降 11–160 倍。

**重复前缀是最贵的一档**：未命中队列在 M 下要遍历 6.38 个子块、执行 19.05 个 SIMD 批次——是 D 的 6.4 倍与 6.5 倍。

## 4. 机制：两项收益，一项代价

### 4.1 溢出探测大幅下降（预期之中）

溢出记录被搬进主块，落位查询不再扫溢出列表。未命中队列尤其明显：D 必须扫完整个溢出列表才能确认不存在，M 下这些记录已在主块里被标签过滤掉。

### 4.2 逻辑比较字节同步下降（此前未注意到）

| 数据 · 溢出命中队列 | D | M |
|---|---:|---:|
| 混合字符串 | 306.2 | **107.0** |
| 重复前缀 | 262.1 | **89.3** |
| 百万域名 | 28.7 | **13.7** |

原因：D 的溢出列表按后缀有序，命中查询要在长公共前缀的后缀间比较，每次 memcmp 走很多字节；搬进主块后比较落在更短的候选上。这与 E7 的发现一致（二分探测收敛到字典序相近的后缀，每次比较走 262–270 字节）。

**这是纯收益，不伴随额外代价**，且幅度可观（2.9 倍、2.9 倍、2.1 倍）。

### 4.3 子块遍历增加（代价）

一个组的子块按 rank 有序。查找**逐个进入子块**，找到即停；**未命中则要遍历全部子块**。这是代价的全部来源，也是 §5 的着手点。

## 5. 回答三个问题

**1. S 减少了多少溢出访问和记录探测？**

| 数据 | 溢出进入 | 溢出探测 |
|---|---|---|
| 混合字符串 | 0.330 → 0.123（−63%） | 5.142 → 0.649（−87%） |
| 重复前缀 | 0.840 → 0.303（−64%） | 7.793 → 1.572（−80%） |
| 百万域名 | 0.343 → 0.182（−47%） | 10.948 → 1.501（−86%） |

按队列看更清楚：D 中溢出命中的键，在 S 下探测从 12.2 降到 0.04（混合）。

**2. 为此增加了多少子块检查、SIMD 批次和后缀比较？**

| 数据 | 子块访问 | SIMD 批次 |
|---|---|---|
| 混合字符串 | 1.00 → 3.23（×3.2） | 1.95 → 8.15（×4.2） |
| 重复前缀 | 1.00 → 5.59（×5.6） | 2.82 → 15.35（×5.4） |
| 百万域名 | 1.00 → 1.79（×1.8） | 2.21 → 3.94（×1.8） |

主块比较次数也上升（混合 0.395→0.634），但那是因为更多键进了主块、本来就要比。

**3. 代价集中在哪些查询和哪些拥挤组？**

集中在**未命中查询**，以及**重复前缀数据**。未命中在 M 下要遍历 1.9–6.4 个子块（D 恒为 1）；主块命中队列几乎不受影响。也就是说代价落在**拥挤组**上——正是多块存在的理由。

## 6. 下一步：是否做子块定位

按诊断给出的三个分支判断：

| 分支 | 本轮证据 | 是否命中 |
|---|---|---|
| 大量查询遍历多个子块 | 未命中队列平均 3.6–7.1 个子块 | **是** |
| 开销集中在少数候选后缀 | 主块比较 0.4–0.8 次/查询，量级很小 | 否 |
| 额外访问主要来自空子块 | 空子块只影响 `subblocks_visited` 的计数，量级不足以解释 | 否 |

**结论：值得做子块范围定位。**

具体做法有直接依据：一个组的子块是**按 rank 有序的连续键区间**。一个查询键（无论存在与否）只可能落在**恰好一个**子块的键范围内。因此：

- **未命中**当前要遍历全部子块——改成只访问键所属的那一个即可，预期把未命中队列的子块访问从 3.6–7.1 降到约 1；
- **命中**当前已经找到即停（平均 `(nb+1)/2`），范围定位同样可以进一步缩小。

这与 E9 建立的 **M1 不变式**直接相关：M1 保证子块 `i` 的每个键都小于子块 `i+1` 的每个键——**范围定位所需的全部信息已经在布局里，只是查找路径还没用上它**。

代价：需要每个子块的首末键（可从块内条目直接读，或额外存一份边界），以及一次子块级的比较。**本轮没有实现，也没有测量。**

## 7. 边界

1. **计数不可相加成一个"总成本分数"**。一次 SIMD 标签批次、一次字符串比较和一次子块访问的时间并不相等；本轮不据此推出快慢。
2. **不计时**：本机端到端计时尚不稳定（E8 修订报告 §5.3）。
3. **逻辑比较字节 ≠ 内存流量**，也不是缓存行读取量。
4. **命中来源跨布局不要求相同**，本轮只核对 `found/value`。
5. 查询为均匀抽样，50% 命中，未命中键由源键追加 `~missing~` 构造并事先核实不存在。
6. 单一平台、三组合成与固定快照数据（mixed / skew / tranco），不含课题要求的 dblp / imdb / reddit / url / wiki。
7. **S 分配器在预算不足时的候选取舍仍未验证**（E9 遗留项，本轮未动）。
