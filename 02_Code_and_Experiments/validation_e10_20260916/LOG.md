### E10-0 继承与起点（2026-09-16）

### E10-1 计数器加在真实查询路径（2026-09-16）
`Result` 增加七项：`subblocks_visited`、`simd_batches`、`tag_candidates`、`str_cmps_primary`、`str_cmps_overflow`、`overflow_entered`，并沿用既有的 `overflow_checks` 作为"溢出记录探测数"。

全部在 `find_impl` 的实际执行点递增，不按组大小估算：
- `subblocks_visited` 在子块循环入口自增——**空子块的块头也会被读取，因此计入**；
- `simd_batches` 在 `_mm_cmpeq_epi8` 之前自增（`top <= lo` 提前退出时不计）；
- `tag_candidates` 取掩码处理后的 `popcount`（标量路径则计 tag 命中数）；
- 主块与溢出的精确比较分别计数；
- `overflow_entered` 在进入溢出容器查找时置 1。

**没有用编译开关隔离**：E10 不做计时，常开计数器不影响任何被测量的量，而三个门只比较 `found/value`，数字逐字不变即为证据。前缀不匹配提前返回的查询所有计数为零。

### E10-2 诊断基准 bench_e10.cpp（2026-09-16）
一条**共享查询序列**（131,072 条，50% 命中，未命中键计时外核实不存在）逐条跑 D／M／S 三种布局，逐条核对 `found/value`。

**不要求命中来源相同**——同一个键在 D 中命中溢出、在 S 中已进主块，这正是布局改变的结果。三种布局的比对只查 `found/value`。

输出三层：总体（含子块访问与溢出探测的 P95／最大值）、按各自来源分类、**按查询在 D 中的来源分队列再看同一批查询在各布局的成本**。第三层是关键——各布局各自的"主块命中平均成本"比较的可能不是同一批键。

比较字节沿用 E7 的 `compare_bytes`，仅在 `bench_e10` 这一目标上加 `-DE7_COUNT_BYTES`（`tools_build.py` 增加按目标附加参数）。三个门保持与 E9 完全相同的编译参数，其"未改变"的结论因此仍可比。报告中称为**逻辑比较字节**，明确不是内存流量。

### E10-3 结果（2026-09-16）
**是交换，交换比按数据集差异很大**（每查询平均，D→M）：

| 数据 | 溢出探测 | 子块访问 | SIMD 批次 | 逻辑比较字节 |
|---|---|---|---|---|
| 混合字符串 | 5.14 → 0.30 | 1.00 → 2.97 | 1.95 → 7.69 | 109.6 → 43.5 |
| 重复前缀 | 7.79 → 0.56 | 1.00 → 5.04 | 2.82 → 14.51 | 191.1 → 44.1 |
| 百万域名 | 10.95 → 0.05 | 1.00 → 1.69 | 2.21 → 3.91 | 9.9 → 6.1 |

队列视图说明代价**不均匀分摊**：D 中主块命中的查询在 M 下几乎不变（子块 1.00→1.02），代价全部落在 D 中溢出命中与未命中两类查询上——正是多块要救的那两类。重复前缀最贵（未命中队列子块 1.00→6.38、SIMD 批次 2.95→19.05）。

**顺带发现一项此前未注意的收益**：逻辑比较字节同步下降（溢出命中队列：混合 306→107、重复前缀 262→89、域名 29→14），因为比较从溢出列表（长公共前缀）挪到了主块。

尾部：D 有一条重溢出尾（域名 P95=68、最大 127 次探测），M 削平到 P95 0–4；代价是换成一条子块访问尾（混合 P95=10、最大 29）。

详见 `RESULTS_E10.md`。

### E10-5 下一步方向（记录，本轮未实施）
诊断指向**子块范围定位**：一个组的子块是按 rank 有序的连续键区间，**一个查询键只可能落在恰好一个子块的范围内**——未命中目前却要遍历全部子块。这与 E9 建立的 M1 不变式直接相关：范围定位所需的信息已在布局里，只是查找路径还没用上。预期可把未命中队列的子块访问从 3.6–7.1 降到约 1。本轮未实现、未测量。
