# E15 结果：给定容量方案后的直接构建

日期：2026-09-16。目录：`validation_e15_20260916`（继承 E14）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**E14 指出 S 的构建里有大半做完就被丢掉。本轮把那一次被替换掉的完整构建去掉。**

**改动的准确名称是「给定容量方案后的直接构建」**——它省掉的是*最终索引*的重复构造，不是整条流程的数据遍数。探针、需求统计与容量规划全部照旧运行，§4 单独计时。

---

## 0. 结论摘要

三个层次必须分开报，混在一起就是夸大的来源：

| 层次 | 两遍 → 一遍 | 说明 |
|---|---|---|
| **最终索引构建阶段** | **0.431×–0.499×**（约 2.0–2.3 倍） | 拿到方案之后把那一步建出来 |
| **完整构建流程** | **0.617×–0.657×**（约 1.5–1.6 倍） | 探针 + 统计 + 容量规划 + 构建 |
| **相对 ART** | 3.28×→**2.12×**、2.83×→**1.76×**、7.10×→**4.88×** | 完整流程 ÷ ART 构建（噪声见 §4） |

| 验证项 | 结果 |
|---|---|
| 规范化结构摘要 | 本轮内一致，**且与 E14 的两遍构建一致**（6 个 (数据, 结构) 组合） |
| 测试查询逐条比对 | 30 次运行共 **3,932,160** 次，**0 处不符** |
| 四个继承正确性门 | 输出与 E12 **逐字相同** |
| **新接口的直接覆盖** | `check_e15_plan` **通过**（4 处方案拒绝、12 组等价对照、12,000 次动态操作） |

**能支持的说法是**：规范化结构摘要一致、测试查询结果一致、现有功能检查未观察到回归。
**不能说的**：物理内存逐字节一致、模型输出全部相同。§1.2 列出了摘要**覆盖不到**的东西。

## 1. 方法

### 1.1 改动

在 `index.hpp` 的 `Index` 上新增：

```cpp
void bulk_load_with_plan(const std::vector<Pair>& pairs,
                         const std::vector<std::vector<std::uint16_t>>& sg,
                         const std::vector<std::vector<std::uint32_t>>& bb,
                         const std::vector<std::vector<std::uint16_t>>& nb_cap = {});
```

按 `bulk_load` 的分块切分输入，用同一个 `Region` 构造函数（`rebuild_with_caps` 用的那个）逐区域构造一次。**既有路径一字节未改。**

**强异常保证**：方案先校验，每个 `Region` 建进一个**局部** vector，全部成功后才换入。被拒绝的方案让索引保持原状，而不是半建状态。

> 这条不是设计出来的，是 `check_e15_plan` 的 A1 用例逼出来的。第一版先 `nodes_.clear()`、先设 `size_ = pairs.size()`，于是中途抛异常会留下「一部分新区域 + 全量 `size_`」——**一个对外自相矛盾的对象**。门直接失败，随后改成局部构造再换入。

### 1.2 摘要覆盖到哪，覆盖不到哪

摘要 = 对一份规范串行化取 SHA-256。

**覆盖**：区域数量与顺序；每区域前缀；三张容量表（槽数／块字节／偏移）；派生的子块数与每子块条目数；每个子块**实际存储的键**；边界目录（键 + 目标子块号）；每区域**溢出记录条数**；以及按扫描序的全部 `(key, value)`（主块 ∪ 溢出）。

**不覆盖**：**模型内部状态**（摘要没有哈希它）；块内空闲与垃圾字节的分布；指纹标签；条目 `offset`/`length` 字段本身；块内填充与对齐；内存地址。

**可推出但未显式编码**：主块 / 溢出的归属。它可由「按扫描序的全部记录」减去「各子块存储的键」推出，但摘要本身不含该归属。

**因此本报告不写「物理布局逐字节不变」。** 哈希的自检只验证哈希实现正确，不会扩大被串行化内容的覆盖范围。

### 1.3 新接口的直接覆盖

四个继承门是 E13 的，**从不调用新接口**，只保护旧路径。新增 `check_e15_plan.cpp` 直接覆盖新接口：

| 用例 | 钉住的性质 |
|---|---|
| A1 | 方案短于区域数 → 拒绝，**且索引保持原状**而非半建 |
| A2 | 某区域的形状长度与其组数不符 → 拒绝 |
| A2b | **合法但不同**的槽数 → 接受（否则 A2 可能只是"任何改动都拒绝"） |
| A2c | 槽数为 0 → 拒绝 |
| A3 | 子块上限表长度不符 → 拒绝 |
| B | 空输入 → 恰好一个空区域，与 `bulk_load` 的兜底一致 |
| C | 末尾区域短于 `region_keys` → 两条路径产生同样的短尾区域 |
| D | 区域规模 {32, 64, 100} × {单块, 多块} × {短, 全} 键集：区域数、围栏、前缀、三张容量表、结构摘要与两遍路径一致 |
| E | 新路径建完之后 12,000 次混合 insert/update/upsert/erase/find/scan 对 `std::map`，含触发分裂的前缀变化插入 |

结果 `passed`：4 处方案拒绝、12 组等价对照、3 处边界、12,000 次动态操作、1,695 次扫描。

### 1.4 协议

数据集与规模沿用 E13（`mixed` 131,072、`skew` 131,072、`tranco` 262,144 键）。5 个独立进程，每个先热身并按 run tag 剔除；**两条流水线在同一进程内各建 3 次、每次交替先后**。表中每个格子是**跨进程的中位数**；差异同时给出「两个中位数相减」与「逐进程配对差的中位数」两种口径——**两者不相等，混用正是本文档上一版出错的地方**。

### 2.1 与 E14 估算的对账

E14 把被丢弃的那半报为两遍构建的 **55.6%–66.3%**（`s_bulk + region_all`）。同一进程内量得的旧流水线自身拆分：

| | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| 旧 `bulk_load` | 53.60 | 66.21 | 83.80 |
| 旧 `rebuild` 循环 | 44.82 | 51.81 | 88.34 |
| 其中 `Region::all` | 11.32 | 10.55 | 12.29 |

**一遍构建仍然要把每个区域的键物化成一个 `vector<Pair>`**——同一次切片。它不再做的是为这次切片按默认容量构造一个 `Region`。所以**可移除的量应记作 `bulk_load` 本身**，E14 的 `region_all` 项是被**替换**而非省掉，不纯粹可加。

旧 `rebuild` 与新构建是**相近工作量的对照，不是同一个量**：两者物化切片的方式不同（`all()` 走完整 `scan` 合并子块与溢出；新路径是连续区间直拷贝），旧侧还多一次对象替换与销毁。**它们的差用于定位成本，没有被要求为零。**

| | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| 旧 `rebuild` − 新构建（两个中位数相减） | +1.12 | +0.19 | +3.46 |
| 旧 `rebuild` − 新构建（逐进程配对差中位数） | +0.57 | +0.94 | +5.98 |

两个口径相差最多约 2.5 ms。**这个差本身跨运行不稳定**：同一次比较的上一轮扫描里，百万域名上是 13–14 ms，本轮是 3–6 ms。所以只报不解。若确有差，一个候选解释是 `Region::all` 的完整归并比直拷贝贵——**本轮没有做隔离实验，它只是候选。**

| | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| 预测可移除（修正口径 = `bulk_load`） | 54.4% | 56.4% | 49.3% |
| **实测降幅** | **54.9%** | **56.9%** | **50.1%** |
| 差（百分点，两个中位数相减） | +0.5 | +0.5 | +0.8 |
| 差（百分点，逐进程配对） | +0.0 | −0.0 | +3.5 |

三组都在 1 个百分点内吻合。

**E14 的 55.6%–66.3% 今后应当读作「阶段成本估算」，而不是任何意义上的界。** `bulk_load + region_all` 描述的是旧流水线的时间去向；两条路径在切片、对象替换与销毁、缓存与分配器状态上都不同，成本不是简单相减。E14 §7.2 已把该数字标注为"代码事实的推论、未经实现验证"——**本节就是那次验证，并把口径修正为 `bulk_load`。** 修正幅度不改变 E14 的结论（被丢弃的那半仍占多数）。

## 5. 适用边界

1. **只覆盖静态批量构建。** 增量路径（`insert`／`erase`／`rebuild`／分裂）逻辑未改；E 用例覆盖了在新路径建成的索引上做增量操作，但没有对增量路径重新计时。
2. **"2 倍"只属于最终索引构建阶段。** 完整流程是 1.5–1.6 倍；相对 ART 仍然明显更贵。
3. **探针未动，且现在是完整流程的近一半。**
4. **摘要不是物理字节相等的证据**（§1.2 列出覆盖与不覆盖）。本报告不写"逐字节不变"。
5. **查询比对不是穷举**：命中查询在 131,072 键集上覆盖约 63% 的不同键，未覆盖的记录由结构摘要负责。
6. **各轮绝对值不可拼接**：E12/E13/E14/E15 的机器状态不同，只有同轮内比值可比。E12/E13 所报的 `build_ms` **只覆盖最终索引构建阶段**，不含探针与容量规划——见 §6 的更正说明。
7. **差异必须标注口径**：本报告所有差值都同时给出两种估计量；只给一个数就是上一版的错误。
8. **不与 E4 拼接**（另一台机器、另一套 `-march`）；**无 sanitizer**（工具链与 WSL 侧均不可用）。
9. **ART 只接受无 NUL 的 ASCII 键**，只在 ASCII 子集上被评估。

## 6. 对 E12／E13 的一处更正

E14 §2 首次测出：E12／E13 口径下的 `build_ms`（`bulk_load` + 逐区域 `rebuild_with_caps`）**不含探针、需求统计与容量规划**。而 E12／E13 的报告没有说明这一点，读者容易把它当作完整构建成本。

**更正**：E12／E13 表中的 S 构建时间（137.7／150.3／182.0 ms）是**排除探针与容量规划的部分构建成本**。按 E14 的完整流程口径，同规模下应为 164.03／195.64／272.68 ms；按 E15 的完整流程口径为 147.40／179.01／247.69 ms（去掉了被丢弃的那一遍）。

**不必重跑旧实验**，但**旧表不应再被当作完整成本引用**。E12／E13 目录内已加更正说明。
