## E15-1 设计（2026-09-16）

### 改动

在 `Index` 上新增 `bulk_load_with_plan`：按 `bulk_load` 的分块切分输入，用**同一个** `Region` 构造函数（`rebuild_with_caps` 用的那个）逐区域构造一次，容量取自分方案。

**既有路径一字节未改。** 分方案覆盖不全时抛异常而不是静默补齐。

### A/B 在同一进程内

`bench_e15` 在同一进程里把两条流水线各建 **3 次**，**每次交替谁先建**，所以"先跑"不与"是旧的"混淆。两个目标：`bench_e15`（无宏）与 `bench_e15_phase`（`-DE14_PHASE`）；本轮的结论数字全部来自前者。

### 先比摘要，再报时间

每个进程内部对两条流水线的布局算 SHA-256 并比对，**不一致直接抛异常**，不产生记录。摘要串行化与 E14 **逐字节相同**，因此还能与 E14 的记录做跨轮比对。

### 记录旧流水线的自身拆分

E14 用"被丢弃那半的独立耗时"预测收益。为了让预测能被**核对**而不是被**断言**，本轮在同一进程内把旧 S 流水线的 `bulk_load` / `rebuild` 循环 / 其中 `Region::all` 三段分别计时（只在第 1 次重复上记录）。

## E15-2 事故（2026-09-16）

1. **JSON 写出裸数字串**。`samples` 写成 `"s_old":1.2,3.4`——键后面跟一串逗号分隔的裸数字**不是合法 JSON**。首轮扫描 5 个进程全部跑完、文件也写出来了，**是分析脚本一读就崩**才发现的。改成数组 `[1.2,3.4]`，重跑整轮。
   （教训：写入端没有校验，读取端是唯一防线。构建闭环能拦住编译失败，**拦不住格式错误的输出**。）
2. **查询 A/B 处漏传新参数**。`build_S_old` 加了 `record` 形参后，第七节里那处 `build_S_old()` 没跟着改，编译失败。**由构建闭环拦下**：失败即不产生可执行文件（`build/` 里没有留下半成品）。
3. **变量声明晚于捕获它的 lambda**。`t_s_bulk` 等三个变量原本声明在 `build_S_old` 之后，而 lambda 里要写它们——C++ 名字查找在 lambda 定义处进行，会编译失败。把声明移到所有 lambda 之前。
4. **对账段落第一版是错的**。我先写了一段自造的推导公式（`slice = rebuild - (s_new - slice)` 之类），并且prose里的数字与生成的表格对不上（写了"agree to 0.8 ms"，表里是 +1.54）。整段重写：不写公式，直接给"旧 `rebuild` 与新构建本应是同一个量"这个可检验的论断，并让 prose 从表里取数。

## E15-3 结果（2026-09-16）

5 个进程 × 3 数据集 × 2 目标，先热身再测量，目标顺序在偶数进程上翻转。完整表见 `E15_TABLES.md`。

**构建时间（ms，跨进程中位数）**：

| | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| S，两遍 | 86.64 | 109.30 | 159.17 |
| S，一遍 | 40.37 | 47.73 | 73.20 |
| **S 一遍 ÷ 两遍** | **0.456×** | **0.438×** | **0.460×** |
| D 一遍 ÷ 两遍 | 0.476× | 0.463× | 0.475× |

池化 15 个样本同样是 0.448×／0.440×／0.478×。

**验证**：

- **布局摘要**：6 个 (数据, 结构) 组合在本轮内各只有 1 个取值，**且与 E14 的两遍构建完全相同**。
- **查询 A/B**：30 次运行共 **3,932,160** 次逐条比对，**0 处不符**。
- **继承门**：四个门输出与 E12 **逐字相同**。

**与 E14 估算对账**：E14 报的可丢弃量是 55.6%–66.3%（`s_bulk + region_all`），实测降幅 54.0%–56.2%。同进程内量得的原因：一遍构建**仍要做同一次区域切片**，`Region::all` 是被**替换**而不是被省掉，所以 E14 的 `region_all` 项不纯粹可加。可移除的量应记作 `bulk_load` 本身。

自洽性检查：旧 `rebuild` 与新构建**本应是同一个量**（各是"一次切片 + 一次按方案构造"）——混合 +1.54、重复前缀 −0.68、**百万域名 +14.46**。前两者在 1.6 ms 内吻合；百万域名的旧侧贵 14.5 ms，因为 `Region::all` 走完整 `scan`（归并子块与溢出），而新路径是直拷贝。**替换比被替换的更便宜**，这也解释了它在那个数据集上降幅超出估算最多（+7.8 点）。
（**以上这条推理已在 E15-6 收回**：两者是相近工作量的对照而非同一个量；且这里混用了两种估计量，数字也不同。）

**对 ART**：完整流水线 3.29×→2.08×、2.92×→1.85×、7.57×→4.85×。**这个比值噪声大**（ART 自身绝对耗时本轮 31–56 ms、E14 44–76 ms），只用于标定量级。

## E15-4 结论与下一步（2026-09-16）

1. **结构性重复构建已消除，收益实物化**：S 构建 **2.2 倍**，且**布局逐字节不变**（跨轮摘要相同），**查询结果不变**（393 万次比对）、**既有门输出不变**。
   （**E15-6 更正**：2.2 倍是**最终索引构建阶段**的倍数，完整流程是 1.5–1.6 倍；"逐字节不变"应读作「规范化结构摘要一致」，摘要覆盖不到模型内部状态与块内空闲分布等。）
2. **E14 的估算口径要改**：今后记作 `bulk_load`，不要记作 `s_bulk + region_all`。E14 的结论（丢弃的那半占多数）不受影响，其 §7.2 的"未经实现验证"标注现在可以视为已验证。
3. **下一个目标是探针**：它现在是新流水线里最大的一项（**46%–50%**），且**完全没被本轮触碰**。`group_stats()` 读的是构造好的区域，所以"不构造也算出同样的统计"是一次真正的实现工作，需要它自己的验证。
4. **`place` 仍未分解**（E14 列为最大常数项）。在动它之前应先知道主块放置与溢出放置的占比。
5. 顺序建议不变：**探针（结构性，约一半）→ `place` 内部（常数，最大项）→ `storage` 与需求统计**。`dir`／`layout`／容量规划不动。

## E15-5 新接口的直接覆盖门（2026-09-16，审阅后追加）

审阅指出：**四个继承门是 E13 的、从不调用新接口，只保护旧路径。** 新增 `check_e15_plan.cpp` 直接覆盖它，随后发现并修掉一个真实缺陷。

**门本身不是形式合规**：A1 用例（"方案被拒绝时必须保持原状"）在第一次运行就**失败**了。第一版 `bulk_load_with_plan` 先 `nodes_.clear()`、先设 `size_ = pairs.size()`，于是中途抛异常会留下「一部分新区域 + 全量 `size_`」——**对外自相矛盾的对象**。改为把 `Region` 建进**局部** vector、全部成功后再换入，A1 通过。这是本轮唯一的实现改动，由测试逼出，不是设计出来的。

覆盖与结果（`logs/check_e15_plan_run.log`）：

| 用例 | 钉住的性质 |
|---|---|
| A1 | 方案短于区域数 → 拒绝，**且索引保持原状** |
| A2 | 某区域形状长度与其组数不符 → 拒绝 |
| A2b | **合法但不同**的槽数 → 接受（否则 A2 可能只是"任何改动都拒绝"） |
| A2c | 槽数为 0 → 拒绝 |
| A3 | 子块上限表长度不符 → 拒绝 |
| B | 空输入 → 恰好一个空区域，与 `bulk_load` 兜底一致 |
| C | 末尾区域短于 `region_keys` → 两条路径同样的短尾区域 |
| D | 规模 {32,64,100} × {单块,多块} × {短,全}：区域数、围栏、前缀、三张容量表、结构摘要与两遍路径一致 |
| E | 新路径建完后 12,000 次混合增删改查对 `std::map`，含触发分裂的前缀变化插入 |

`passed`：4 处方案拒绝、12 组等价对照、3 处边界、12,000 次动态操作、1,695 次扫描。

**改完 `index.hpp` 后按纪律重跑全部**：四个继承门输出与 E12 **仍逐字相同**（四个可执行文件的哈希与改动前一致，本身即证据）；E15 扫描重跑，6 个 (数据, 结构) 摘要**仍与 E14 的两遍构建一致**。

## E15-6 证据表述修正（2026-09-16，审阅后追加）

审阅指出三处表述问题，已修正。**修正后重跑了扫描**（因为 §E15-5 改了 `index.hpp`），数字随之更新；以下是改法。

1. **"约 2.2 倍"是最终索引构建阶段的倍数，不是完整流程的。** 现分三层报：**最终索引构建阶段 0.431×–0.499×**、**完整构建流程 0.617×–0.657×**、**相对 ART**（§4，噪声另行标注）。`E15_TABLES.md` §3 在阶段比值后直接插入完整流程的对照表，并在 §3 开头写明 `s_new` 是"给定容量方案后的直接构建"。
2. **对账表的统计口径不一致。** 此前"旧 `rebuild` − 新构建"一行用的是**逐进程配对差的中位数**，而同表其余行是**各量的中位数**——两者不等，`mixed` 上是 `+1.54` 对 `+0.78`。现在**两种口径并列给出并逐行标注**，`E15_TABLES.md` §3b 开头写明"每个格子是跨进程中位数的中位数、差异同时给两种口径"。
   同时收回"旧 `rebuild` 与新构建**应当是同一个量**"的说法：它们是**相近工作量的对照**，量化的方式不同（`all()` 走完整 `scan` 归并子块与溢出；新路径是连续区间直拷贝），旧侧还多一次对象替换与销毁。差用于定位成本，不被要求为零。**该差本身跨运行不稳定**（上一轮扫描百万域名是 13–14 ms，本轮 3–6 ms），因此只报不解。
3. **摘要相同的强度被削弱到证据支持的程度。** 现写明：覆盖 = 区域划分、前缀、三张容量表、子块结构与每子块存储的键、边界目录、溢出条数、按扫描序的全部键值；**不覆盖 = 模型内部状态、块内空闲/垃圾字节分布、指纹标签、条目 `offset`/`length`、填充与对齐、地址**；主块/溢出归属**可推出但未显式编码**。结论统一为「**规范化结构摘要一致，测试查询结果一致，现有功能检查未观察到回归**」，不再写"物理布局逐字节不变"。
4. **查询比对不是穷举**：命中查询在 131,072 键集上按有放回抽样，覆盖约 63% 的不同键。已在 §2 标注。
5. **E14 的 55.6%–66.3% 改称阶段成本估算**，不再是"上界"；完整流程口径的比值随之改写。

**结论未变**：省掉那一次重复的完整构建确实值得做，容量规划不是优先对象。
