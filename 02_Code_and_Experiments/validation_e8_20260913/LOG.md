### E8-1 Region 容量表与偏移目录（2026-09-13）
`Region` 的标量 `slots_/start_` 替换为逐组表：`sg_[g]`（槽数，≤48）、`bb_[g]`（块字节，64 对齐）、`off_[g]`（块基址偏移目录，G+1 项）；块地址＝`storage_+off_[g]`。统一布局成为容量表的特例（每项相同），因此 E5 存储门直接覆盖新寻址代码。派生量（`start_of(g)=64+sg×16`）与全部使用点（put_primary/compact/find_impl/scan/group_stats/memory/insert）同步修改。`Index` 新增 `rebuild_with_caps(i,data,sg,bb)`（不分裂；语义不变仅容量变化），`structure_version` 机制沿用。
验证：`check.cpp`（51,000 次差分＋守恒＋穷举）通过，数字与 E5–E7 完全一致。

### E8-2 容量集中度诊断 diag_capacity.cpp（2026-09-13）
问题（评审）：溢出主要来自容量不足，还是容量分配不均？结果（16 槽/1024B）：
- mixed：21,251 组，空组 67.2%，溢出 Gini 0.936，最热 10% 组占溢出 88.4%；

### E8-8 三相位计时与 48 槽量化（2026-09-13，评审第 4、5 点）
`bench_e8` 升级为三相位：U1（目录+统一）→ D（目录+需求）→ U2（目录+统一复测，作为顺序偏差括号），另输出空间双分解（需求布局分解在 U2 破坏前采集）与 48 槽上限统计。结果（3 种子中位数）：

- tranco U1=371.1 / D=250.1 / U2=278.9：D 低于括号，改善方向明确。

### E8-16 代码可读性重构与统计修复（2026-09-13；2026-09-14 按审阅第 1 点拆开重记）

原记录把整轮写成"纯格式重构（语句内容逐字保留）"，但同一节又承认修了一处统计逻辑，两者矛盾。**整轮不能只称为格式重构**，拆成三项。

**(a) 格式调整**：index.hpp、bench_e8.cpp、check_e8_hetero.cpp 重排——逻辑块之间加空行、密集的一行多语句拆分为多行、逐语句对齐 JSON 输出与守恒断言。重构过程另发现并修复了检查程序中 `data` 变量重复声明的编译错误（编译错误，无行为影响）。E5–E7 已交付轮次按记录纪律保持原样；后续轮次沿用本排版约定。

**(b) 统计修复**：bench 的 V2 `model_other` 字段存在 **uint64 下溢**（`Index::memory()` 与各分项在不同布局状态下采样，相减得到 1.8e19）。修复为各变体在自身布局状态下同步采样。**但该修复沿用了同义反复的对账口径**（`model_other := total − 已知项`，再校验各项之和 == total），已于 2026-09-14 重做，见 E8-17。

**(c) 验证结果**：重构后重编译，存储门 51,000 次差分输出与重构前逐字一致，异构门 12,000 次差分同样一致。**测试输出一致是回归证据，不能证明所有行为完全不变**；若要确认格式部分只改变空白与注释，应核对源码差异，不必重复性能实验。

**(d) 纪律失误**：本轮两次直接运行 `./build/bench_e8.exe` 绕过运行闭环（一次跑了旧二进制）——重申：正式运行一律经 `tools_build.py run`。

### E8-19 平台迁移到 WSL2 Ubuntu（2026-09-14）
原 E8 跑在 Windows + MinGW g++ 15.2.0。为对齐原前三轮（Linux x86-64 + g++ 13.3 + taskset）与课题要求的 Ubuntu 环境，v4 迁移到 **WSL2 Ubuntu 24.04 + g++ 13.3.0**，进程内 `sched_setaffinity` 绑 CPU 0（原代码的绑核在 `#ifdef _WIN32` 内，Linux 下完全缺失）。

如实记录：**迁移不足以消除波动**。WSL2 与 Windows 共享同一宿主，宿主侧调度抢占与降频会穿透。第一次 Linux 运行的种子离散度为 26.8%，带 stderr 落盘的第二次为 11.8%——同平台、同二进制仍有明显波动，说明平台迁移不足以消除波动，**具体来源尚未隔离**，不能归因于任何单一因素。绝对耗时比归档的 v3（Windows）高约 34%–49%，因此 **v4 的绝对值不可与 E5–E7 或 E8-v3 拼接**。

第一次 Linux 运行被取代的客观原因：它跑完后 `logs/bench_*.log` 仍是更早一次 Windows 运行的 stderr 记录，与 `results/main/` 下的 Linux 结果不对应——属于本轮要消除的记录混用，与该次数值本身无关。因此重跑一次并把 stderr 正确落盘，以第二次为正式运行。**该次运行的数值未被否定，只是被取代**，已归档于 `results/archive_wsl_run1_20260914/`（见 E8-22）。
