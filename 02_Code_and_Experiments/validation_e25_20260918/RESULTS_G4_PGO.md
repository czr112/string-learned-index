## 0. 装置

**同一份源码的四个构建**（`bench_widest.cpp`）：算法、ISA 目标、数据结构与发布配置**完全相同**，只有编译不同。

| 构建 | 编译行 |
|---|---|
| **base** | `-O3 -march=x86-64-v2 -static`（发布构建，即 `bench_widest`） |
| **lto** | base ＋ `-flto` |
| **pgo** | base ＋ `-fprofile-use=build/pgo_profile -fprofile-correction` |
| **pgo_lto** | base ＋ `-flto` ＋ 上面那条 |

**训练与评估分离**：训练跑**插桩构建** `bench_pgo_gen`（`-fprofile-generate`），语料 **65,536 键**、模式 `grow`；评估用 **131,072／262,144 键**、模式 `same`。**两次运行都做了**：`g4a` 用 `grow` 训练（分布不同但完全留出），`g4b` 用 `same` 训练（同模式、四分之一规模）作为稳健性检查。

**协议**：四个构建是**独立可执行文件**，所以"一次重复"＝四个构建各调用一次、按轮转顺序。记录里的 `run_tag` 编码（进程, 重复, 构建）：`P1R0B`／`P1R0L`／`P1R0P`／`P1R0PL`。5 进程 × 4 重复 × 3 语料 × 4 个臂。比值**严格在同一次重复内、同一个臂**上求。

## 1. 先说一个必须说的协议事实：PGO 差点"看起来成功了"

第一次构建 `bench_pgo` **成功**了——链接通过、二进制可用。但 `-Wmissing-profile` 报出：

```text
warning: '…/bench_pgo.378.….tmp-bench_widest.gcda' profile count data file not found
```

**原因是 `tools_build.py` 每次编译到一个唯一临时名**（这是"编译失败不得留下可运行产物"的保证），而 **g++ 从对象输出路径派生 `.gcda` 的文件名**。于是生成方写出的名字与消费方要找的名字**永远不同**，PGO 静默地不生效。

**这正是"不能用仅成功链接判定 PGO 生效"那个情形**，而这台装置**按设计拒绝了**（`run_pgo.py` 会读回编译器自己的 stderr，出现 profile 相关诊断就 `REFUSED`，不进入计时）。

**修法**：`tools_build.py` 加一张 `STABLE_TMP` 表，让三个 PGO 相关目标编译到**同一个固定对象路径**。原子性未变（仍是先编临时、成功后 `os.replace`）；变的是同一目标的两次**并发**构建会互相覆盖——本项目构建串行，PGO 那一对由同一个脚本驱动。**`bench_lto` 不在这张表里**（它没有 profile 要找）。

修完后四个构建产出四个**不同**的可执行文件（`base=d2d4a9e5`／`lto=13041efa`／`pgo=3ab8f1e0`／`pgo_lto=60305dd5`，见 `logs/run_pgo_g4*.log`），且**没有任何 profile 诊断**——所以后面报的确实是有 profile 的构建。

### 读数

1. **LTO 单独使用：小幅、不一致。** skew/S0 两次都是 5/5（0.978／0.952），但 skew/WIDE 一次是 1.014（0/5）一次 0.975（4/5）——**符号都不稳定**；其余格的方向计数在 1–4/5 之间，量级与噪声底（1.03–1.12）相当。**记为"未观察到明确差异"更诚实**，不记为收益。

2. **PGO 在 mixed 与 skew 上的损失是「按臂」的，不是三个臂一致的。**

   - **`S0` 与 `E31` 两个臂的 8 格一致更慢**：`pgo/base` **8 格 0/5 且 >1（1.038–1.084）**；`pgo_lto/base` **8 格 0/5 且 ≥1（1.028–1.120）**。
   - **`WIDE` 臂不跟随**：`pgo_lto/base` 的 mixed/skew **四格全部 <1**（g4a mixed 0.992／g4a skew 0.972／g4b mixed 0.988／g4b skew 0.966，方向 3–5/5）；`pgo/base` 在同四格是 1.008／0.986／1.003／0.987（方向 1–5/5）。

   **所以「三个臂一致更慢 4%–12%」是错的**——本节初版把 `S0`／`E31` 的方向与量级扩写到了 `WIDE`，而**本报告的表格本身就给的是 0.992／0.972／0.988／0.966**。**表没有错，是正文越过了表。**

3. **tranco 上的收益不可复现——这是本轮最重要的一条。** `g4a` 的 tranco 三格是 **0.954／0.904／0.876（全 5/5）**，看起来是漂亮的收益；`g4b` 换成同模式训练后变成 **1.138／1.055／1.029（0–2/5）**——**符号翻转**。所以 `g4a` 的那个 tranco 优势是**那一份 profile 的产物，不是 PGO 的性质**。

4. **PGO+LTO 相对只 PGO：不一致，表内是分裂的。** `pgo_lto/pgo` **18 格中 10 格 <1、8 格 >1**，**不是一致的**。<1 的十格范围 **0.953–0.992**，其中 **4 格 5/5**：`g4a` mixed/S0 0.986、`g4a` mixed/WIDE 0.953、`g4a` tranco/WIDE 0.971、`g4b` mixed/WIDE 0.977。**十格里有 6 格来自 `WIDE` 臂**（两次运行各 3 格）、5 格来自 tranco。「LTO 把 PGO 的一部分损失追回来」只在部分格成立，**不能写成一致的**；**无论哪一格，都没有超过 base**。

5. **点查（`FIXED`）没有结论**：噪声底 1.05–1.60，绝大多数格的方向计数 0–4/5，**落在噪声内**。

## 3. 结构核查：编译不能改变索引持有什么

每个 (语料, 臂) 上，四个构建的 `overflow`／`blocks`／`memory` **逐位相同**（例：mixed/WIDE 四构建都是 `ov=748, blocks=21755392, mem=23972017`）。**所以四个构建在跑同一份数据结构**——时间差不是布局差异造成的。

## 4. 判定

按总计划 §9 的采用表：**「只有计数改善、时间和空间无可辨收益」→ 完成实验并保留负结果；「入口条件不成立／收益不可复现」→ 记录并继续**。

**结论：编译不是这根杠杆。** 具体地：

- **没有任何一个构建变体一致优于发布构建。**
- **PGO 在 mixed 与 skew 上的损失按臂而异**：`S0` 与 `E31` 两臂**一致更慢 4%–12%**（8 格 0/5），**`WIDE` 臂不跟随**（同语料四格反而 <1）。**不能概括为「PGO 在 mixed/skew 上一律变慢」。**
- **PGO 在 tranco 上的效果依赖训练集**：换一份 profile 就从 −12% 变成 +14%——**不可复现，因此不作为收益**。
- **LTO 单独使用无一致效果**（方向不稳、量级与噪声底相当）。
- **PGO+LTO 相对只 PGO 一致略快，但仍不优于 base。**

**处置**：**发布构建保持 `-O3 -march=x86-64-v2 -static` 不变**；PGO/LTO 作为**已实测的负结果**登记，**不再重做同一试验**。

## 5. 边界（必须随数字一起读）

- **这是"原型内部的编译收益"，不是"优化后原型 vs ART"。** ART 与原型在**同一个二进制**里，单方 PGO 会让 ART 也一起被优化——`g4a` 的 `pgo/lto` 在 ART 臂上就是 0.980（5/5）。**所以本轮不报任何"对 ART"的编译结论**；若今后要报，必须让外部基线**采用明确且可比的编译策略**，不能只给原型加 PGO。
- **两次训练都不是"完全匹配"的**：`g4a` 用不同模式，`g4b` 用同模式但四分之一的规模——而 `make_data` 是确定性的，**65,536 键是 131,072 键的前缀**，所以 `g4b` 的 profile 与评估数据**部分重叠**。这一点必须写明，不能把 `g4b` 当成"干净的同分布训练"。
- **没有做"按结果反复挑 profile"**——两次运行都是预先设定的训练集，看到结果之后没有重新生成。
- **只有一种 workload 形状**（长期替换到 200%）；纯插入、短期替换与扫描没有做编译对照。
- **臂序在单次调用内是固定的**（`reps=1`，程序的内部轮转为 S0→E31→WIDE→ART），驱动轮转的是**构建**。比值在同一臂上取，位置效应在比值里抵消；但**这一条不能读成"臂序受控"**——那套纪律在 `run_widest.py` 里。
- **`-fprofile-correction` 开着**：多个进程的 profile 合并时，g++ 会丢弃它认为不一致的计数器。它改变了用到哪些计数器，不改变源码与语义。

## 6. 本轮发现并修掉的装置缺陷（都影响过已有产物）

| # | 缺陷 | 后果与修法 |
|---|---|---|
| 1 | **PGO 静默不生效**（唯一临时名 vs `.gcda` 名派生） | 第一次 `bench_pgo` **构建成功但无 profile**；被 `-Wmissing-profile` 与驱动的验证**拒绝**。修法：`STABLE_TMP` 表 |
| 2 | 分析器 `keyed()` 的键里**没有 `arm`** | 每个 (构建,进程,重复) 只剩最后写入的臂（ART），于是第一版表**比的是 libart 跨四个构建**，不是原型；结构列全 0 才暴露了它。修法：键里加 `arm`，并**按臂报告** |
| 3 | 训练阶段的 `.gcda` glob **非递归** | GCC 把对象的绝对路径镜像到 profile 目录下，文件在深层；非递归 glob 找到 0 个，驱动**拒绝了**（正确的行为，但检查本身是错的） |
| 4 | 正则用 ASCII 单引号匹配 g++ 的诊断 | g++ 用的是 **U+2018/U+2019 弯引号**，匹配恒不中 |
| 5 | `run_pgo.py` **只在模式循环结束后归档** | 违反了本项目"边跑边归档"的纪律：约一小时的评估期间工作文件之外无任何留存，中断即全失。**本轮的两次运行没有中断**，所以数据完整；但这是必须修的 |

**第 2 条与本项目已经记过一次的教训同源**：一个"跑得很好、算得也没错"的分析器，如果分组键漏了一个维度，**会安静地回答一个没人问的问题**。
