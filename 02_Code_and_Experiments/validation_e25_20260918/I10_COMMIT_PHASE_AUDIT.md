# I10 提交阶段审计：`compact()` 能不能因为真实的可抛操作中断

日期：2026-09-23。触发：G0–G5 交付审阅（P0-3）。
被审计的源码：`index.hpp`，**4,697 行，SHA-256 `269b65cf37b3f82c51f0241f…`**（**审计当时**）。
审计方式：**逐行阅读提交路径上的每一个被调用函数**，判定它是否分配、是否可能抛。

> **2026-09-23 后续**：本文给出的修法**已实施**，源码已改变（`index.hpp` **4,857 行**），
> 门 `check_i10_commit` 已验收，实现、验收与回归见 **`RESULTS_I10_COMMIT.md`**。
> 本文保留为**审计当时的判定**，§1–§4 的结论与行号均指改动前的那份源码。

---

## 0. 结论先说

**不能声称「提交阶段不会中断」。** 提交路径上**存在两个真实抛点**，其中一个**必然发生在旧状态已被销毁之后**：

| # | 位置 | 抛什么 | 抛出时的状态 |
|---|---|---|---|
| 1 | `compact()` 的 `rebuild_dir(g)`（`index.hpp:2054`） | **`std::bad_alloc`**（`dir.clear()` 之后构造 `std::string` 与 `push_back`） | **记录已全部重放完毕、旧目录已被 `clear()` 销毁** |
| 2 | `compact()` 重放循环内的 `throw std::logic_error`（`:2051`） | 显式抛出 | 第 k 条已放回、其余尚未 |

**第 1 条的后果：初版写重了，据实测更正。** 初版称残缺目录会把查找**静默导向错误的子块**，
后果「比丢记录更坏」。**这道断言没有通过实测**——`check_i10_commit` 在**两个注入位置**
（`dir.clear()` 之后的第一项、以及第二项，即目录**非空但残缺**的那种）各做了一次
**全量点查扫描**（131,071 条活键，mixed 与 skew 各一轮），**误路由 0 处**；索引状态确实变了
（`index_changed: true`，目录字节数跟着变），**但没有变成错答**。

**所以正确的说法是**：旧设计在目录重建处**确实可被中断**，中断**确实留下了一个改变了的状态**，
但**它的正确性后果未被本次探测证实**。代码上**存在**那条路径——`locate_subblock` 的答案会把
搜索收窄到单块（`lo_blk = cand; hi_blk = cand + 1`，`:3289`），所以**错误的 `cand` 本来会漏键**——
**但本门没能把它触发出来，因此本文不声称它已被观察到**。

**中段中断可复现的后果仍然是 G1 测到的那个**：丢 24／173／34 条且 `size` 失真。
**修法的理由不依赖上面这条更正**：I10 要的是「提交段不含可失败操作」，
而现在这一点是**由构造保证**的（提交段只有 `append_planned` 与 `noexcept` 的 `swap`）。

## 2. 重放循环是「无分配」的——逐项核过

| 调用 | 实现 | 分配？ |
|---|---|---|
| `live[k]` | `std::vector<Pair>` 下标读 | 否 |
| `Fingerprint::of(live[k].first)`（仅 `!want_tags` 时） | 哈希计算 | 否 |
| `put_primary(g, s, value, tg)`（`:1909`） | 只调用 `insert_into`；**自身不分配** | 否 |
| `insert_into(g, i, s, value, tag)`（`:1653`） | 检查槽位与字节 → `es[j] = es[j-1]` 描述符搬移 → `memcpy` 写入块内预分配区 → 写头 | **否** |

**关键的一条**：`insert_into` 在**前插**时会调 `rebuild_dir(g)`（`:1681`），而
`compact()` 在进入循环前把 `suppress_dir_rebuild` 置为 `true`——**所以重放期间目录一次都不会被重建**。
这正是「重放循环无分配」成立的原因，**而它依赖的是一个布尔开关，不是类型保证**。

**所以循环内唯一的抛点是 `:2051` 的显式 `throw std::logic_error("compaction lost capacity")`。**
它是「不该发生」的不变量违例，但**它确实是一行可执行的 `throw`，位于组已被改动之后**。

## 3. `rebuild_dir` 是真正的缺口

```cpp
void rebuild_dir(std::uint32_t g) {           // index.hpp:1530
    if (dirs_.empty()) return;
    auto& dir = dirs_[g];
    dir.clear();                              // <- 旧目录在这里就被销毁了
    const std::size_t nb = subblocks(g);
    if (nb < 2) return;
    for (std::size_t i = 0; i < nb; ++i) {
        ...
        dir.push_back({std::string(suffix(g, i, entries(g, i)[0])),   // <- 分配
                       static_cast<std::uint32_t>(i)});               // <- 分配
    }
}
```

`dirs_` 是 `std::vector<std::vector<Boundary>>`（`:1395`），`Boundary` 内含 `std::string`。
每一次 `push_back` 都可能因**构造字符串**或**扩容目录向量**而抛 `std::bad_alloc`。

**这是「先销毁、后重建」的写法**：`clear()` 与 `push_back` 之间没有任何保护，
**所以这个循环不是原子替换，而是就地重建**。抛在第 i 次迭代上，
留下的是**前 i 个边界项构成的残缺目录**，而**组内记录此刻已经全部就位**。

**两个直接后果**：

1. **目录残缺且没有任何计数器或断言会察觉**——它只在后续查找里表现为「找不到本该找到的键」。
2. **它不是可恢复状态**：`compact()` 已经把原目录的字节释放掉了，**没有回滚的余地**。

---

## 4. 「真实分配会不会失败」这一问

审阅要求区分「可抛」与「真的会抛」。**本文不声称 `bad_alloc` 在这条路径上常见**——
它需要分配器在目录项数规模上失败。要主张的是另外两件事：

1. **契约层面**：只要路径上有分配，就**不能**声称「提交阶段不会中断」；
   **「通常不会失败」不是 no-throw 契约**。审阅给出的两条路（证明 no-throw，或改成 prepare/commit）里，
   **第一条现在不成立**。
2. **量级层面**：这个目录**每个组每次压缩整体重建一次**，长期替换负载下压缩次数是千级
   （G3 的 `check_widest` 计数：200% 时 `compactions` 为百到千量级）。
   **触发概率低，但触发时的后果是静默错答**，而本项目的正确性口径不接受这一点。

## 5. 修法（按原任务书 §6.3：把可能失败的工作放在提交之前）

**目标形态**：提交阶段只由「无分配的写」与「`noexcept` 的替换」构成。**已实现**，见 `check_i10_commit.cpp`。

| 步骤 | 改动 |
|---|---|
| **① 把容量检查提到提交之前** | 在 `:2024` 改动任何状态**之前**，用 `live` 的字节与条数逐子块核对 `bb_[g] - bottom` 与 `slots_of(g)` 是否容得下。**容不下就此刻返回 false，组一个字节都没动。** 这样 `:2051` 的 `throw` 变成「不该发生」且**可被前置检查排除**；保留时也应在提交前触发。 |
| **② 目录改成「先建后换」** | 在**局部** `std::vector<Boundary>` 里构造新目录（分配都发生在这里），成功后再 `dir.swap(local)`——**`std::vector::swap` 是 `noexcept`**。构造失败则旧目录原样保留。 |
| **③ 断言提交段无分配** | ②之后，`rebuild_dir` 在提交段内的调用点只剩 swap。把「提交段不分配」写成一条**可检查的**约束（例如提交段内不再调用任何 `rebuild_dir` 的重载，只调 `swap_dir`）。 |
| **④ 重跑注入** | 准备点与提交中途（`k == live.size()/2`）两个注入都重跑，**并要求提交点注入不再改变任何持久状态**（改由 ① 在提交前拦住）。 |

**②的一个更彻底的变体**：连目录的构造也提前——目录内容依赖重放后的状态，所以只能在重放后构造；
但可以**在准备阶段就预留好容量**（`local.reserve(nb)`），使构造阶段只剩下 `std::string` 的分配，
**再进一步则可为 `Boundary::key` 改用与块内后缀同生命周期的视图**，把分配也消掉。**这一层是可选优化，不是完成 ①–③ 的前提。**

## 6. 与既有证据的关系

- **G1 的注入实验结论不变**：准备阶段原子、**提交阶段不原子**。本文给出的是**成因**。
- **本文的判定会让「提交阶段不原子」从「测得的现象」升级为「已定位的机制」**：
  破坏原子性的不是记录重放本身（它是无分配的），**是重放之后的目录重建**。
- **①–④ 落地后 `index.hpp` 改变**（已成为事实），于是**所有构建记录漂移**、正确性门需要全部重建复跑、
  **G3／G5 的计时需要重测**——**这正是 G0 判定的那类缺陷**。所以它作为**独立一轮**完成：
  重建 → 复跑门 → 重测三个 sweep → 更新文档。**结果见 `RESULTS_I10_COMMIT.md` §3。**
- **在改动落地之前**，正确性口径写成：「**I10 在生产路径上仍是开放的正确性欠账**：准备阶段原子；
  提交阶段存在两个真实抛点，其中目录重建发生在旧目录销毁之后。**未修复。**」
  **落地之后**见 `RESULTS_I10_COMMIT.md`：提交段已不含可失败操作，`compact_plan_commit` 开关默认 **false**，
  待计时对照后再决定是否翻转。
