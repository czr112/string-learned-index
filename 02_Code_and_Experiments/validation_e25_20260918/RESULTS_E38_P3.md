# E38/P3 结果：M0 ／ HPT＋Context16 区域回退 ／ ART

日期：2026-09-22。目录：`validation_e25_20260918`。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**三臂**：**M0**（冻结的参考模型）／**HPT ＋ Context16 区域回退**（下称 **HPT 臂**）／**ART**（同轮重测）。

**首轮只测三件事**：**完整构建、静态混合点查、常驻空间**。映射、指纹字节、子块访问、溢出探测走**独立的诊断构建**（`diag_lits_adapter`），**不与计时并行**。纯命中与纯未命中作为**独立负载**另行报告，**不是**混合负载的分解。

**"扫描"在这里指的是遍历实验配置**，不是对索引做范围扫描。

## 0. 装置与协议

**协议**（`run_lits.py`）：**5 个独立进程** × 3 语料 × 2 模式 × **3 次重复**。臂在同一次重复内**轮转**，`rep 0 → 0 1 2`、`rep 1 → 1 2 0`、`rep 2 → 2 0 1`，**每个臂在每一个位置恰好出现一次**——驱动**计算并断言**这一点，不满足则拒绝启动。

**比值一律在同一次重复内求**（同一进程、同一次重复、那一对的两个臂），报告**每进程中位数**、**五进程的中位数**、**方向计数（k/5）**与**噪声底（五进程中位数的 max/min）**。**落在自身噪声底内的变化记为"未观察到明确差异"。** 比值 < 1 表示**前者更快或更小**。

**每臂按自己的需求重新规划容量**：区域边界、组数 `G`、主块预算与规划算法在两臂间相同，**只有被测量到的需求不同**——那正是实验对象。

## 1. 完整构建（`build_ms`）

**这一项本轮才被单独测出来。** 记录里原有的 `cum_ms` 是**到某检查点的累计维护时间**（含构建 ＋ 该检查点之前的替换周期），把它当构建耗时用会把两个量折在一起。现在三臂用**同一个计时窗口**只量构建；**HPT 臂的窗口里包含共享 HPT 的训练**（`Index::bulk_load_with_plan` → `ensure_lits_shared`），这是有意的：用这个后端建库的代价就包含训表。

| 数据／模式 | HPT/M0 | 中位数 | 方向 | 噪声底 | 绝对（M0 → HPT） |
|---|---|---:|---|---:|---|
| mixed / same | | **2.410** | 0/5 | 1.155 | 37.0 → **89.8** ms |
| mixed / grow | | **2.447** | 0/5 | 1.135 | 34.6 → **87.4** ms |
| skew / same | | **2.555** | 0/5 | 1.163 | 42.8 → **111.8** ms |
| skew / grow | | **2.687** | 0/5 | 1.143 | 41.4 → **112.6** ms |
| tranco / same | | 1.099 | 0/5 | 1.143 | 78.4 → 86.2 ms |
| tranco / grow | | 1.144 | 2/5 | 1.312 | 77.3 → 87.1 ms |

**读法：**

1. **mixed 与 skew 上构建慢 2.4×–2.7×，方向五进程一致。** 绝对增量 **+50 到 +72 ms**，三个语料上量级相同——**这与"训一张 2 MiB、1024 次独立分配的表"的固定代价相符**，与键数关系不大。
2. **tranco 那一格落在自己的噪声底内**（1.099 对噪声底 1.143；1.144 对 1.312）——**记为未观察到明确差异**，不记为"更快"。tranco 有 262,144 个键、建库本身 78 ms，**固定训练代价被摊薄了**。
3. **对 ART**：HPT/ART **1.81–2.74（0/5）**，**全部更慢**。M0/ART 则是 **skew 上我们更快（0.68–0.75，5/5）、tranco 上 ART 更快（2.4–2.5，0/5）、mixed 上持平**——**换模型没有改变"对 ART 的构建劣势"这件事，skew 上还把它放大了**。

## 2. 静态混合点查（`query_ms`，200% 检查点）

| 数据／模式 | HPT/M0 | 方向 | 噪声底 | HPT/ART | M0/ART |
|---|---:|---|---:|---:|---:|
| mixed / same | 1.135 | 1/5 | 1.238 | 2.082 | 2.042 |
| mixed / grow | 1.087 | 1/5 | 1.278 | 1.854 | 1.656 |
| skew / same | **0.867** | **5/5** | 1.565 | 1.270 | 1.668 |
| skew / grow | **0.939** | 4/5 | 1.240 | 1.653 | 1.801 |
| tranco / same | **0.770** | **5/5** | 1.251 | 1.608 | 1.985 |
| tranco / grow | **0.843** | **5/5** | 1.327 | 2.130 | 2.562 |

**读法：**

1. **skew 与 tranco 上点查更快，方向五进程一致**（tranco 0.770／0.843，skew 0.867／0.939）。**这是模型的收益第一次出现在端到端点查上**，而不是只出现在布局统计里。
2. **mixed 上的 1.135／1.087 落在自身噪声底内**（噪声底 1.238／1.278）→ **记为未观察到明确差异**，不记为"慢了 9%"，也不记为"追平"。
3. **对 ART 仍全面落后**（HPT/ART 1.27–2.13，0/5）。**接入 LITS 没有改变原型相对 ART 的位置**：M0/ART 是 1.66–2.56，HPT/ART 在同一区间。
4. **skew/same 那一格的噪声底 1.565 偏高**（五进程范围 0.634–0.992），所以 **0.867 这个中位数要按高噪声格读**，不如 tranco 那两格可靠。
5. **没有一个格子落在"混合查询"之外**：这里的混合查询就是前面各轮的混合点查负载，**纯命中／纯未命中在 §3 单独列**。

## 3. 纯命中与纯未命中（独立负载）

固定查询队列，`ns_per_query`。**这两者是独立负载，不是 §2 的分解**——队列由固定种子生成、两臂同键同结果（`queue_hash` 逐臂比对）。

| 数据／模式 | 纯命中 HPT/M0 | 方向 | 噪声底 | 纯未命中 HPT/M0 | 方向 | 噪声底 |
|---|---:|---|---:|---:|---|---:|
| mixed / same | 0.784 | 4/5 | 1.564 | 0.837 | 4/5 | 1.378 |
| mixed / grow | **0.751** | **5/5** | 1.174 | 0.964 | 4/5 | 1.295 |
| skew / same | 0.780 | 5/5 | **3.227** | 0.935 | 4/5 | 1.233 |
| skew / grow | 0.780 | 5/5 | 1.177 | 0.936 | 3/5 | 1.456 |
| tranco / same | 0.941 | 3/5 | 1.686 | 0.835 | 4/5 | 1.533 |
| tranco / grow | 0.873 | 5/5 | 1.196 | 0.825 | 5/5 | 1.236 |

**读法**：**纯命中侧 HPT 更快**（0.75–0.94，多数格 5/5），**纯未命中侧也偏快但方向计数更弱**（0.82–0.96，3–5/5）。**skew/same 的噪声底 3.227 说明那一格不可用于结论**——五进程范围 0.270–0.872 跨度过大（该数据集的命中分布极不均匀），**只登记不上结论**。

**ART 不参加队列阶段**（它不是 `Index`，没有标签／子块／溢出结构），所以这一节的 LITS/ART 与 M0/ART 一律为 `--`，**不是缺失**。

## 5. 必须随数字一起读的口径

### 5.1 回退覆盖率——**对应被计时的那份状态**

| 数据／模式 | LITS 区域／活跃区域 | LITS 记录／总记录 | 回退原因 |
|---|---|---|---|
| mixed / same | **61/64 = 95.3%** | 124,929/131,072 = 95.3% | admission=**3**，其余 0 |
| mixed / grow | **61/64 = 95.3%** | 124,928/131,072 = 95.3% | admission=**3**，其余 0 |
| skew / same | 64/64 = **100%** | 131,072/131,072 = 100% | 全 0 |
| skew / grow | 64/64 = **100%** | 100% | 全 0 |
| tranco / same | 128/128 = **100%** | 262,144/262,144 = 100% | 全 0 |
| tranco / grow | 128/128 = **100%** | 100% | 全 0 |

**这是"当前活跃区域"的口径**，不是"整轮构造过的区域"——后者在正确性门上测到过 **18.2%／17.0%／7.9%**，两者**相差约两倍**，因为多数回退发生在过程中的临时构造上、重建时又校准成功。**拿累计值解释一个静态成绩是错的**，见 §5.1 的更正记录。

**回退查询占比**（只能在跑某个查询序列时测）：

| 数据／模式 | 命中队列 | 溢出队列 | 未命中队列 |
|---|---|---|---|
| mixed / same | **14/484 = 2.9%** | 0/2048 = 0% | 0/2048 = 0% |
| mixed / grow | **8/239 = 3.3%** | 0% | 0% |
| skew / tranco 全部格 | 0% | 0% | 0% |

**所以：mixed 上约 5% 的区域走 Context16，被问到的查询里约 3% 落在它们上；skew 与 tranco 上是纯 HPT。** 臂名"**HPT ＋ Context16 区域回退**"就是为这个而取。

### 5.2 那 3 个被拒的区域

mixed 的 64 个区域里有 3 个**被保守的数值准入界拒收**（`|G·α|·(区域最长键+1) + |G·β| > 1e9`）。**正确叫法是"被保守数值界拒收"，不是"模型无法区分键"**——局部线性校准本来就在放大小跨度。本轮**没有**对它们做校准后组号分布／碰撞／数值稳定性的测量，所以**不宣称**模型在那里分辨不出什么。

**这个准入策略改变了 HPT 臂的覆盖范围**，它是一条**策略选择**，不是安全机制（安全由 `predict_group` 的运行时饱和保证）。

## 6. 本轮发现的装置缺陷（都已修，但都影响过已有产物）

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `run_lits.py` 的 `--reps` 默认 4，而 `PHASES` 里写的是 3，**驱动读的是前者** | 第一次正式采集（`p3a`）用 4 次重复跑，**三臂下轮转不平衡**，**已作废** |
| 2 | 基准里的轮转数组是 `int order[4]`（四臂遗留），`ARMS` 已是 3 | 第 4 项未被读（循环走 `oi < ARMS`），**无功能影响**，但注释与数组宽度不符，已修并有 `static_assert` |
| 3 | 位置平衡断言**对诊断阶段也生效** | 诊断阶段 1 次重复、三臂，**平衡不可能成立**，于是 `REFUSED: arm 0 is not position-balanced: [1, 0, 0]`——**守卫自己误报了一个合法配置**（与 P1 那次"语料相关的非空性断言"同类）。已限定为只对计时阶段断言 |
| 4 | 记录里**没有单独的构建耗时** | 首轮要求的"完整构建"无法从 `cum_ms` 里分离出来。已加 `build_ms`，**`p3a` 的数据因此没有这一项**，重新采集为 `p3b` |
| 5 | 我加计时器后**没重建诊断目标** | 诊断阶段全部 `rc=2`——**严格运行入口正确地拒绝了过期二进制**，这正是它存在的理由 |

**产物登记**：`p3a` 的两个文件**保留在工作区、不删除**，但**不进入分析**（协议不正确／缺构建字段）；`p3b` 是正式数据。`p3a` 的那次运行**不是中断**，是**协议作废**，与预检报告里登记的那 200 条（中断后删除）是两回事。

## 7. 边界

- **这一轮不改模型参数、不改容量规划、不改溢出策略。** 上面全部是"照原样接入"的结果。
- **`same` 与 `grow` 是长期替换负载的标签**，沿用前几轮以便对照；**本轮没有做长期替换，也没有做范围扫描**。
- **ART 的队列与空间列为 `--`**：它不参加队列阶段，也不是 `Index`。这是设计，不是缺测。
- **`skew/same` 的纯命中格噪声底 3.227**，只登记，不结论。
- **HPT 臂的构建耗时含训表**；把它读成"纯预测开销"会重复计数。
- **诊断阶段（映射、指纹字节、子块访问、溢出探测）单独采集**，其数据不与本节混用。


## 8. 诊断构建：机制在哪里

`diag_lits_adapter`（**独立运行，不与计时并行**）的 200% 检查点队列计数。三语料、两臂、固定队列。

| 数据 | 臂 | 溢出线性查询 | **每次溢出查询读过的记录数**（线性路径） | 标签拒绝 | 标签通过 |
|---|---|---:|---:|---:|---:|
| mixed | M0 | 6,084 | **84,804** | 78,309 | 651 |
| mixed | **HPT** | 5,892 | **47,922** | 41,583 | 258 |
| skew | M0 | 324 | 5,547 | 5,211 | 54 |
| skew | **HPT** | 237 | **3,048** | 2,793 | 24 |
| tranco | M0 | 4,110 | **156,693** | 150,480 | 816 |
| tranco | **HPT** | 2,685 | **121,356** | 120,849 | 507 |

**读法**：**HPT 臂上溢出线性扫描读过的记录数一致下降**——mixed **−43.5%**、skew **−45.1%**、tranco **−22.6%**。标签拒绝数随之等比下降（要拒的记录本来就少了）。

**这就是 §2 与 §4 之间的因果链**：HPT 的映射把**更少的记录放进溢出**（§4 的空间降幅同向），线性扫描因此更短，点查更快（§2）。**不是**把溢出读得更快——E34/E35/E36 都试过那条路（O1 的稳定存储、T8 的内联标签），点查都没赢过冻结版本；**这一轮赢在让溢出里没那么多东西**。

**与 §2 的一致性**：tranco 的记录数降幅最小（−22.6%）却有最大的点查收益（0.770／0.843），说明**收益还取决于溢出在这条路径上占多少**，不只是绝对条数；mixed 的条数降幅最大（−43.5%）而点查落在噪声底内，同一个道理的反面。**这条因果链是"同向"的证据，不是逐格的定量预测**，本轮不做逐格归因。

**边界**：这是 `-DE25_DIAG` 构建，**计数开销在比较循环内部且两臂不对称**，所以**它的时间一概不报**，只用计数。
