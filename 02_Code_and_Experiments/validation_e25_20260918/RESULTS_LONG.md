# 长期替换结果：50%／100%／200% 累计周期

日期：2026-09-20。目录：`validation_e25_20260918`（补任务书阶段三的原定测试）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**本轮不开发任何优化，只用冻结版本补原定测试。** 对照是 **C1 vs C2**——要判断的是 **C2 自身的长期价值**；"最终版本 vs ART"是另一个问题，在 `E25_TIME.md`／`E26_TAGS.md` 里用同轮 ART 臂回答。

---

## 0. 结论摘要

1. **空间不趋稳。** 三种数据、两种模式下，溢出与索引字节都**单调增长**；到 200% 周期时**溢出条数已接近活跃记录数**（混合 128,533／131,072；重复前缀 127,070／131,072；百万域名 127,053／262,144）。**C1 与 C2 的空间完全相同**——**C2 不解决空间增长**。
2. **C2 的时间收益依负载而定，不是普遍的。** 在"替换键更长"的负载上它全程有效（C2/C1 = 0.69–0.93）；在"等长替换"上 **25%–100% 完全无效**（0.98–1.02、方向不一致），**只在 200% 才出现**（0.87–0.93、方向 5/5）。
3. **C2 从不造成一致劣化**：所有 24 个格子的比值 ≤ 1.02，方向不成立的几格是噪声。
4. **C2 的收益随运行长度增长**：等长模式下它拒绝的压缩占比从 25%–100% 的 **0%** 升到 200% 的 **39%**。

---

## 1. 工作负载（必须与数字一起读）

- **活跃记录数恒定**：每个周期删除一个活跃键、插入一个不同的键，活跃数始终为 N（任务书要求）。
- **检查点** `25%／50%／100%／200%`，N 个周期为 100%。
- 索引每段结束后**与参考表逐点抽查**，漂移即中止（不给一个测的不是同一结构的时间）。
- **两种键模式**，因为只报一种会把原因留成空白：

| 模式 | 替换键 | 说明 |
|---|---|---|
| `grow` | 原键 + 有界后缀（约 10 字符） | **键长分布也随之漂移**——插入一个真正"不同"的键就是这样 |
| `same` | 与被替换键**等长**、锚在同一位置 | 键长分布与容量规划时**完全一致**；**只有它能回答"纯 churn 下空间是否趋稳"** |

## 2. 时间（同一次重复内配对，按进程取中位数）

### `grow` 模式

| 数据 | 25% | 50% | 100% | 200% |
|---|---:|---:|---:|---:|
| 混合字符串 | **0.928（5/5）** | **0.928（5/5）** | **0.694（5/5）** | **0.775（5/5）** |
| 重复前缀 | **0.561（5/5）** | **0.582（5/5）** | **0.610（5/5）** | **0.657（5/5）** |
| 百万域名 | **0.734（5/5）** | **0.655（5/5）** | **0.694（5/5）** | **0.732（5/5）** |

### `same` 模式

| 数据 | 25% | 50% | 100% | 200% |
|---|---:|---:|---:|---:|
| 混合字符串 | 0.993（3/5） | 0.991（3/5） | **1.009（2/5）** | **0.927（5/5）** |
| 重复前缀 | **1.005（2/5）** | 0.993（3/5） | 0.982（3/5） | **0.874（5/5）** |
| 百万域名 | 0.997（4/5） | 0.980（4/5） | **1.019（1/5）** | **0.929（5/5）** |

**读法**：`grow` 下 C2 全程有效；`same` 下 25%–100% **落在噪声里**（方向只有 1–4/5，且比值跨过 1.0），**到 200% 才一致成立**。**C2 的收益不是负载无关的。**

**C2 从不一致劣化**：24 格全部 ≤ 1.02；超过 1.0 的三格方向都是 1–2/5，即噪声。

## 3. 空间：**不趋稳，而且 C2 不解决它**

| 数据 | 模式 | 指标 | 25% | 50% | 100% | 200% |
|---|---|---|---:|---:|---:|---:|
| 混合字符串 | `same` | 溢出条数 | 16,743 | 39,829 | 98,564 | **128,533**（活跃 131,072） |
| | | 索引 MB | 24.35 | 28.17 | 37.28 | **41.13** |
| 重复前缀 | `same` | 溢出条数 | 31,724 | 62,963 | 125,996 | **127,070** |
| | | 索引 MB | 25.29 | 29.42 | 39.93 | **40.07** |
| 百万域名 | `same` | 溢出条数 | 23,546 | 45,164 | 85,594 | **127,053**（活跃 262,144） |
| | | 索引 MB | 26.18 | 27.96 | 31.30 | **34.82** |

**C1 与 C2 在每一格的溢出条数与索引字节完全相同**（等长模式下逐位相同；增长模式下相差 ≤ 25 条）。**C2 改变的是时间，不是空间。**

**到 200% 周期时，混合与重复前缀上溢出的条数已接近全部活跃记录**——主块几乎不再持有记录。**这不是"趋稳"，是持续退化。**

### 3.1 组号转移：已测量，**此前的归因被推翻**

本报告此前写"原因在数据里：替换键落到别的组（模型映射变了）"。**那是推断，现已实测并否定它。**

`diag_transfer`（`-DE25_DIAG`）在每个替换前后各取一次该键的**逻辑组号**，逐周期比对：

| 模式 | 数据 | **换组的替换数 / 总周期** | 占比 |
|---|---|---:|---:|
| `same` | 混合字符串 | **41 / 262,144** | 0.016% |
| `same` | 重复前缀 | **48 / 262,144** | 0.018% |
| `same` | 百万域名 | **241 / 524,288** | 0.046% |
| `grow` | 混合字符串／重复前缀 | **0 / 262,144** | 0 |
| `grow` | 百万域名 | 6 / 524,288 | 0.001% |

**几乎没有替换会改变逻辑组。** 所以"分布漂移"不是已测到的机制，**此前的归因作废**。（`grow` 模式换组更少，因为它只是把原键加长，前缀不变。）

### 3.2 那么增长的机制是什么：**擦除只还槽位、不还字节**

等长替换下每个组**收一条、放一条，记录数不变、总字节不变**——本该稳态。数据给出的机制是：

1. `erase` 把一个条目从描述符数组里移出，**槽位**立即空出；
2. 但那条记录的**后缀字节留在块内**，子块的**水位 `bottom` 不动**，于是 `bottom − start_of(g)`（可用后缀字节）**没有增加**；
3. 后续插入要的是**字节**。若该子块本来按字节就满了，新键仍然放不进去；
4. `compact` 的触发条件是 `group_has_room(g, len)`——**某个子块同时有空槽且有足够字节**。组里有垃圾、却**没有任何一个子块同时满足两者**时，**压缩一次都不会跑**，垃圾持续积累，更多记录被推到溢出。

**这是一条可检验的机制，与 E24 的"合法迁回 11/12 格为 0、卡在字节上"直接接续**，也正是下一步 F0–F3 快照试验要分辨的：**F1（只回收该子块垃圾）若有效，则碎片是直接原因；F1 无效则要 F2／F3。**

**本条仍是"与数据一致的机制"，不是已证根因**——它需要 F0–F3 的对照来确认。

## 4. 压缩工作随运行长度的变化（诊断构建，计数器按臂重置）

| 模式 | 数据 | 臂 | 200% 时的压缩次数 | 重放记录数 | 复制量 | 促成的放置 |
|---|---|---|---:|---:|---:|---:|
| `grow` | 混合字符串 | C1 | 10,253 | 886,101 | 42.3 MB | 1,809 |
| | | C2 | **3,081** | **368,466** | **17.3 MB** | 1,057 |
| `grow` | 重复前缀 | C1 | 36,504 | 3,933,695 | 236.7 MB | 4,657 |
| | | C2 | **10,421** | **1,669,452** | **98.5 MB** | 2,634 |
| `same` | 混合字符串 | C1 | 14,639 | — | — | — |
| | | C2 | **8,962** | — | — | — |
| `same` | 百万域名 | C1 | 48,344 | — | — | — |
| | | C2 | **35,987** | — | — | — |

**C2 的拒绝率随运行长度增长**：等长模式下 25%–100% 它**一次都没拒绝**（C1 与 C2 的压缩次数逐位相同），到 200% 拒绝了 **39%**（混合 14,639→8,962）。

**这不是缺陷，是判据的性质**：门是"组内可回收垃圾 ≥ 待放置记录长度"，运行越久、垃圾越多，这个条件越容易满足——**所以 C2 在长运行里比在短运行里更常生效。**

## 5. 对冻结版本的影响

**不改变冻结决定，但把 C2 的边界写清楚：**

- C2 **从不一致劣化**（24 格 ≤ 1.02，方向成立处全为改善）；
- C2 的**收益是负载相关的**——E26 短程 `replace` 上 0.049–0.970，长期 `grow` 上 0.56–0.93，长期 `same` 上前 100% 无效、200% 才 0.87–0.93；
- **C2 不解决空间增长**，也**不声称解决**；它省的是压缩时间。

**"长期替换下空间趋稳"这个目标没有达到**，而且**不是本轮四项改动能解决的**——这一点由数据直接支持（C1 与 C2 的空间逐位相同）。

**至于它指向什么，本轮只是列出候选而不下结论**：可能是组分布漂移、可能是组内槽位/字节/键序三者的错配、也可能是区域容量分配本身不适用。**§3 已说明"分布漂移"那一步未测量**，因此不能据此认定根因。

---

## 6. 适用边界

1. **工作负载是"删除一个活跃键、插入一个不同的键"，活跃数恒定**；不是混合负载，也不含批量插入。
2. **两种键模式都报**；`grow` 的键长分布漂移，`same` 不漂移——**只有 `same` 能支持关于纯 churn 的陈述**。
3. **检查点到 200% 周期**；更长的运行未测，**趋势上看不出会自行趋稳**。
4. **诊断构建每臂只跑一次**（计时是 5 进程 × 3 重复）；压缩次数与复制量来自诊断，计时来自干净构建。
5. **计数器的按臂重置是本轮修的一个 bug**：不重置时 C2 的累计值含 C1 的部分，表现为"C2 重放比 C1 多 35×"。
6. **单线程、单核绑定**；无 sanitizer。
