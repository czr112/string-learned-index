# G5 —— B+ tree 外部基线（TLX）

日期：2026-09-23。run_id **`g5bt`**。目录：`validation_e25_20260918`。
装置：`bench_btree.cpp`（四臂）／`third_party/fetch_tlx_btree.py`／`run_widest.py --phases bt`／`analyze_btree.py`。

---

## 0. 为什么加这一个基线

文献任务书 §十 要求「**应增加一个支持相同字符串、值所有权和扫描语义的成熟 B+ tree 候选**」。

此前的外部基线只有 **libart**，而它是**基数树**，不是有序容器：

- 它**没有 seek-to-key 的迭代器**，所以本项目测出来的扫描是**适配器全树遍历**的成本（E23 实测慢 **40×–3823×**，并已判定**那是适配器的成本**）；
- 因此「原型 vs 成熟的有序容器」这个问题**一直没有被测过**。

---

## 1. 选了哪一棵，以及为什么不是最常想到的那一棵

| 候选 | 许可 | 处置 |
|---|---|---|
| **STX B+ Tree**（`bingmann/stx-btree`） | **GPL-3.0** | **不采用**。引入即等于**把整个项目重新许可为 GPL-3.0**——**这是项目所有者的决定，不是本轮的决定** |
| **TLX**（`tlx/tlx`，STX B+ tree 的维护后继） | **BSL-1.0（宽松）** | **采用** |
| Abseil `btree_map` | Apache-2.0 | 未采用：需要引入的传递闭包远大于三个头文件 |

**固定方式与 libart 相同**：`third_party/fetch_tlx_btree.py` 钉住 commit `2dd63ab839909f0b43cd02108a1869c4670b2c8e`，**每个文件按 SHA-256 ＋ 字节长度校验，不符即中止**。包含闭包是从该 commit 解析出来的，**恰好三个头文件**：

```

tlx/container/btree.hpp      130,659 B   566bc3f8ba7199f6…

```

**能编译**：g++ 13.3.0、`-std=c++17 -O3 -march=x86-64-v2 -static` 下零错误零警告。

## 2. 语义对齐（不对齐就不是基线）

| 维度 | 原型 | libart | **TLX B+ tree** |
|---|---|---|---|
| 键 | `std::string` 完整键 | 同 | **同**（无截断、无前缀压缩） |
| 值所有权 | `std::uint64_t` **按值存** | 同 | **同**（`btree_map<std::string, std::uint64_t>`） |
| 扫描 | 从第一个 `key >= start` 起、至多 n 条、升序、**完整键值** | **无 seek 迭代器** | **同**（`lower_bound` 顺序迭代） |
| 更新 | 擦一个活键、插一个新键，**活跃数恒定** | 同 | **同** |

**扫描是逐起点对参考表校验的，不是一个总数校验**：每条记录在**每个检查点**把结果与参考 `std::map` 逐起点比对（哈希），**不一致就中止本次运行**，所以**本文件里的任何扫描耗时都不可能测在错的输出上**。归档记录里 `scan_acc == scan_exp` 逐条成立。

> **一个自己踩的坑，记在这里**：这项检查的第一版把两侧累加器的**初值取成了不一样的种子**（一侧 FNV 偏移基准、一侧 0），于是它**必然报错**——那是**检查本身的缺陷，不是索引的缺陷**。修好后加了「逐起点 + 报出第一个不符的起点与两侧条数」的失败信息，否则「扫描不一致」这句话不可诊断。

**另一个自己的坑**：扫描的**参考遍历原本被写在了计时区间之内**。它给**每个臂**都加上了同样的参考工作，**不会相消**——那会把所有配对比值**拉向 1**，让基线和原型看起来比实际更接近。已把参考计算挪到计时区间之外（更新循环本来就是这么做的）。

## 5. 结论

| 问题 | 回答 |
|---|---|
| 原型相对**成熟有序容器**的位置 | **点查更快（0.633–0.931，5/5）；维护更慢（1.526–5.990，0/5）；扫描更慢（1.200–2.113，0/5）** |
| A1′ 能不能补上维护差距 | **补不完**：`WIDE/BTREE` **1.076–1.642，六格仍全部 0/5** |
| A1′ 对扫描 | **未观察到明确差异**（除 mixed/same 一格） |
| 与 ART 的对照 | 原型**点查也慢于 ART**（1.529–2.846），但**维护上对 ART 的差距（2.36–8.18）比对 B+ tree 的（1.53–5.99）更大**——**两个外部基线给出的短板不是同一个** |

**这条对外对照把「原型相对同类有序容器」的画像补全了**：**它赢在点查、输在维护与扫描**，而且**这不是靠 A1′ 能扭转的**。此前只有 ART 一个基线时，「维护是短板」看起来像是「相对基数树的短板」；现在有了 B+ tree，**维护仍然是短板，幅度还更小一些（1.53–5.99 对 ART 是 2.36–8.18）**——**同样的结论在两个不同族的基线上都成立**。

## 6. 边界（必须随结论一起读）

1. **TLX 跑的是它的库默认参数，没有手调**。它的槽位数是**由 `sizeof(value)` 推出的**（`max(8, 256 / sizeof(Value))`）；对 `std::pair<const std::string, std::uint64_t>` 而言这**落到下限 8 槽/节点**。**一个手调过节点大小的 B+ tree 可能更好**——本报告不声称「B+ tree 就该是这个成绩」，只声称「**库默认参数下的成熟 B+ tree 是这个成绩**」。
2. **不测尾延迟**（本基准没有逐操作计时装置）。
3. **ART 的扫描不测**，理由见 §0；**不对 libart 的扫描下任何结论**。
4. **空间不与外部臂比较**，理由见 §4。
5. **`grow` 与 `same` 是两种负载**，结论按格报告，不合并。
6. **单机、单线程**，与项目其余部分相同。
