## 0. 先纠正一句话：运行中的代码**有**预测模块

此前"我负责的部分没有模型"这个说法不准确。准确的说法是：

- **模型的训练与选型不在本课题的职责内**（属于模型负责人）；
- **但索引内部一直运行着一个表驱动的参考模型**，构建时现场训练、查询时现场预测，索引靠它的输出决定记录落在哪个逻辑组。

所以"原型 vs ART"从来不是"无模型 vs 有模型"，而是"**参考模型 + 本索引结构** vs ART"。方案 §1.1 在 E3 历史源码上核实的结论，在**当前冻结版本上同样成立且更完整**——本文件用当前源码的具体位置、配置与一次真实运行给出。

## 1. 模型是什么（当前源码）

| 项 | 内容 | 位置 |
|---|---|---|
| 种类枚举 | `ModelKind { Context16, Position16, Unigram }` | `index.hpp:468` |
| 实际启用 | `Context16`（`Config` 默认值与 `baseline_config()` 都显式写死） | `index.hpp:476`、`switches.hpp:46` |
| 模型类 | `class Model`：**量化概率上的整数区间运算**。位置标度 `Q = 2^47`、概率质量 `MASS = 2^16`、**16 个上下文行** | `index.hpp:583` 起 |
| 累计表 | `using Table = std::vector<std::array<std::uint32_t, 258>>`（258 = 256 字节 + 2 个哨兵） | 同上 |
| 行选择 | `Unigram` → 第 0 行；`Position16` → `min(15, pos)`；`Context16` → `((pos & 3) << 2) | (previous & 3)`，即 **4 个位置段 × 4 个前驱字节桶 = 16 行** | `Model::row()` |
| 训练 | `Model::train(first, last, prefix, kind)`，由区域构建调用：`model_.train(sorted, prefix_.size(), config_.model_kind)` | `index.hpp:1248` |
| 预测 | `Model::predict<Hash>(s, groups, route, fp)` → 返回 `{group, …}`，把区间映射到**逻辑组号** | `canonical_group` |
| 映射入口 | `Region::canonical_group(s)` = `model_.predict<false>(s, groups_, config_.canonical, dummy).group` | `index.hpp:959` |

**三点必须一起说清：**
1. **它是训练出来的，不是空接口**：`bulk_load` 对**每个区域**的**已排序键**、**去掉该区域公共前缀之后的后缀**做统计，生成累计表。输入是真实数据，不是常量表。
2. **它只输出逻辑组号**，不输出物理地址。物理地址由组几何（`sg_`／`bb_`／`off_`）与子块枚举决定。
3. **它与模型负责人要交付的"差异化后缀模型"不是同一个东西**。本索引从未集成后者（任务书 §13 列为尚待实施）。**因此本项目所有数字都是"参考模型下"的条件结果，换模型必须重测**——尤其 E28–E32 那条空间线，它的结论建立在"预测质量决定的组内字节分布"之上。

## 2. 从完整键到子块：一次真实运行的轨迹

**证据来源**：`diag_trace`（本轮新增的只读诊断，`-DE25_DIAG` 无关、不计时），冻结配置，真实数据集，键均匀取样。日志 `logs/diag_trace_{mixed,tranco}.log`。

**百万域名：**

**读法**：完整键 → `locate(key)` 选区域 → 减去该区域公共前缀得到后缀 → `canonical_group(后缀)` 得逻辑组号 → 组内的子块按 `put_primary` 的枚举规则确定 → 落在子块的槽位或该组溢出容器。**同一个键在查询路径上算出的组号，与放置路径用的是同一个函数**（`canonical_group`），这正是下面 I1 要验的东西。

**I1（同一键的查询组号 = 放置组号，且在范围内）**：每个数据集抽 **512 个键**逐条检查——组号在范围内、且查询路径返回的**值等于 `bulk_load` 放进去的值**。**两份日志都是 `i1_result: pass`**。

## 3. 方案 §1.2 的八问，逐条回答

| # | 问题 | 答案 | 依据 |
|---|---|---|---|
| 1 | 外层区域如何选取？ | `Index::locate(key)` 用外层路由（`Route::Full` 默认；A/B 两种替换方案只在实验开关里，不默认）选出区域下标 | `index.hpp:2810`；E6 |
| 2 | 公共前缀何时计算，模型输入是完整键还是后缀？ | 构建时 `compute_prefix(该区域已排序键)` 一次算好；**模型吃的是后缀**（`key.substr(prefix_.size())`），它的统计与预测都在后缀上 | `index.hpp:1242`、`:1248`、`Region::canonical_group` |
| 3 | 训练代码来自哪里、是否改写过、实际启用哪个？ | 项目自研的表驱动条件模型（非 LITS 官方实现、非第三方）；`Context16`；`bulk_load` 时按区域训练 | §1 的表 |
| 4 | 返回的是近似排名、坐标、物理位置还是逻辑组号？ | **逻辑组号**（区域内下标）。近似排名／坐标只在模型内部作为中间量 | `predict` 的返回结构 |
| 5 | 逻辑组数如何确定？截断、早停、取整、限幅如何处理？ | `derive_groups(n, suffix_bytes, cfg)` = `max(按键数估的组数, 按后缀字节估的组数) + 1`，可被 `fixed_groups` 覆盖；模型内部按 `Q = 2^47` 定点、`MASS = 2^16` 量化，最后映射并**限幅**到 `[0, groups)`；`canonical_group` 里 `groups_` 作为上界传入 | `index.hpp:1007–1017`、`Model::predict` |
| 6 | 构建、点查、插入、删除、扫描用的映射是否一致？ | **构建、点查、插入、删除都用 `canonical_group`**；扫描不用模型——它靠子块 M1 序（每个子块内按键排序、子块间有序）与边界目录推进 | `canonical_group` 的调用点；E9/E11 |
| 7 | 什么时候重训或改变组数？哪些记录必须重放？ | `rebuild(region, data)`／`rebuild_all()` 会重建区域（含重训）；`compact()` 只重排组内物理布局、**不重训、不改组数**；分裂／容量重规划会改变组几何。需要重放的记录：被重建区域的全体活跃记录 + 溢出记录 | `INDEX` 的 rebuild／compact／split 路径；E20 §生命周期 |
| 8 | 扫描是否依赖"组号随字典序不下降"？这个性质从何而来？ | **不依赖组号序**。扫描走的是 `Region::scan` 的**子块序 + 组内槽序 + 溢出归并**，靠的是不变量 **M1**（同一组内子块按键序排列，子块 i 的每个键都小于子块 i+1 的每个键）与边界目录，而不是模型输出的单调性。**代价**：模型不需要保序，但维护（子块边界变化）会立刻让 `Located` 失效 | `index.hpp:1054–1073`（M1 注释）、E11 边界目录、E31 §1 |

**结论（对方案 §1.3 的回应）**：模型与映射都是**表驱动、按区域训练、输出逻辑组号**，且**扫描不依赖模型保序**——这意味着"换模型"的接口面比方案担心的要小：只需 `predict` 在给定 `groups_` 下返回合法组号，扫描、子块序、边界目录都不受影响；**受影响的只有组内字节分布与溢出分布**（也就是 E28–E32 那条线）。

## 4. 边界与未决

1. **本文件只描述冻结版本**（五个开关默认全开 + R1）。其它开关的配置差异见 `switches.hpp` 的四张表与各轮报告。
2. **不声称本模型与 LITS 或任何论文模型等价**。它是同一族（条件概率 + 区间运算 + 早停思想）的**参考实现**，这一点在任务书 §1.3 里被明确允许（"可以先使用参考模型开发和隔离测试布局"）。
3. **没有测量预测质量**：本项目从未报告误预测分布或组间不均衡度。E8 做"按组需求重分配容量"（溢出降 21.9%–62.1%）本身说明各组需求不均，但**不均里有多少该算模型的账、多少算布局的账，没有拆开**。
4. **"接入差异化后缀模型"未做**，接口契约（方案 §8.1 的 `MappingContract` / `PredictorAdapter`）尚未起草。若要接入，受影响的至少包括：组数（`derive_groups`）、区域前缀、`canonical_group` 的返回域，以及**所有已发布数字的条件前提**。
5. **`group_of()` 是本轮新加的只读访问器**（`index.hpp`，紧邻 `slot_table`／`boundary_dir` 等既有只读暴露），加它是为了让诊断**检查**映射而不是"读代码推断"。它是加法，不改变任何既有行为。
