## 0. 为什么有这一轮

G0 账本（`PRIOR_WORK_AUDIT.md`）里有四项原任务要求属于**"有实现、无验收"**：

| 项 | 原任务出处 | G0 的判定 |
|---|---|---|
| I11 只改值不改变键布局与空间计数 | 结构审查 §3 | 现有门只比**内容**（`check_lits_index`）或比**两个配置**（`check_freeze`），**没有**同一个索引在纯值更新前后的前后比较 |
| I12 扫描 `n = 0` | 结构审查 §3 | 三个扫描门的 count 集都是 `{1,2,16}`，`n = 0` **从未被测**，只有代码可读 |
| I1 缺席新键"查询组 == 放置组" | 结构审查 §3 | `check_scan_contract` 对**已在索引里**的键断言过；缺席键没有，而两条路径**不是同一个调用** |
| I10 维护失败不丢记录、计数不半更新 | 结构审查 §3；§6.3 | 无失败注入设施，`置信度 low` |

这一轮把四项补上。新程序是**派生**的：只加目标，不改任何已有程序，所以每一条既有构建记录都保留自己的身份。

## 1. A —— I11：纯值更新不动布局（`A_value_update_layout`）

**做法**：按发布配置建库；取 4,096 个活跃键，把值改成新值；**前后各取一次完整快照**并逐项比较：

```text
size, region_count, memory(), overflow_count(), compaction_count(),
memory_breakdown() 的 7 个分量,
每个区域的 prefix_length / offset_table / slot_table / block_table,
每个区域逐组的 (primary_entries + overflow_entries + primary_bytes
                   + overflow_bytes + free_bytes + garbage_bytes)
```

**结果**：

| 数据 | 键 | 更新数 | 区域 | 组 | 布局未变 |
|---|---:|---:|---:|---:|---|
| mixed | 131,072 | 4,096 | 64 | 21,251 | **是** |
| skew | 131,072 | 4,096 | 64 | 20,163 | **是** |
| tranco | 262,144 | 4,096 | 128 | 21,888 | **是** |

**非空性**：每个被更新的键都被重新查回、值与参考表一致（否则抛异常）——"快照没变"只有在**确实变了东西**的时候才有意义。

## 2. B —— I12：`n = 0` 与 `n > size`（`B_scan_zero_and_over`）

**起点集**：首键、末键、中间键、`首键+"\x01"`、`末键+"\x01"`（尾后）、空起点、以及 8 个缺席键 —— 共 14 个。

| `n > size`（`size+1` 到 `size+64`） | 结果**逐条等于**参考有序表 `lower_bound(start)` 到末尾的截断 |

三数据集、14 起点全部通过（`zero_scans = 14`、`oversized_scans = 14`）。

## 3. C —— I1：缺席新键的"查询组 == 放置组"（`C_absent_key_group`）

**这一条要防的具体错误**：两条路径**不是同一个调用**——

```text
Region::canonical_group(...)  ->  model_.predict<false>(suffix, groups_, config_.canonical, ...)
Region::predict_for(...)      ->  model_.predict<Hash>(suffix, groups_, mode.route, ...)
```

不同函数、不同模板实参、**不同 route**。而发布配置里放置走 `Config::canonical`（默认 `Route::Full`）、查询走 `query_mode`（`Route::Interval`）——**两条 route 本来就不同**。若二者对某个键给出不同组号，查询就会找错组，而其余门全绿。

**做法**：对每个缺席键，先问查询路径"这个键属于哪个组"（`Index::diag_where`），再把它插进去，然后**数哪个组的记录数 +1**，要求那个组就是查询路径说的组。

**两种探针形状，故意各占一半**（这一点是修出来的）：

- **同长度**（把一个活跃键的最后一个字符换成另一个）→ 落在键序**内部**，可能进主块；
- **加长**（追加后缀）→ 排在组尾，几乎必然进溢出。

**只测第一种会让这一节无声地变成"只测溢出路径"**——初版就是这样：`placed_into_overflow` ≈ 99.6%，主块路径一次没走到。现在门**断言两种形状都被用到**，退化会直接失败。

| 数据 | 查询 route | 探针 | 观测到 | 主块 | 溢出 | 跳过（重建后） |
|---|---|---:|---:|---:|---:|---:|
| mixed | Interval | 1,024 | 1,024 | 5 | 1,019 | 0 |
| mixed | Full | 1,024 | 1,024 | 6 | 1,018 | 0 |
| skew | Interval | 1,024 | 1,024 | 25 | 999 | 0 |
| skew | Full | 1,024 | 1,024 | 25 | 999 | 0 |
| tranco | Interval | 1,024 | 1,024 | 32 | 992 | 0 |
| tranco | Full | 1,024 | 1,024 | 37 | 987 | 0 |

**6,144 个缺席键，两条 route，零处不符。** 插入若重建了区域就**跳过并计数**（区域重编号后观测无意义），跳过的那些仍逐条核对内容——它们不是组号一致的证据，但也不是未验证。

## 4. D —— I10：维护失败原子性（负结果，但是一个精确的负结果）

> **2026-09-23 更新（G0–G5 审阅 P0-3 之后）。** 审阅要求把「提交阶段不原子」从**测得的现象**
> 推进到**可核查的机制**，并问：提交段能否因**真实的**分配、复制或目录构造而中断。
> **已逐行审计并交付 `I10_COMMIT_PHASE_AUDIT.md`**，结论是：
> **提交路径上有两个真实抛点，其中一个发生在旧状态已被销毁之后**——
> `compact()` 末尾的 `rebuild_dir(g)`（`index.hpp:2054`）**会分配**（`dir.clear()` 之后构造 `std::string`
> 与 `push_back`），抛 `std::bad_alloc` 时**记录已全部重放、旧目录已销毁**，留下**残缺的边界目录**；
> 而 `locate_subblock` 对该目录做二分。**初版据此称后果是「静默错答」，这一条已被自己的门证伪**：
> `check_i10_commit` 在**两个注入位置**（含目录非空但残缺的那种）做全量点查扫描，**误路由 0 处**。
> **可复现的后果仍是本文测到的那个**：丢记录且 `size` 失真。详见审计文档顶部。
> 第二个抛点是重放循环内的显式 `throw std::logic_error`（`:2051`）。
> **重放循环本身经逐项核对是无分配的**（`insert_into` 只做 memmove，且 `suppress_dir_rebuild`
> 使它在重放期间不重建目录）——**破坏原子性的不是重放，是重放之后的目录重建**。
> **修法（任务书 §6.3）已作为独立一轮实施并验收**——见 **`RESULTS_I10_COMMIT.md`**：
> 提交段现在只由无分配的写与一次 `noexcept` 的 `swap` 构成，**不再含有可失败操作**；
> 开关 `compact_plan_commit` **默认 false**（本节 D 部分的负结果仍由 `=0` 那一臂给出）。
> **本节 D 的负结果保留为原始证据，它没有被推翻，也不该被删**——但它的范围要标清楚：
> 它证明的是「**人为在已经不含可抛操作的提交段里强制中断，仍会破坏状态**」，**不是普通同步异常下的可达路径**。
> 修复做的是**把可失败操作从提交段移走**，**不是给重放加回滚**；**结论不外推到「抗任意中断」**。

### 4.1 装置

`index.hpp` 里加了**诊断专用**注入钩子（`-DE25_DIAG` 才编译，不新增 Config 开关，四张开关表不动）：

```text
Region::inject_at / inject_point / inject_seen / injected
point 0 -- PREPARE：收集阶段已读完所有活跃记录、缓冲已分配，但**一个字节都还没动**
point 1 -- COMMIT ：原地重放进行到一半（块已清空并重置，一半记录已放回）
```

**工作负载是替换序列（erase + insert），不是纯插入**：初版用纯插入，131,072 次追加**一次压缩都没触发**——加长的键排在组尾、直接进溢出，根本走不到 `compact()`。替换序列才是到达压缩路径的那条负载（前几轮为同一个原因都用的它）。

### 4.2 PREPARE 点：**原子**

| 数据 | 触发注入的操作序号 | 注入触发 | 索引逐字节不变 | 记录数 |
|---|---:|---|---|---:|
| mixed | 4,203 | 是 | **是** | 131,071 |
| skew | 373 | 是 | **是** | 131,071 |
| tranco | 187 | 是 | **是** | 262,143 |

**断言**：失败后索引的完整快照与操作前**逐项相同**，全量扫描与参考表逐条一致，那个键仍然不存在。

**这是"准备—验证—提交"里"准备失败保留旧状态"这一半**——在没有临时缓冲的原地设计里，它成立，因为收集阶段只动自己的临时量。

### 4.3 COMMIT 点：**不原子，且尺寸计数也跟着错**

| 数据 | 触发序号 | 注入触发 | 记录数（before） | `size` 之后 | 参考表 | 仍可查到 | **丢失** |
|---|---:|---|---:|---:|---:|---:|---:|
| mixed | 4,203 | 是 | 131,071 | 131,071 | 131,071 | 131,047 | **24** |
| skew | 373 | 是 | 131,071 | 131,071 | 131,071 | 130,898 | **173** |
| tranco | 187 | 是 | 262,143 | 262,143 | 262,143 | 262,109 | **34** |

**读数**：

1. **提交失败会丢记录。** 块已被清空、只重放了一半，没有回滚路径——这正是任务书 §6.3 的"准备—验证—提交"要避免的。
2. **`size_` 同时失真。** 它仍报 131,071，而实际只有 131,047 条查得到——**尺寸计数也是半更新的**。
3. **所以 I10 的"维护失败不丢记录、计数不半更新"在当前设计下不成立**，成立的是更弱的一条：**失败不可达**。`compact()` 提交前有 `repack_budget_fits` 的必要条件检查，`put_primary` 失败时还有 `throw std::logic_error("compaction lost capacity")` 兜底——**原子性完全建立在这个前置条件成立之上，而没有验证与回滚**。

**这一条按负结果登记，并作为 G2 的输入**：要么实现 §6.3 的临时缓冲版本并与原地版对照，要么把"必须持有前置条件"写成显式契约并让调用方在 `logic_error` 后重建——**两者都不做，就不能宣称维护是失败安全的**。

### 4.4 顺带抓到并修掉的一处：`++compactions` 的位置

注入一开，PREPARE 点就把索引"变了"——查下去发现**不是布局变了，是计数器**：

```text
void compact(g) {
    E30_INC(compact_calls);
    ++compactions;          // <-- 原来在这里：还没做任何事就记了一笔
    ...
```

一次**失败**的压缩被记成了一次压缩。这正是 I10 说的"计数不半更新"。已**移到提交成功之后**：

```text
    suppress_dir_rebuild = false;
    rebuild_dir(g);
    ++compactions;          // 完成了才算
```

**E25/E30 的计数器没有跟着移**：它们量的是**已经真做过的工作**（收集阶段确实读完了每条活跃记录），失败时把这份工作记下来是对的。两者的区别写在源码注释里。

## 5. 回归核查：改动有没有影响正常路径

`index.hpp` 被改了两处（计数器位置、诊断钩子），所以**每一个门的身份都重新建立**，并逐字段比对：

| 结果 | 个数 | 说明 |
|---|---:|---|
| **逐字段相同** | 34 | 22 个门 × 各数据集，含三个读压缩计数的门（`check_e9_multiblock` 的 `compactions = 79`、`check_e26_c2`、`check_c3`） |
| 不同 | 3 | 只有 `check_g1_contract_*`——它多了 D 部分 |
| 无改动前对照 | 4 门 | `check_freeze` / `check_overflow_store` / `check_tag_store` / `check_scan_contract` |

四个没有对照的门里，`check_overflow_store`（7 字段）与 `check_scan_contract`（10 字段）三数据集**逐字段相同**；`check_freeze` 的差异全部来自**对照日志是 E32 时期的**（`cfg_shipped` 串少了 E34–E38 加的四个字段、内存差来自那一段跨度），而它输出的**压缩计数一致**；`check_tag_store` 本来就没有留存运行日志（G0 已登记）。

**其中 `check_e16_probe`、`check_e19_reuse`、`check_e20_r2` 重建后的可执行哈希与改动前完全相同**——那几个目标根本不实例化 `compact()`。

**结论**：两处改动在正常路径上**没有移动任何可观测量**。

## 7. 边界

- **这一轮只加验收，不改任何算法或开关默认值。** 两处 `index.hpp` 改动：一处是把计数记在正确的时刻，一处是诊断专用的注入钩子（`-DE25_DIAG` 之外完全编译掉、不新增 Config 开关、四张开关表未动）。
- **D 部分的提交失败是人工注入的**，而且注入点选在"半个组已重放"处。**真实运行里这个点不可达**——`repack_budget_fits` 是提交前的必要条件检查，`put_primary` 失败还有兜底抛错。**但这不等于安全**：它意味着原子性没有实现，只有"前置条件必须成立"这一条假设。
- **C 部分只覆盖缺席键**；已在索引里的键由 `check_scan_contract` Part 1a 覆盖（全量逐键）。
- **A 部分只测纯值更新**，不覆盖"更新触发重建"的路径（那条由 `check_lits_index` 的前缀重建/分裂计数覆盖）。
- **`n = 0` 现在有断言了，但只在三数据集 × 14 起点上**；没有穷举所有起点族。
- **没有做交错混合负载**（§10.3 的完整成本检验仍未做，属 G2）。
