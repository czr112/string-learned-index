# P2 / A4 进入诊断：扫描的计数花在哪里，以及它是否随结果增长

日期：2026-09-23。目录：`validation_e25_20260918`。
装置：**`diag_scan_nav.cpp`**（**独立诊断构建**，`-DE25_DIAG`；**不进入任何正式计时程序**）。
原始记录：`results/main/scan_nav_{mixed,skew,tranco}.jsonl`（每条记录 ＝ 一次扫描）。

**本轮只诊断，不实现游标。** 总计划 §5 A4 明确：「**仅在有诊断确认重建成本后实施**」。

---

## 0. 判定先说

**A4 的进入条件不成立——记录负结果，按计划关闭该条件分支，转向下一项。**

计划怀疑的三处「重复工作」，实测只有一处存在、且那不是可避免的重建：

| 计划怀疑 | 实测 | 判定 |
|---|---|---|
| **每区域重新求 `canonical_group(start)`** | **≈ 1.0 次／扫描**，**与区域数无关** | **不存在。** 它只在**第一个区域**求一次 |
| **跨区域重复 `locate(start)`** | **恰好 2.0 次／扫描**，不随结果增长 | **存在但已经是常数**——不是 R+1，见 §4 |
| **每组重建游标** | 0.039–0.147 次／返回记录，**与访问的组数成正比** | **是「每条结果必需的工作」，不是可避免的设置** |

**随结果增长的只有三样：组游标启动、归并比较、结果分配。三者都是结果强制的。**
而**每次扫描的固定设置（`locate`／`canonical_group`／`regions`）在 n=1024 时合计每返回记录 < 0.005**——
**随 n 增大而消失。**

## 2. 绝对口径：每次扫描的固定设置

| 量 | mixed | skew | tranco | 说明 |
|---|---:|---:|---:|---|
| `locates` ÷ 扫描数（n=16） | **2.00** | **2.00** | **2.00** | 每次扫描**恰好两次** |
| `canonical_group` ÷ 扫描数（n=16） | 1.00 | 1.00 | 1.00 | **每次扫描一次** |
| `regions` ÷ 扫描数（n=16） | 1.00 | 1.00 | 1.00 | 进入一个区域 |
| `locates` ÷ 扫描数（n=1024） | 2.37 | 2.37 | 2.25 | 略升（200% 状态进入更多区域） |
| `canonical_group` ÷ 扫描数（n=1024） | 1.01 | 1.00 | 1.05 | **仍是一次** |
| `regions` ÷ 扫描数（n=1024） | 1.37 | 1.37 | 1.25 | 偶尔跨区域 |

**读法**：无论 n 从 16 涨到 1024（**64 倍**），`canonical_group` **始终 ≈ 1 次**，
`locate` 从 2.00 到 2.37。**这两个量是「每次调用的设置」，不是「每个区域的重复」。**

**`dir_rebuilds` 在扫描期恒为 0——由构造保证**：`Index::scan`／`Region::scan` 都是 `const`，
边界目录只在变更路径上重建。**这一条没有计入表里，因为它是类型层面的而非测出来的。**

## 4. 一条必须记下的计划修正

计划 §P2a 写「**跨区域重复 `locate(start)`**」。**实测是恰好 2 次，不是 R+1（R 为区域数）。**

原因：`Index::scan` 的循环条件是 `i < nodes_.size() && out.size() < count`——
**一旦收集够 `count` 条就退出**，而 512 次抽样起点里绝大多数**在第一个区域内就收够了**。
所以「R+1 次外层搜索」这个上界在本轮的状态与长度下**从未接近**（R 是 64 或 128）。

**E32 的 S2 候选（起点缓存）因此也失去了对象**：它要把 R+1 降到 1，
而这里本来就是 2（且其中一次是循环体里的重悬）。**这两次都不是「可避免的重建」。**

**一条必须随本节一起读的限制**：**多数扫描在第一个区域就结束了**（因为收集够 `count` 条就退出），**所以这份数据不能排除「专门跨多区域的负载」有不同表现**（例如 `n` 远大于单区域容量、或起点均落在区域尾部）。**本节的结论限定为本轮样本负载。**

## 5. 计数不能换算成时间

**本报告不估计任何加速比。** 计数只能定位候选，而下面的换算会误导：

- 一次**归并比较**是几个字节的比较；一次**结果分配**是一次 `std::string` 构造 ＋ 一次 `emplace_back`。
  **两者的单位成本相差很大**，所以「`merge_cmps` 是 0.14–0.58 × 结果分配数」**不能读成「归并占 14%–58% 的时间」**——
  **实际时间占比必然小得多**。
- 同理，`cursor_starts` 每记录 0.04–0.15 次**不说明它占多少时间**。

**要得到时间结论，只能做同轮计时**——而本轮按停止条件不需要做。

## 6. 停止条件与处置

计划 §5 P2a 的停止条件：

> 「若『每区域重建游标』的成本与返回记录数成正比且占比很小，**按条件未满足关闭** A4；
> 若确有可避免的重建，进入 P2b。」

**实测**：
- 「每区域重建游标」**不存在**（`canonical_group` ≈ 1 次／扫描，与区域数无关）；
- 与返回记录数成正比的三项（游标启动／归并比较／结果分配）**都是结果强制的**，
  其中**结果分配恰好 1 条／记录，已经是 S1 之后的下限**。

**处置：按条件未满足关闭 A4。记录本诊断作为负结果，转向计划 §6 的下一项。**

**边界**：
1. 本诊断**只覆盖长期替换到 200%**这一种状态与 16／128／1024 三个长度；**纯插入、短期替换、以及 n > 1024 未测**。
2. **`region_all()`（全量扫描）走的是同一条 `Region::scan`，但起点为空、长度不限**，
   本轮的起点集合不覆盖它的形状——**它的计数可能不同**。
3. **计数是确定性的，不套时间统计的措辞**（无噪声底、无 5/5）；本报告也没有做任何计时。
4. **三语料比对 5,386,538 条，0 处不符。** **返回 0 条的扫描每语料 6 次**——全部来自「排在末键之后」那个起点，出现在 **initial 与 pct25 两个状态 × 三个长度**（pct200 下新键已排到它之后，不再为 0）。**单列，未做除法。**

**本轮修掉的一处自己的装置缺陷**：诊断程序第一版把起始键**原样**写进 JSON，而其中一个探针**故意含 0x01 控制字节**——于是 `scan_nav_*.jsonl` **不是合法 JSON，下游无法解析**。已按 JSON 规则转义（控制字节写成 `\u00XX`），重跑后 **13,905 条记录全部可解析**，且**计数与本轮结论逐格不变**（`scans_checked` 三语料仍为 1,794,488／1,794,488／1,797,562）。
