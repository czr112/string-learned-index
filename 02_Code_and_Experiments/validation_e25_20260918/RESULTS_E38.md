## 1. 结论摘要

**四条验收结论**（全部 PASS）：

| 验收面 | 结果 |
|---|---|
| **与参考版逐条比较最终组号** | **518,144 条实时键 ＋ 518,144 条缺席键，零处不符**；256 个真实区域中 **253 个可校准**（3 个被系数上界拒收，见下）；局部系数与源码**逐比特相同**（343 次比对） |
| **组号保序**（扫描的前提） | **零违例 / 518,144 键**。**本轮对实际区域与查询集另行验证**；原实现自己也在**逐键分发循环**里检查（`lits_node.hpp:416`：`idx < lastIdx || idx < 0 || idx >= item_array_length`），本文早先写成“原实现只查首末键”**是错的、已撤回**。**两者都不能替代 P2 的完整扫描验收** |
| **指纹兼容** | 两条路径（M0 融合、LITS 独立）在 524,288 键上**都与存储标签一致**；负对照在 **99.56%** 的键上不同 → 这个门确实抓得住它要防的错误 |
| **边界与内存安全** | 边界区 37 个 / 2,370 条键，覆盖 `p = 0/1/31/32/33/121/123`；**空区域、单键、`G = 1` 用构造输入覆盖**；**七条拒绝路径**全部触发；**ASan/UBSan 八次运行无报告** |

**四条会带进 P2 的模型侧实测**（不是失败，是发现）：

1. **系数上界不是“有限性”，而且它真的会拒区域**。`getPos` 内部就做 `static_cast<int>(c)`，外面再 `clamp` **修不了它**——所以守卫必须保证 `c` 本身有界。本轮把原来的 `isfinite` 换成真正的**量值上界**（`|G·α|·(最长键＋1) ＋ |G·β| ≤ 1e9`）后，**mixed 有 3 个真实区域被拒**（region 50：prefix 89／G 268；region 57：prefix 58／G 388；另一个同类）。它们的 CDF 跨度小于 ~4×10⁻⁵，**被一条保守的数值准入界拒收**。**“跨度小”不等于“模型分辨不出键”**——局部线性校准本来就在放大小跨度，真正该看的是**校准后的组号分布、碰撞与数值稳定性**，而本轮**没有对这 3 个区域做过那一测量**。**旧守卫放过了它们**，因为 `isfinite` 对 `1e300` 也是通过。见 §3.4。
2. **这 3 个区域的回退方式要按任务书 §3.4 定**：规定的回退是**该区域改用 Context16**，并把实验标成 `LITS-HPT + Context16 fallback`、**报告回退区域数与记录／查询比例**——**不是**让它们落到组 0。**这是 P2 要实现的，本轮只报数。**
3. **映射质量是两面的**：LITS **每个数据集都用到了更多的组**（Context16 的 1.56×／1.70×／2.01×），但**最坏的那个组更挤**（mixed 88.1% 对 66.7%、skew 68.1% 对 40.2%、tranco 33.4% 对 33.5%）——**数据集相关，tranco 上是平局**。**非空组数量增加不等于分配更均衡。** 见 §3.5。
4. **我为此提的机制假设被证伪**：我原以为原因是 `getPos` 的 `ps >= 1` 提前停止使整个区域一次也不进循环。实测 `regions_ps_lt1 = 0`——**三个语料上一个这样的区域都没有**。**所以挤拤的原因本轮未确认，报告不宣称成因。**

**一处必须随数字读的边界****一处必须随数字读的边界**：本轮所有"一致"都是**在受限域内**的。字节 ≥ 128 与嵌入 NUL 一律**拒绝**，不是处理（§5.3）。这不是缺陷而是任务书的域限定，但它意味着**"适配器正确"这句话的适用范围就是那三个语料**。

### 2.2 补丁（两个 hunk，一条理由）

`patches/lits_model_safety.patch`：

```diff
-            const auto &uni = m[i & PS_MASK][key[i - 1] & FC_MASK][key[i]];      (getPos)
+            const auto &uni = m[i & PS_MASK][i == 0 ? 0 : (key[i - 1] & FC_MASK)][key[i]];

-            const auto &uni = m[i & PS_MASK][key[i - 1] & FC_MASK][key[i]];      (getCdf)
+            const auto &uni = m[i & PS_MASK][i == 0 ? 0 : (key[i - 1] & FC_MASK)][key[i]];
```

**理由**：两个循环都从 `i = gcpl` 起步读 `key[i - 1]`。`gcpl == 0` 时首次迭代读 `key[-1]`——键之前的一个字节，调用方无法使之合法。修法用的是训练路径**本来就在用**的同一个哨兵（`lits_model.hpp:119` 的 `int _fc = b == 0 ? 0 : ...`），所以训练与预测对"首字节的前文是什么"取得一致。

**为什么只有这两个 hunk**：任务书 P1 第 1 步要求**最小**安全修复，且**禁止在同一步里改 HPT 的内存布局**。表形状、`UNI`、掩码宽度、权重数组、提前停止条件一律未动。`getPos_woGCPL` **故意不打**——它显式处理 `key[0]` 后从 `i = 1` 循环，`key[i-1]` 永远是 `key[0]`，够不到 `key[-1]`。

### 2.3 哈希核对：这是 E4 验证过的同一个修复

```
pristine  d5ac9b88f796c476259ac89bd9d52a81199e51a0567dc0e304e9af733529fd73
patched   b5a1c28251da7e74fd011e6b14a40927481c65ed24c837cc4892f26740af4c18  == E4 记录的补丁版
```

**打补丁后的文件与 E4 记录里那个哈希逐字节相同**——所以这不是"看起来一样"的改写，是同一个修复。`patch_lits_safety.py` 在源不是原始哈希、或结果不是 `b5a1c282…` 时都会 `ABORT`。

### 2.4 留在源码里、本轮不修的缺陷

`lits_model.hpp:170` 用**裸 `char`** 做表下标，而训练路径 `:120` 用 `unsigned char`。在带符号 `char` 的目标上，字节 ≥ 128 是**负下标**。这是**固定源码里的真实缺陷**（不是假设），但修它属于**改行为**而不是为本次输入域做边界修复——所以**适配器改为拒绝**（§5.3），让这个缺陷**够不到**，而不是悄悄抹平。

### 2.5 依赖子集（`vendor/lits_model_safe/`）

补丁版 `lits_model.hpp` ＋ **逐字复制**的 `lits_base.hpp`／`lits_gpkl.hpp`（哈希与留档相同，所以"未改动"是可核对的数字）。**`lits_node.hpp` 故意不复制**——它 include 了 HOT、cnode、iter、PMSS，任务书 §7 明确禁止为了接模型把这些带进来。它留在留档里，作参考。

## 3. P1.2 适配器与参考版逐条对照

### 3.1 键坐标：从源码读出的确切约定

任务书 §3.1 说"输入应该是 `full_key + prefix_length`"。**源码证实这就是原实现自己的用法，不是我们新造的适配**：

| 源码位置 | 传的是什么 |
|---|---|
| `lits_node.hpp:347` | `gcpl = ucpl(kvs[l].k, kvs[r-1].k)` —— 节点自己管辖范围的公共前缀 |
| `lits_node.hpp:365-366` | `getCdf(kvs[l].k, gcpl)` ／ `getCdf(kvs[r-1].k, gcpl)` —— **校准用的就是它** |
| `lits_node.hpp:292` | `getPos(key, item_array_len - 2, ccpl + icpl, K, B)` —— 预测传的也是它（`:302` 的 `ccpl += icpl` 之后两者相等） |

**本项目里扮演 `gcpl` 这个角色的正是区域前缀长度 `p`**（`lits_node.hpp:379` 把节点自己的部分键前缀存下来，对应我们的 `prefix_`）。所以适配器传**完整键 ＋ `p`**。

**四种接法逐个核过**（本文档早先写的"suffix 会读 `suffix[-1]`"**撤回**，机制说错了）：

| 传入 `key` | 传入 `gcpl` | `i = p` 时读 | 后果 |
|---|---|---|---|
| **完整键** | **`p`** | `full_key[p-1]` 与 `full_key[p]` | ✅ 合法，正是本意 |
| 后缀 | `p` | `suffix[p-1]` 与 `suffix[p]` | ❌ **重复跳过 p 个字节**，相位与前文都错；后缀短于 p 时越界 |
| 后缀 | 0 | `suffix[-1]`（补丁前） | ❌ 补丁前越界；补丁后不越界但相位归零 |
| 完整键 | 0 | `full_key[-1]`（补丁前） | ❌ 同上 |

### 3.2 哨兵偏移：`size = G` 是怎么来的

源码在 `lits_node.hpp:292-305`：

```cpp
pos = model->getPos(key, node->get_item_array_len() - 2, ccpl + icpl, K, B) + 1;
return std::max<int>(std::min<int>(pos, node->get_item_array_len() - 2), 1);
```

我们的组数组长度是 `G`、**没有两个哨兵槽**。代入 `item_array_len = G + 2`，上式化为 `max(min(getPos(key, G, p, K, B) + 1, G), 1) - 1`，即 **`clamp(getPos(key, G, p, α, β), 0, G-1)`**——就是适配器写的那一行。`check_lits_model` 把这个等式**逐键断言**，而不是相信这段文字。

### 3.3 接口为什么是 `const std::string&`

固定源码的 `str = char *`，且循环条件是 `key[i]`——**依赖 NUL 终止**。`std::string_view` 不保证视图后方有终止符。要在"不假设终止符"和"不把算法抄第二遍"之间同时成立，只有让**类型**来保证：`std::string::data()` 由标准保证 NUL 终止（C++17 的非 const 重载还直接给 `char *`）。**零分配**，因为调用方本来就持有 `std::string`。

**没有重写循环**——位置与 CDF 全部来自固定源码。E37 的教训（㊻）在这里是直接理由：同一件事写两遍必然漂移，而漂移恰好在门看着的地方看不见。

### 3.4 门的结果（`check_lits_model`）

**装置**：三语料按 `region_keys = 2048` 分块，每块的**真实** `Region` 对象给出 `prefix()` 与 `groups()`；一份共享 HPT 由全部键训练；每个区域按 `RegionModel::calibrate` 校准。

**参考版是手抄，不是第二份实现**：`lits_node.hpp:290-305` 的 `+1`、哨兵夹取、偏移减法逐行抄下来。

**而这个对照只在它的整数转换有定义的范围内成立**（任务书指出）：参考版调的是源码的 `getPos`，它以 `static_cast<int>(c)` 结尾；**不能拿原实现的未定义行为当标准答案**。本轮的对照之所以安全，是因为**准入界把被拒区域排除在外**，其余区域的 `|c|` 实测最坏只有 8.49e6，远在 int 范围内；适配器侧则由 `predict_group` 的 **double 域饱和** 保证。

|---|---:|---:|---:|

**这一行后来又改了一次，而且改的是它的定位**：**这个上界不再是安全机制。** 位置循环现在返回**浮点**，由 `predict_group` 先拒绝非有限值、**再在 double 域里饱和到 \([0, G-1]\)、最后才转换**；这样就算查询、缺席键或后续插入比建库时的最长键还长，也不会越界。**一个静态的、逐区域做一次的判定，不能是一个运行时量的唯一保护。**所以 `1e9` 现在登记为**额外的保守准入策略**：这 3 个区域仍被拒，因为 `|G·alpha|` 极大意味着映射数值上病态，拒收给它们一个**定义明确的 Context16 布局**，而不是一个任意布局。**它会改变 LITS 臂的覆盖范围**，这一点必须随数字报。

**原先那一行的说法继续成立**（它是修正 ② 逼出来的）： 上界按**区域自己的最长键**计算（不是全局 4096），实测最坏只有 **8.49e6**，离 1e9 两个数量级——**所以没有一个是擦边过的**。而被拒的 3 个区域即使按自己的键长算也超限，说明它们的系数是**真的太大**，不是守卫太紧。

**这 3 个区域长什么样**：prefix **89**／`G` **268**、prefix **58**／`G` **388**、以及同类的一个——**都在 mixed**。它们的 `alpha = 1/span` 大，等价于**该区域的 CDF 跨度小于 ~4×10⁻⁵**。

**一句必须改掉的措辞**（审阅指出）：本文档早先把它们写成“**模型在这些区域分辨不出键**”。**不成立**——局部线性校准本来就是靠放大小跨度工作的，`alpha = 1/span` 大正是它在做事。该看的是**校准后的组号分布、碰撞与数值稳定性**，而本轮对这 3 个区域**没有做过那一测量**。**正确的叫法是“被保守的数值边界拒收”**，不是“模型无法区分”。

**边界与拒绝**（与语料无关，每次运行都跑）：**37 个边界区 / 2,370 条键**，覆盖 `p = 0/1/31/32/33/121/123` × `G = 1/2/64/613`、短后缀（长 = `p+1`）、`a`／`aa`／`ab` 前缀关系、以及 120 字符公共前缀的**平台**（区分只发生在末尾）。**空区域、单键区域、`G = 1` 用构造输入覆盖**（§5.1）。**七条拒绝路径**全部触发：高位字节、嵌入 NUL、键数不足、键短于前缀、**键长超过上界**、退化校准、对不可用模型预测。

**训练公共前缀实测 29（skew）**——本文档早先估的 25 是错的；29 与 `diag_domain` 测出的区域前缀最小值 29 一致。

**一处被探、未被触发的分支**：上界守卫的“探针”（共享 120 字符前缀的两个键 ＋ `G = 613`）**被接受了**，所以 `CoefficientTooLarge` 这一条在本轮是由**真实区域**触发的（3 个），不是由构造用例。这比反过来好：它说明守卫不是摆设。

**两条读法：**

1. **LITS 每个数据集都用到了明显更多的组**——分别是 Context16 的 1.56×／1.70×／2.01×。
2. **但最坏组更挤，而且 mixed／skew 上明确**：均值与区域计数两个稳健量都指向同一方向。**skew 是最有意思的一格**：更松的区域有 38 个、更挤的只有 26 个，**但均值反而更高**——少数区域被压得极狠，把均值拉了上去。**百万域名是平局**。

**一条口径**：**非空组数量增加不等于分配更均衡。** 这张表的两半是分开的，不能只引用“用到的组更多”那一半。

**这是模型侧的半边。**“子块数量和溢出”那半边需要索引，属于 P3。

### 3.6 一个被证伪的假设（附上，因为它是测量的一部分）

mixed 上 `raw_below_1 = 12,755`（10.2%）与 `raw_at_or_above_G = 1,425` 这个**31:1 的不对称**让我提出过一个机制假设：`getPos` 的循环条件是 `ps >= 1`，而 `ps` 的初值是 `G × alpha`；若 `G·alpha < 1`，**循环一次都不执行**，整个区域一条键都不做区分。

**实测证伪**：`regions_ps_lt1 = 0`——**三个语料上都没有一个这样的区域**，而挤拤恰恰出现在 mixed 上。

**所以挤拤的成因本轮未确认，报告不宣称。** 那个不对称是**真的**，只是不是我以为的那个原因。`raw_below_1` 的名字也是按它**实际测的东西**起的——`raw < 1` **包含**区域首键落在 0 组这个合法位置，所以它本身不构成任何病态的证据。

## 4. P1.3 指纹兼容

**要证的事**：**标签是区域后缀的函数，与模型无关**；而适配器读的是完整键，**因此它对哈希的贡献必须是零**。

**为什么需要门**：查询路径是融合的——`Model::predict<Hash>` 把它读的每个字节喂进 `Fingerprint` 并返回 `consumed`，`find_impl` 再用 `fp.tail(s.substr(pred.consumed))` 收尾（`index.hpp:2655,2662`），结果恰好是 `insert_slow` 存下的 `Fingerprint::of(suffix)`（`index.hpp:3070`）。**一个"读了字节却把它们报成 consumed"的模型会悄悄改变查询标签，而存储标签原地不动**——于是每次候选都穿透标签过滤，索引**仍然正确、只是变慢**。这正是能穿过内容检查的那类故障。

**三条路径，524,288 键：**

| 路径 | 结果 |
|---|---|
| M0 融合路径（`predict<true>` ＋ `tail`） | 与存储标签**逐条一致** |
| **LITS 接线**（`fp_consumed = 0`，从后缀头开始哈希） | 与存储标签**逐条一致** |
| **负对照**：把模型的读取数当作指纹偏移 | **在 99.56%（522,002 / 524,288）的键上不同** |

**负对照是断言不是报告**：它必须在可测比例上不同，否则这个门就抓不住它存在的理由——那时门会报"失效"而不是报"通过"。

**顺带测到两个 M0 的既有事实**：`consumed` **从不为 0**（`consumed_zero = 0`），且**最大到 21**——比训练的 16 字节上限长，因为 `Route::Interval` 的停止条件（同一桶）不一定在 16 字节内满足。

**`fp_consumed` 的设计因此是被实测支持的**（任务书 §5.1 给的接口）：`result.steps` 保留"模型处理了多少"的原义，新字段单独表示"哈希状态吸收了多少连续后缀字节"，LITS 后端下为 0。**本轮没有改 `index.hpp`**，所以这条设计是**验收过的契约**，落到代码里是 P2 的事。

# P2：索引接线

日期：2026-09-22。**P2 已完成**：`index.hpp` 现在能按 `Config::model_backend` 选择参考模型或 LITS HPT，**M0 逐位未变**。

## 8. 接了什么

| 位置 | 改动 |
|---|---|
| `Config::model_backend` | 新增，默认 `Context16`。与 `ModelKind` **分开**：后者选的是参考模型自己的表行形状，把 LITS 折进去会让 `kind == Context16` 取决于另一个字段 |
| `Model::Prediction` | 新增 `fp_consumed`，与 `consumed` **分开**。`find_impl` 改用 `fp.tail(s.substr(pred.fp_consumed))` |
| `Region::canonical_group` | **只接完整键，内部自己推后缀**。先前的两参数版本**并不能保证坐标正确**——两个 `std::string_view` 同型，`canonical_group(suffix, full_key)` 一样编得过。**签名变化只能迫使旧调用点被改，坐标正确性靠实现与测试保证**。现在只剩一个参数，**这一类错误已经无法表达** |
| `Region::predict_for<Hash>` | 新增的融合入口：参考模型走原路（`fp_consumed == consumed`），LITS 走全键走法并报 `fp_consumed = 0` |
| `Index::lits_shared_` | `shared_ptr<const SharedModel>`，**全索引一份**。`ensure_lits_shared()` 一次性训练，`adopt_lits_shared()` 供统计回放共用 |
| `Region::demand_profile_impl` | 统计探针改用**同一张表**、**同一个后端判定**。同一个回退区域在计划里也回退 |
| `Region::calibrate_lits` | 校准；失败则**该区域整体回退 Context16**，并计数 |
| `switches.hpp` 四张表 | `model_backend` 全部登记；在白名单里作为**可以不同的开关**，而不是“必须相等”的字段 |

**一条设计决定值得单说**：适配器的预测入口从 `const std::string&` 改成了 **`std::string_view`**，因为索引的查询、写入、扫描起点全部持有视图，而固定源码的 `getPos` 只能接受 NUL 终止的 `char*`。所以**位置循环按长度重写了一遍**，而“它等于源码的 `getPos`”是**测出来的**：`check_lits_model` 拿两者跑同一批键（518,144 实时 ＋ 518,144 缺席），零处不符。校准仍调源码的 `getCdf`（它的键是 owning string）。

## 10. 三个真实缺口（已修）

**① 空索引会去训练 HPT，然后报错**。`ensure_lits_shared` 对 `pairs.size() < 2` 也调 `train()`，而固定源码的 `train` 读 `keys[1]`。任务书 §3.4 对少于两键的区域规定的是**定义好的边界路径**（组 0），**不是训练**。修法：不足两键就**不建表**，`calibrate_lits` 处理空实例并计入 `regions_boundary`。已由 `check_lits_index` 的空索引与单键索引用例验证。

**② `compactions` 这个计数器在库里从未被递增**。**本文早先把后果写反了**：它不是“永远不会失败”，**而是一定会失败**——`count > 0` 对一个永远为 0 的量永远不成立。**它确实失败了，而且那正是我发现它的方式**：`check_lits_index` 报的就是 `compaction never ran`。这与 E30 那次“白名单漏字段导致断言恒真”**方向相反**：那一次是**假通过**，这一次是**假报警**。两者都要修，但不是同一种错。

已改用真正在递增的 `compact_entered`，并确认**它在接受构建里真的执行**（不是被 `NDEBUG` 或分支未进入绕过的）：本轮三个语料上分别报 48,208／48,208／48,222。

**③ `erase_released_overflow` 是删除计数，我当成插入用了**；已分开，插入侧改用**容器活跃数的峰值**（在插入密集阶段采样，不在末尾——峰值之后会降回来）。

**另一条不改只记**：`Index::upsert` 的返回值与它旁边的注释**相反**（实现是“已存在时返回 false”，而 `upsert_one` 的注释说两者同一约定）。本轮**按实现写参考表**，因为冻结版本就是要保存的基线。
