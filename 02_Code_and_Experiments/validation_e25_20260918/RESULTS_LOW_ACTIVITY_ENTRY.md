# 低活跃子块回收：入口诊断（计数轮）

日期：2026-10-10。目录：`validation_e25_20260918`。
来源：`../docs/NEXT_ACTION_PLAN_20261009.md`「先补现有候选的一个证据缺口」与「下一项结构改动」。
**本文只做计数诊断，不产出任何耗时数字，也不宣称收益。**

---

## 0. 一句话结论

`reclaim_low_activity` 放开的那个分支**接通了一个真实存在的总体，但它够不到其中的绝大部分**：
块级字节拒绝里有 19%–85% 落在 0–1 条活跃记录的块上（mixed/skew 上其中 ≥99.9% 是**空块**，tranco 95%），
而候选在整个 200% 替换里只跑出 **183 / 27 / 88** 次 repack、促成 **182 / 26 / 68** 次放置。
它把溢出插入改写掉的比例是 **0.84%（mixed，E31 臂）／0.03%（skew）／0.15%（tranco）**。
判定见 §5：**不进入计时轮，按负结果收口。**

## 1. 为什么要有这一轮

`RESULTS_HOLES_ENTRY.md` 的登记条目里写着下一件该测的事：

> **`repack_subblock` 的 `if (n < 2) return;` 是一行条件，不是机制**。
> 它在晚期检查点上正是挡掉 53%–98% 拒绝的那一句。**验它只需改一行**。

代码已经改完（`Config::reclaim_low_activity`，默认 false，四张开关表全登记），
正确性门 `check_low_activity` 也已存在。**缺的是第 2 步**：在当前身份下跑入口诊断，
按同一失败目标块记录 n=0 / n=1 的**实际机会**、**回收字节**、**促成放置**与**最终溢出**，
并区分块级与插入级。

## 2. 这一轮对源码做了什么

`index.hpp` 只加计数与判读，不改行为：

| 计数器 | 语义 |
|---|---|
| `hole_count_eq0` / `hole_count_eq1` | 现有 `hole_count_lt2` 的**细分**（该值的语义与数值不变）：一次字节拒绝发生时，目标块持有 0 条 / 恰好 1 条活跃记录 |
| `low_activity_n0` / `low_activity_n1` | `reclaim_subblock` 的 n<2 分支按 n 分开计数（`low_activity_reclaimed` 不变） |
| `low_activity_bytes` | 该次 pass 真正释放的占用字节（pass 前 `bb_ - bottom` 减活跃后缀总长） |
| `low_activity_helped` | **紧随一次 n<2 pass 之后** `put_primary` 重试成功了多少次。在两个调用点就地判定 |
| `usage` 其余 | 复用既有计数器，未新增重复量 |

`low_activity_helped` 的读取包在 `#ifdef E25_DIAG` 里：计时构建中 `E25_INC` 展开为 `((void)0)`，
若不包住，那句 `header(...).count` 会留在发布路径上——**不是错，但没必要**。

## 4. 结果

### 4.1 200% 检查点：拒绝落在哪种块上，机制跑到什么程度

| 语料 | 臂 | 字节拒绝 | 其中 n<2 | n=0 | n=1 | n<2 pass | 释放字节 | 促成放置 | 溢出插入 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| mixed | E31 off | 1,146,701 | 977,279 | **976,676** | 603 | 0 | 0 | 0 | 41,251 |
| mixed | E31 **on** | 1,145,845 | 976,423 | 976,172 | 251 | **183** (n0=7) | 69,873 | **182** | **40,905** |
| skew | E31 off | 2,103,691 | 1,730,775 | **1,730,709** | 66 | 0 | 0 | 0 | 102,068 |
| skew | E31 **on** | 2,103,639 | 1,730,720 | 1,730,664 | 56 | **27** (n0=7) | 5,585 | **26** | **102,042** |
| tranco | E31 off | 501,535 | 96,825 | **92,080** | 4,745 | 0 | 0 | 0 | 82,072 |
| tranco | E31 **on** | 500,530 | 95,856 | 91,568 | 4,288 | **88** (n0=25) | 2,650 | **68** | **81,953** |

（FIFO 臂；`n<2` 占字节拒绝的比例：mixed 85.2%、skew 82.3%、tranco 19.3%。）

**三件事可以同时读出来，而且它们并不矛盾：**

1. **总体是真的。** 晚期替换上，绝大多数字节拒绝确实落在 0–1 条记录的块上——
   与 `RESULTS_HOLES_ENTRY.md` 的 53%–98% 同向，本轮把它**拆开**了：
   其中绝大多数是**空块，不是单记录块**——mixed 976,676 : 603、skew 1,730,709 : 66、tranco 92,080 : 4,745。
2. **机制够不到它。** 183 / 27 / 88 次 pass 对应 97 万 / 173 万 / 9.6 万次 n<2 拒绝。
   代码级原因只有一个：`first_candidate()` 对 `h.count == 0` 直接 `continue`，
   空块成为 E31 首选块的唯一路径是它末尾那个 `prev == SIZE_MAX ? 0 : prev` 的退化分支
   （mixed 那 7 次 n0 pass 就来自它）。其余 n<2 的 pass 全部是单记录块。
3. **够到的那部分，转化率接近 100%。** `low_activity_helped` 182/183、26/27、68/88——
   pass 一旦发生，记录基本都放下了。**问题从来不是"放下没放下"，是"够不够得着"。**

### 4.2 溢出侧的量级（这才是判定依据）

| 语料 | E31 臂 溢出 off→on | 变化 | E31+WIDE 臂 溢出 off→on | 变化 |
|---|---|---:|---|---:|
| mixed | 41,251 → 40,905 | **−346（−0.84%）** | 5,698 → 5,352 | **−346（−6.1%）** |
| skew | 102,068 → 102,042 | −26（−0.03%） | 13,919 → 13,893 | −26（−0.2%） |
| tranco | 82,072 → 81,953 | −119（−0.15%） | 46,786 → 46,721 | −65（−0.1%） |

索引占用同向微降（mixed/E31 3,052.9 万 → 3,045.9 万字节），
`compact_helped` 仍恒为 0（与 E26/I10 的结论一致）。

### 4.3 一条必须一起读的对照：WIDE 臂

| 语料 | 字节拒绝 E31 → E31+WIDE | 其中 n<2 | 溢出插入 |
|---|---:|---:|---:|
| mixed | 1,145,845 → 94,572 | 976,423 → **1,041** | 40,905 → **5,698** |
| skew | 2,103,639 → 171,755 | 1,730,720 → **84** | 102,042 → **13,919** |
| tranco | 500,530 → 241,339 | 95,856 → **285** | 81,953 → **46,786** |

**而 WIDE 臂的 n<2 pass 数与 E31 臂几乎相同（183 / 27 / 84–88）。**
也就是说：那 97 万次"落在空块上"的拒绝，是被**修好 ≥2 条记录的块**消掉的，不是被修复空块消掉的。
读法（这是解释，不是计数）：`put_primary` 的走查在前面那些块修好之后就提前成功返回，
根本不会再走到后面的空块上去——**那些空块上的拒绝是下游症状，不是独立机会**。

### 4.4 纯插入对照：分支会空转

| 语料 | 分支触发 | 释放字节 | 促成放置 | 两臂可观测 |
|---|---:|---:|---:|---|
| mixed | 54 | **0** | **0** | 逐字节相同 |
| skew | 19 | **0** | **0** | 逐字节相同 |
| tranco | 263 | **0** | **0** | 逐字节相同 |

`place_fail_bytes`、槽位拒绝、溢出插入、索引占用在两臂上**完全相同**。
这正是 `RESULTS_HOLES_ENTRY.md` 要的"无垃圾对照"：分支跑得到，但没有东西可回收，
于是所有可观测量不动。**"分支触发过了"与"产生了收益"是两件事**，这张表把它们分开了。

## 5. 判定

**`reclaim_low_activity` 不进入计时轮；按负结果收口，保留为默认关闭的候选。**

理由按计划书自己的停止条件走：

1. **够到的机会太小。** 最好的格子是 mixed/E31 上的 −346 次溢出（占该段 131,072 次插入的 0.26%，占该臂溢出的 0.84%）。
   skew 是 −26。这个量级不可能在端到端维护耗时上被测出来，
   而计划书写的是"有真实促成机会才跑干净构建的配对计时"——**0.13% 不是**。
2. **更大的机会不在这个入口上。** 85% 的拒绝落在空块上，而 `first_candidate` 不选空块。
   要够到它，得改的是**候选选择**（把空块变成一等候选），那是一个**新候选**，不是这个开关的参数。
   本轮不扩大范围去做它。
3. **真正消掉那批拒绝的是 `reclaim_widest`**（已独立测过的 G3/A1'，六格 5/5，保留为最终组合的候选）。
   本轮的 WIDE 臂只是再次显示它的量级，**不作为本文的收益宣传**。

**下一步**：回到 `NEXT_ACTION_PLAN_20261009.md` 的后续顺序——先测 C-2（缩到历史峰值）的**维护期新峰值事件率**，
再按证据决定 E3（写路径分配）是否进入。

## 6. 本轮留下的一条方法教训（如实记）

诊断程序第一版有两处**自查缺陷**，都不是索引的问题，但都属于本项目反复抓过的那一类：

1. **随机臂从语料抽受害者。** 替换到 100% 时原始键已全部消失，受害者搜索必然抽空，程序直接抛错退出。
   改为从**存活池**抽（`pool[chosen] = fresh` 随替换同步更新）。
2. **审计把"被二次替换掉的键"记成丢失。** 修好第 1 点后，随机臂会在同一段内把一个刚插入的新键再抽中当受害者——
   它**合法地**不在索引里，而审计当时的判据是"本段插入的键必须都能查到"，于是报到 ~11% 的假缺失。
   判据改成**先问参考表**（`ref` 里没有就不追）。
   **审计本身错了，索引没错。** 这与 `RESULTS_COMPACT_ROUTING.md` §7 记的那条是同一类：
   **自检的判据写窄了，它就会把合法状态报成缺陷**，而它看起来像是索引坏了。
