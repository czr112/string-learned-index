    read: for W1 the dead region is one run almost always; for W3 it is NOT. The
    difference is the ERASE ORDER, not the layout: erase_at drops a descriptor and
    never writes h.bottom, and h.bottom is a low-water mark, so a gap left below it
    is indistinguishable from one above. W1 erases the lowest key every time, which
    is the lowest-offset record of its block; permuting the victims splits the run.
    So a hole table needs a real free list, and W1's 'one pointer per block' was an
    artifact of the driver -- which this round published as a property of the layout.
    count<2 is the share where repack_subblock no-ops because it returns for n < 2.

DECISION
====================================================================================================================

    The entry condition has TWO halves and BOTH must hold:
      (1) 局部整理有效            -- local reclaim works
      (2) 重复复制活跃后缀占主导   -- the repeated copying of live suffixes dominates

    READING. Three corrections the adversarial review forced onto an earlier draft:

    1. THE CANDIDATE IS NOT COVERED BY repack ON THE LATE CHECKPOINTS. `guarded` applies
       repack_subblock's own n<2 early return; the earlier draft's test did not, so it
       credited repack on blocks holding 0 or 1 live records, where repack does nothing.
       With the guard the 200% rate collapses while hole stays high.
    2. THE COPY IS TINY. mean_live_to_copy is 39-119 bytes at 200%, and on most of those
       events there is at most one live record to move -- there is no repeated copying
       for the candidate to eliminate. The entry condition's SECOND HALF fails, and it
       fails independently of point 1.
    3. THE STRUCTURE IS THE DRIVER'S. W3 permutes the erase order and the dead region
       splits, so 'one run per block' was an artifact of W1 always erasing the lowest
       key. A hole table needs a real free list. The first draft published the opposite
       as a property of the layout, and the metadata-cost registration rode on it.

    DISPOSITION: do not enter hole reuse as specified. What the round DOES establish is
    narrower and cheaper to test: repack_subblock's 'if (n < 2) return;' is a one-line
    condition, not a mechanism, and on the late checkpoints it is what turns the
    refusals away. Checking that costs one guard change. The n == 0 case needs care --
    it would set h.bottom to bb_ without moving a record. THAT is the next test, not a
    hole table.

    The whole-group compact help rate below is reported with its denominator caveat
    attached; the gap to a per-block repack is NOT explained by compact_plan_rejected.
    (a) compact_entered is incremented BEFORE worth_compacting() is asked, so it counts
        every entry to the branch, including the ones the gate then refused. It is NOT
        'compactions that ran'. The denominators are entered / gated-in / helped, and
        this round separated only the first and the third.
    (b) On the PURE-INSERT arm the help rate is exactly 0 and that one IS explained:
        worth_compacting requires the group's garbage to reach the record's length, and
        nothing was erased, so the gate never opens.

    What would settle the residual gap: a completed-compaction count and the retry's
    failure reason (slot vs bytes) after the compaction commits. Not measured here.

    See RESULTS_HOLES_ENTRY.md for the full reading and the registration.
