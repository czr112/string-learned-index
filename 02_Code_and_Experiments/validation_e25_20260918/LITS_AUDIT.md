## 3. 键坐标：当前模型读的是后缀，而且要改的不止调用点

**这一节是 P0 的核心发现。**

### 3.1 事实

`Model::train`（`index.hpp:794`）第一行就是：

```cpp
const auto s = std::string_view(it->first).substr(prefix);
```

`Model::predict`（`837`）在 `s` 上走 `for (p = 0; p < s.size(); ++p)`，并用 `row(p, previous)` 选表行：

```cpp
std::size_t row(std::size_t pos, unsigned previous) const {
    if (kind == ModelKind::Unigram) return 0;
    if (kind == ModelKind::Position16) return std::min<std::size_t>(15, pos);
    return ((pos & 3U) << 2U) | (previous & 3U);
}
```

`p` 是**后缀内的位置**，`previous` 是**后缀内的前一个字节**（首字节时为 0）。训练时 `previous = 0` 起步，与预测一致。

**所以当前模型是一个纯粹的"后缀局部"模型**：位置 0 指的是区域前缀之后的第一字节，`previous = 0` 是哨兵而不是真实字节。

### 3.2 与 LITS 的冲突不是一个调用点，是三层

任务书 §3.1 说的是"输入应该是 `full_key + prefix_length`"。实测下来要分三层看：

1. **位置坐标**：LITS 的位置桶按**完整键中的绝对位置**选。同一个后缀位置 0，在 mixed 的某区域对应绝对位置 0，在 skew 的某区域对应绝对位置 76。**当前模型对这两者用同一行**；LITS 会对它们用不同的桶。这不是接口包装问题，是**两个模型问的问题不一样**。
2. **前文字符**：后缀首字节处，当前模型用哨兵 0；LITS 要用**完整键的前一个字节**，也就是**区域前缀的最后一个字节**。这个字节在 `Region` 里**没有单独保存**——`prefix_` 是 `std::string`，取末字节是免费的，但**没有任何调用点目前传它**。
3. **表选择**：LITS 的 HPT 是**全索引一份**、由初始完整键集训练；当前模型是**每区域一份**、由该区域的后缀训练。`Region` 目前对模型的全部依赖就是成员 `model_`。改成共享 HPT 后，`Region` 要持有"共享只读对象的指针 ＋ 本区域的 `prefix_length` ＋ `alpha/beta` ＋ `groups`"，生命周期归 `Index`。

### 3.3 一个顺带的量级事实

当前模型的**输入长度上限是 16**：`train` 里 `lim = min(16, s.size())`，`predict` 靠提前停止退出，`Position16` 把位置截到 15，`Context16` 只看 `pos & 3`。

**LITS 的 HPT 会读更长的前缀**（这正是它的卖点）。所以本轮比较的**不只是"换了个表"，还有"读的字节数变了"**——`predict` 的提前停止与 HPT 的提前停止是两套不同的停止条件（任务书 §3.2 已经点到），而 §2.3 的 8 个调用点全都会受影响。

## 4. 指纹融合：`consumed` 的语义比任务书写的更重

`find_impl`（`2645`）的融合路径：

```cpp
const auto s = key.substr(prefix_.size());
Fingerprint fp;
const auto pred = model_.predict<Hash>(s, groups_, mode.route, fp);   // 模型边读边喂 hash
...
fp.tail(s.substr(pred.consumed));                                      // 模型没读完的收尾
tag = fp.tag();
...
result.steps = pred.consumed;                                          // ← 关键
```

**两件事同时依赖 `pred.consumed`**：

1. 指纹从哪个字节续上——所以只要模型**按顺序、不重不漏**地喂完它读过的字节，`fp` 最终就等于 `Fingerprint::of(s)`，与存储在 `3070` 的标签一致。
2. `result.steps`——一个**被报告给基准和门**的量（`Result` 的公开字段）。

**LITS 适配器为什么必须返回 `consumed = 0`**（任务书 §5.1 的结论，此处给出本代码里的确切理由）：

- LITS 读字节的**顺序与集合**与当前模型不同（它可能回头读 `prefix` 的末字节，也可能跳过）。把这样的字节序列喂进 `Fingerprint`，得到的**不是** `Fingerprint::of(suffix)`——而**存储标签是按 `Fingerprint::of(suffix)` 算的**（`3070`）。那会让每一次候选比对都白白穿透标签过滤。
- 返回 0 则 `fp.tail(s)` 覆盖整个后缀，**恰好复现存储标签**。

**但必须同时接受一个代价**：`result.steps` 会变成 0。**它是一个已发布指标**（E5 起的 `steps`），把它从"模型读了多少字节"改成"0"会让跨轮比较失去意义。**本轮的处置**：`steps` 保留为"模型实际读的字节数"由适配器自己填，指纹续接点**另设一个字段**，两者不共用。任务书 §5.1 说"另设 `model_bytes_read` 诊断量"是对的，但**反过来更准确**：`consumed` 应该留给 `steps`，新设的是**指纹续接点**这个字段。

**M0 侧不动**：任务书 §5.1 要求"不能为了接口整齐把 M0 故意改慢"，与本代码一致——M0 继续走融合快路径，需要解释指纹遍历成本时另立 `M0_separate_hash` 诊断臂。

## 5. 两个训练点是分开的（任务书 §5.2 的担心成立）

`Region::demand_profile_ctx`（`2468`）**自己造了一个 `Model`**：

```cpp
Model model;                                          // 局部对象
model.train(first, last, prefix.size(), cfg.model_kind);
...
const std::uint32_t g = model.predict<false>(s, groups, cfg.canonical, dummy).group;
```

它与 `Region::Region` 里那个 `model_` **没有任何共享**，只是按同样的规则各自训练了一遍。两者的输入是**同一段键**（`bulk_load_reusing_ids` 用同一个 `pairs`），前缀也各自算一遍。

**先澄清一件事，免得读成"当前代码有 bug"**：**两个训练点本身不证明当前存在映射错误。** 同输入、同参数、确定性的训练，两处会得到相同的表，因而得到相同的映射——**这是"两处独立"，不是"两处不一致"**。本节要说的是接 HPT 时的要求。

**后果**：接入 LITS 时如果只替换 `1836` 那处，需求统计仍按 Context16 算，放置按 LITS 算——正是任务书 §5.2 点名禁止的接法。**所以两处必须都指向同一个不可变 HPT 对象**，这不是为了消除一个已存在的错误，而是为了让"统计与放置用同一映射"成为**结构上成立**的事实，而不是靠"两次训练恰好一致"来维持。

另有一处**已经在用模型身份做校验**、接入时要照顾到：

- `model_identity`（`1457`）把 `m.kind` ＋ 整个 `m.cumulative` ＋ `groups` ＋ `canonical` 折成一个 64 位摘要，用于 E20/E21 的 `preset_ok` 判定（`1890`）。**它当前只认 `Model` 这一个类型**。
- 本轮**不接 R2**（任务书 §1 已定），所以 `preset_ok` 永远为假、这条路径不会被走到。但它是一个**静默点**：新后端的字段若不在摘要里，将来接 R2 时会得到一个"摘要相同"的错误结论。**建议在 P1 就把它改成按 backend 分派，而不是等接 R2 时再补。**

### 11.1 更正本文 §10 第 2 项：`p` 超过桶数不是问题

**撤回。** 源码里位置索引是**掩码取模**，不是直接下标：

```cpp
static constexpr uint32_t PS_MASK = (1 << PS_HASH_LEN) - 1;   // = 31，PS_HASH_LEN = 5
...
int _ps = b & PS_MASK;                                        // 训练，lits_model.hpp:118
const auto &uni = m[i & PS_MASK][...][...];                   // 预测，lits_model.hpp:170
```

`PS_SZ = 32`，`i` 到 123 也不越界。**所以 §8.3 第 3 点担心的"`p = 123` 远超 32 个位置桶"是虚警**，我按"位置桶要按三位数设计"写下的那条建议**作废**。

**但换出来一个真实的设计问题**：位置是**按 32 取模**的，所以 `p` 决定的是**相位**。`p = 0` 的区域与 `p = 76` 的区域，同一个后缀位置会落在**不同的桶**里——**这正是"位置坐标"那件事在 HPT 内部的具体形态**（§3.2 第 1 点），而且它比"桶不够用"这一类问题更贴近本轮要测的东西：**换模型换掉的是条件化方式，不是表的大小**。

### 11.2 更正 §4 的一处：E4 的补丁只在"传完整键"时够用

E4 的 `lits_model.hpp` 补丁把两处 `key[i - 1]` 改成 `i == 0 ? 0 : (key[i - 1] & FC_MASK)`。**它修的是 `gcpl == 0` 时读 `key[-1]`。** 而预测循环的起点是 `i = gcpl`：

```cpp
for (int i = gcpl; key[i] && ps >= 1; ++i) {
    const auto &uni = m[i & PS_MASK][key[i - 1] & FC_MASK][key[i]];
```

**所以补丁是否够用，取决于适配器传进来的是什么。** 循环是 `for (int i = gcpl; key[i] && ps >= 1; ++i)`，体内读 `key[i-1]` 与 `key[i]`——**起点是 `i = gcpl`，不是 0**。四种接法逐个看：

| 传入的 `key` | 传入的 `gcpl` | `i = p` 时读的是 | 后果 |
|---|---|---|---|
| **完整键** | **`p`** | `full_key[p-1]` ＝ 区域前缀末字节，与 `full_key[p]` | ✅ **合法，且正是 LITS 的本意** |
| 后缀 | `p` | `suffix[p-1]` 与 `suffix[p]` | ❌ **重复跳过 p 个字节**（后缀已经跳过了一次），位置相位与前文字符都错；后缀短于 p 时越界 |
| 后缀 | 0 | `suffix[-1]`（补丁前） | ❌ 补丁前越界；补丁后不越界，但**相位与前文字符都已改变** |
| 完整键 | 0 | `full_key[-1]`（补丁前） | ❌ 同上，相位错 |

**更正**：本文早先写成"传后缀会读 `suffix[-1]`"——**不成立**。传后缀而仍传 `p > 0` 时，读到的是 `suffix[p-1]` 与 `suffix[p]`，问题是**重复跳过**而不是负下标；负下标只在 `gcpl = 0` 时出现，而补丁正好覆盖那一种。**两种错配都不能采用，但错法不同**：一种是语义重复跳过（后缀＋`p`），一种是相位归零（后缀＋0 或完整键＋0）。**E4 的零位置补丁只负责后者里的越界，不负责任何一类的坐标错配。**

**这条把任务书 §3.1 从"推荐接口"升级成"必需条件"**：不是风格问题，是坐标对不对得上的问题。而 `p = 0` 的频率已实测（§8.3 第 4 点）：**百万域名 21.9%、mixed 3.1%、skew 0%**——补丁在百万域名上每五个区域就走一次，**不是可选项**，但也不是 everywhere。

### 11.3 源码证实的一条：`full_key + prefix_length` 就是原实现自己的约定

不是我们发明的适配。`lits_node.hpp:292`：

```cpp
pos = model->getPos(key, node->get_item_array_len() - 2, ccpl + icpl, ...);
```

传给 `getPos` 的 `gcpl` 是 **`ccpl + icpl`——本节点管辖范围在完整键中的绝对起点**。本项目里这个角色由**区域前缀长度 `p`** 扮演（`lits_node.hpp:379` 把节点自己的部分键前缀存下来，正对应我们的 `prefix_`）。**所以 §3.1 的设计是照原实现的用法来的，不是新造。**

### 11.5 一个没关掉的口子

**E4 的 `sources.json` 里没有 LITS 的 LICENSE 文件**，所以没有可校验的哈希，取源脚本**不会去猜一个 URL**。任务书 §12 要求对外发布提取源码前确认代码许可、且不得把论文的文档许可当代码许可。**本轮只读不发布**，所以这个口子被记录而不是被关掉——**但它是一个真实未决项，不是疏漏。**
