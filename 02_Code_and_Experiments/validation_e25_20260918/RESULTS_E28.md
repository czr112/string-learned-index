# E28 结果：长期替换为何把记录推入溢出——失败原因分层

日期：2026-09-20。目录：`validation_e25_20260918`（接 E26 长期替换的后续诊断，**不修改冻结实现**）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**本轮只做诊断，不改任何实现。** 全部试放是**只读**的（对当前结构提问，不做任何改动），被测对象不被扰动。

---

## 0. 结论摘要

1. **"替换键换了逻辑组"这个归因是错的。** 实测换组率 **0.016%–0.046%**（混合 41/262,144、重复前缀 48/262,144、百万域名 241/524,288）。我此前把它写成长期空间增长的原因，**已作废**。
2. **溢出几乎全部由"候选子块内部的字节碎片"造成。** 在落到溢出的插入里，**按序选中的那个子块自己的垃圾被回收后就能放进去 80%–95%**（F1）。
3. **组预算不是约束。** F2（整组重排、预算不变）在 **97% 以上**的失败插入上判定预算够用。
4. **卡的是字节不是槽位**：因字节被拒的候选数比因槽位被拒的高一个数量级（混合 208,689 对 18,527）。
5. **因此要做的是四层里最小的一层**：组内的**子块级重排**，不需要区域级容量重分配（F3）。

## 1. 第一步：替换到底有没有换组（`diag_transfer`）

在每个替换前后各取一次该键的**逻辑组号**，逐周期比对：

| 模式 | 数据 | **换组 / 总周期** | 占比 |
|---|---|---:|---:|
| `same` | 混合字符串 | **41 / 262,144** | 0.016% |
| `same` | 重复前缀 | **48 / 262,144** | 0.018% |
| `same` | 百万域名 | **241 / 524,288** | 0.046% |
| `grow` | 混合字符串 | **0 / 262,144** | 0 |
| `grow` | 重复前缀 | **0 / 262,144** | 0 |
| `grow` | 百万域名 | 6 / 524,288 | 0.001% |

**几乎没有替换会改变逻辑组。** `grow` 模式更少，因为它只是把原键加长、前缀不变。

> **更正**：`RESULTS_LONG.md` 初版写"替换键落到别的组（模型映射变了）"，那是**推断**。实测否定它。该处已改。

## 2. 第二步：失败原因分层（`diag_overflow`）

对**每一次**替换，在操作**之前**取一次只读试放，然后执行操作并读回该记录落在主块还是溢出。

四个层次（F3 未实现——F2 已判定预算够用时它没有对象）：

| 层次 | 允许改变什么 | 回答 |
|---|---|---|
| **F0** | 什么都不改，走现有 `put_primary` 规则 | 当前规则为何拒绝 |
| **F1** | **只回收该子块自己的垃圾**，归属与几何不变 | 字节碎片是否直接阻碍插入 |
| **F2** | 整组重排、**组预算不变** | 组预算本身够不够 |
| **F3** | 区域内跨组重分配 | 空闲是否在别的组 |

**三点读法：**

- **F1 就够。** 80%–95%（`same` 模式 63%–92%）的溢出插入，**只要回收按键序选中的那个子块自己的垃圾**就能放进主块。**这是四层里最小的一层。**
- **F2 从来不是约束。** F2 判定"整组重排后预算够用"的条数**高于** F1 可修复的条数（如混合 200%：220,481 对 207,916）——**组的总预算够，卡的是子块边界。**
- **卡字节远多于卡槽位**（混合 200%：208,689 对 18,527），与 E24 的"合法迁回卡在字节上"一致。

### 口径（必须与数字一起读）

- **"卡字节"与"卡槽位"是候选级的计数，不是互斥的插入分类**：一次失败插入可能有多个候选子块，其中有的因槽位、有的因字节被拒，**因此两列可以同时为正，不能相加当作总数**。`consider()` 内部按"先查槽位、后查字节"记录，所以同一候选只会计入一列。
- **F1/F2 是某个具体判定的可行性结果，不是数学最优上界**：F1 判的是"该子块重排后字节够且有空槽"，F2 判的是"组内活跃字节 + 新键 ≤ 组总面积且有空槽"。**换一个装箱算法可能更多，也可能更少。**
- **F3 未实现**：F2 已判定预算够用，区域级重分配在这个负载上**没有对象**。
- 试放**全部只读**，`trial_place` 不移动任何记录、不改任何计数。

## 3. 这是怎么和冻结版本对上的

机制链条（与数据一致，且每一步都已测量）：

1. `erase` 移出条目 → **槽位**立即空出；
2. 但该记录的**后缀字节留在块内**，子块水位 `bottom` 不动 → **可用后缀字节没有增加**；
3. 后续插入要的是**字节**。按键序选中的那个子块若按字节已满，新键仍放不进去（**F0 拒绝，卡字节**）；
4. `compact` 的触发条件是"**某个**子块同时有空槽和足够字节"。**组里有垃圾、却没有任何一个子块同时满足两者时，压缩一次都不会跑**——这正是 C1／C2 空间逐位相同的原因（它们只改压缩怎么跑／跑不跑，不改触发条件本身）。

**E26 的 C2 只跳过了"腾不出足够字节"的压缩，没有改变"要不要压缩"的判据**，所以它对空间无能为力。这与实测（C1 与 C2 空间逐位相同）一致。

## 4. 因此下一步最小、有依据的改动

**实现 `repack_subblock` 级或 `repack_group` 级的局部重排**，而不是区域级容量重分配：

- **F1 的上位实现**：把"候选子块"扩展到其所属的组内重排（`repack_group(g)`），或先把触发条件从"某子块同时有空槽与字节"改为"**组内垃圾 ≥ 待放置长度**"——后者是一行改动，且直接对准实测到的拒绝原因。
- **预算不变、逻辑组号不变、模型不变**；子块边界可以重划。
- **必须计入**复制字节、临时峰值与目录重建；**子块边界一变，E25 的 `Located` 立即失效**。
- 触发带迟滞与最小间隔（任务书与文献检索文档都提到）。

**若 F1 上位实现后主块利用率恢复，则 F2／F3 不做。**

## 5. 适用边界

1. **只做诊断**，没有实现任何维护机制，**冻结版本未改动**。
2. 负载是"删除一个活跃键、插入一个不同的键"，活跃数恒定；两种键模式都报。
3. **F1/F2 是可行性判定，不是收益预期**：合格 ≠ 值得做，收益要等实现后按完整成本测。
4. **不含更新（只改值）**；那条路径不触发压缩与溢出。
5. **单线程、单核绑定**；无 sanitizer。
6. **F3（区域级重分配）未实现**，因此"空闲是否在别的组里"这个问题**本轮没有直接答案**；只能说在**这个负载**上 F2 已判定预算够用。
