# E36 结果：内联标签（B / O / T）——把 tag 从记录里搬到有序条目旁边

日期：2026-09-21。目录：`validation_e25_20260918`（E35 之后）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**审阅裁定**：**保持冻结配置，先完成 E35 的三处统计口径修订（已做，见 `RESULTS_E35.md` §7），然后实施一次 B/O/T 内联标签对照。有界迁回再后移一轮。O1 仍不进入默认。**

**一句话结论**：**机制成立且按预测工作，但点查的恢复是有条件的——它在"线性扫描占主导"的数据集上完全恢复（mixed 追平 B、百万域名反超 B），在"二分占主导"的 skew 上无法恢复（仍慢 18%–27%）。按审阅的停止条件，这属于第 ④ 条：按场景报告，不增加数据集专用选型规则。** **内联标签本身的边际代价是零**（空间与搬动都恰好 1.000×O），因为它住进了结构体的对齐填充里。

## 0. 装置与口径

| 变体 | 内容 | 对照目的 |
|---|---|---|
| **B** | E34 同一 OFF 配置（冻结版本） | 原始读写表现 |
| **O** | B ＋ `overflow_stable_store` | 稳定记录存储的表现 |
| **T** | O ＋ `overflow_inline_tag` | 标签读取位置的净影响 |

**同轮直接计算 `T/O` 与 `T/B`，不从历史结果换算。** 两臂之间的断言：`B↔O` 差 `overflow_stable_store` 一个开关，`O↔T` 差 `overflow_inline_tag` 一个开关，都由 `require_only_switches_differ` 对着 `switches.hpp` 的唯一字段表断言（新开关在**四张表**里都登记了）。

**边界（按审阅固定，逐条守住）**：Hybrid 阈值未改、无 SIMD、不缓存前缀、不动分配器；二分仍按**完整字符串**排序，**标签不用于确定字典序**；扫描仍读完整记录、**不按查询标签过滤**；原记录中的标签保留（记录布局未变）；插入、删除、空闲槽复用时标签与句柄**同一个结构体、同一个数组、同一处写入**；**首版没有为追求 5 B 而引入 packed 布局**。

**装置**：`bench_tag.cpp`（由 `bench_prefix.cpp` 派生）一个源两个目标——干净构建供时间、`-DE25_DIAG` 供计数；**四臂 {B, O, T, ART} × 4 重复**（四臂四重复让每个臂在每个位置上各出现一次，轮转平衡）；5 独立进程 × 3 数据集 × 2 模式。扫描由 `bench_scan_s4.cpp`（由 `bench_scan_s3.cpp` 派生）另测，四臂 {S2, S2O1, S2OT, ARR}。

**配对声音性（先断言再看比值）**：三臂在同一格上计时的是同一批键、返回的是同一批结果——`queue_hash` 与 `queue_acc` **2880 对比较，0 处不符**。

**读法，四条：**

1. **点查的恢复是条件性的，而且条件正好是 E35 找到的那条路径分派。** mixed 与百万域名的溢出查询**以线性为主**（E35：mixed 在 200% 上二分占比 **0.0%**、百万域名 **8.7%–14.6%**），T 把点查**追回到 B 的水平**（mixed 1.019–1.038，即持平；百万域名 0.924–0.946，即**反超**）。**skew 的溢出查询 94.7% 走二分**，而**标签不能用于定序**，所以二分那一段它一点也帮不上——skew 的点查**仍慢于 B 18%–27%**（1.181–1.266，方向 0/5）。
2. **维护优势保留下来了**：`T/O` 全部 ≤1（0.933–0.989，方向 4–5/5），`T/B` 在六格上**全部优于 B**（0.863–0.980，多数 5/5）。**没有出现审阅担心的"为恢复读性能而丢掉维护优势"。**
3. **空间与搬动：内联标签的边际代价是零。** `T/O` 的 `memory`、`ov_bytes`、`ov_handle_moves`、`ov_handle_move_bytes` **逐位相同**（诊断构建实测：mixed/same 两臂都是 18,184,935 次搬动／145,479,480 字节）。原因是 `sizeof(OrderedEntry)==8`——`uint32_t` ＋ `uint8_t` 补齐到 8，**标签住进了那 3 字节填充里**。**审阅预计的"相对 O1 的 4 B 句柄翻倍"确实发生了，但它发生在 O 和 T 两臂上（见 §4 第一条），不是 T 单独付出的。**
4. **扫描没有为标签付出代价。** `S2OT/S2O1` 落在 **0.968–1.029**，全部在各自的噪声底（1.037–1.279）之内，方向计数散开。这与设计一致：扫描仍读完整记录、不按查询标签过滤。`S2OT/S2` 上 skew 的 1.044–1.154（0/5）**是 O 相对 B 的既有扫描代价**（E35/E34 的 `S2O1` 同向），**不是标签新增的**。

## 3. 判定：按审阅的四条停止条件逐条对照

| 审阅的条件 | 本轮实测 | 是否成立 |
|---|---|---|
| **① 记录访问显著减少 ＋ 点查恢复 ＋ 维护优势保留 → T 进入候选** | 记录访问降到 O 的 **3.8%–7.7%**；点查在 **mixed 与百万域名**恢复（1.019–1.038 与 0.924–0.946）；维护六格全优于 B | **在 mixed 与百万域名上成立** |
| **② 机制成立但点查仍明显慢于 B → 停止扩展 O1，保留为特定写入／尾延迟场景的方案** | **skew** 的点查仍 1.181–1.266（0/5），原因是它的二分占比 94.7% 而标签不能定序 | **在 skew 上成立** |
| **③ 为恢复读性能导致条目增大、维护优势消失 → 记录结构取舍，转向原容器上的有界迁回** | 条目确实从 4 B 增到 8 B，**但维护优势没有消失**（T/O ≤1，T/B 全优于 B） | **不成立** |
| **④ 只有某个数据集获益 → 按场景报告，不增加数据集专用选型规则** | 见下 | **成立** |

**所以本轮落在 ① 与 ② 的并集上，按 ④ 的口径报告**：

> **T 在"溢出查询以线性扫描为主"的负载上恢复点查（mixed 追平 B、百万域名反超 B），在"以二分查找为主"的负载上不能（skew 仍慢 18%–27%）。差异的来源是已测量的路径分派，不是数据集的名字。**

**不增加数据集专用选型规则**（审阅明确要求）。**T 是否进入候选、以什么条件进入，由审阅决定。** **O1 与 T 都保持非默认，冻结版不变。**

## 4. 边界与必须随数字一起读的三件事

**（一）本轮把有序条目的类型改宽了，O 和 T 都受影响——这一轮的 O 与 E34 的 O 不逐字节相同。** E34 的 `order_` 是 `vector<uint32_t>`（4 B）；本轮为了"标签与句柄同一个结构体"把它改成 `vector<OrderedEntry>`（8 B），**两条臂都用新类型**。后果：

- `T/O` 的搬动与空间**恰好 1.000**，因为两臂都是 8 B 条目——**这正确隔离了标签**，但**它不度量"4 B 句柄 → 8 B 条目"的代价**。
- 相对 B，本轮 O 与 T 的搬动都是**八分之一**（8 B 对 48 B），而 E34 的 O 是**十二分之一**（4 B 对 48 B）。
- **这个变宽的代价在维护时间上低于本测量的分辨力**：本轮 `O/B` 完整维护 200% 是 0.922（mixed/same）、0.876、0.943、0.841、0.984、0.968，与 E34 的 0.912／0.876／0.943／0.841／0.984／0.968 **同一量级、逐格接近**。**E34 的数字仍是 E34 那个二进制的记录，两者不混引。**
- **但它在空间上是看得见的，而且这一处有独立测量**：`O/B` 的常驻空间在 mixed 上是 **1.001–1.010**（其余两数据集仍 ≤1）。差分门在同一配置上给出的是 **+51,072 字节**（mixed、131,072 键、200%，即每条目 +4 B × 约 12,768 个条目）——**`arm_a_memory` 25,467,239 → `arm_b_memory` 25,470,607，其余逐字段不变**（`handle_moves_total` 528,988、`record_moves_total` 0、比对条数 553,027 全部相同）。**所以变宽的代价是"空间可见、时间不可见"，不是"没有代价"。**
- 想做"4 B 句柄的 O ＋ 8 B 条目的 T"这个对照，需要 packed 布局——**审阅已明确首版不做**，所以本报告不做这个减法。

**（二）skew 的未恢复不是"标签没用"，而是标签用不上。** 二分查找按完整字符串定序，标签在定序里没有位置；skew 的溢出容器大（E34：824 条），大多越过冻结阈值走二分。**这条依赖是本轮最重要的边界**：T 的收益上限由"线性扫描占该负载溢出查询的比例"决定，而那个比例是**数据决定的**（E35 §1 已量）。

**（三）点查的恢复幅度不能等同于端到端收益。** 本轮点查是在计时时段**之外**测的（`query_ms`），而维护是时段内。`T/O` 的点查是 **0.656–0.993**，维护是 **0.933–0.989**；**两者不能说成"整体快了 X%"**。

**（四）其它沿用既有边界**：绝对值只来自干净构建；诊断构建的计数在热路径里、两臂不对称，**其时间不进入任何表格**；ART 不参加队列阶段（libart 没有溢出容器），所以队列表里没有 ART 列；队列长度截断到 2048 键并由 `keys` 字段如实报出。

## 5. 正确性门：`check_tag_store`（三数据集全 pass）

按审阅列的五项逐条落地，**每一项都是断言而不是说明**：

| 审阅要检查的 | 门怎么回答 | 实测 |
|---|---|---|
| **标签碰撞后仍完整判等** | 大规模**缺席键**查询必须全部返回 `found == false`——tag 匹配落到完整比较上，假阳性会在这里现形 | mixed/skew/tranco 各 **40,960** 次缺席查询，**全部为 false** |
| **删除、重插、空闲槽复用后没有旧标签残留** | `Region::diag_tag_pairing` 逐条比较**每个有序条目的标签副本与它所指向记录里的标签**，任何不符即失败；操作序列专门制造删除、重插与槽位复用 | 配对检查 **27,532 / 38,932 / 244,716** 条，**0 处不符** |
| **句柄与标签始终成对** | 同一次遍历（两者本就在同一个结构体、同一个数组里，这条是**被验证的不变量**而不是被追的 bug） | 同上 |
| **点查、更新判重、任意起点扫描与参考表一致** | 三臂各自对**独立的 `std::map` 参考**作答，再**互相比对**（含 `Result::source`——开关不得把键在主块与溢出之间挪动） | mixed **389,120** 次点查、skew 389,120、百万域名 **2,826,240**；扫描 **5,120** 次、逐条比对 **245,760** 条记录 |
| **三臂键值内容与溢出记录数一致** | 每批之后比较 `overflow_count()`，扫描输出逐条比 | 溢出计数 **B ＝ O ＝ T**（mixed/skew 2,476／4,285，百万域名 22,772） |

**门的非空性**（否则"没有旧标签"只是"没有执行到那段"）：断言 `ov_tag_entries > 0`、**`ov_tag_reject_pre > 0`**、`ov_linear_recs > 0`——**标签路径真的跑过**，且真的有候选被拒后才走到完整比较。

**`sizeof(OrderedEntry)` 由门报告，不作假设**：**8**（`uint32_t` ＋ `uint8_t` 补齐；不是设想的 5）。
