# 扫描起点轮结果（阶段 A 计数诊断 + 阶段 B2 判别器）

日期：2026-10-10。轮次目标（`../docs/NEXT_ACTION_PLAN_20261010_SCAN.md`）：定位 WIDE 组合在
grow/tranco 与 25% 检查点上测到的扫描代价，证据支持则实现一个最小修复候选。
**收口判定：W 的扫描代价 = 一次性停顿（主因，机制未定）+ 稳态遍历代价（ctx16/grow/tranco
100–200%）；起点推进经独立核验修正为"两臂共同的极端起点走行"（位置不同、合计相同），
不构成对 W 额外代价的解释，但作为通用优化证据完整、另立候选 S。按计划 3.3 节停止扫描轮。
W/WC 维持默认关闭的场景候选身份，扫描取舍按本文第 3 节重新表述。**
收口验证（组合门/sanitizer 重跑、计数器手检门、首批逐调用探针）已全部完成，见第 6 节。

## 0. 结论摘要

1. **阶段 A：入口假设对"中位起点"不成立；独立核验把代价定位到少数极端起点，且证明它是
   两臂共同的成本、被 WIDE 换了存放位置。** 逐调用计数在三个网格的所有检查点上，17 个起点的
   **中位数**都是 1 次比较、0 次跳过（W 与 B 相同）；但独立核验件
   （`RESULTS_SCAN_ENTRY_VERIFY_20261010.md`）的逐起点表显示，个别起点一次调用要线性走
   136–492 条记录。把两侧相加后，W 与 B 的推进比较**逐起点完全相同**
   （例：lits/same/mixed frac=1.0 start=14：B `0+367`、W `360+7`）——WIDE 只是把同一段线性
   走行从溢出容器搬到主块。首批探针的墙钟证实：极端起点的调用在两臂都贵（10–30 µs vs 常规
   5–7 µs），W 侧并不更慢。
2. **唯一随 WIDE 变化的计数量是合并比较**（200% 时 W/B 最高 2.97×，见第 1 节表 1），
   但它是结构差异的**结果**（W 把记录从溢出容器搬回主块，两侧游标同时活跃），不是可省的工作。
3. **阶段 B2 判别器**（同一索引状态上，物化扫描 `scan()` 与不物化扫描 `scan_consume()` 并排计时，
   3 进程 × 4 重复 × 17 起点，交替先后）给出：ctx16/grow/tranco 100–200% 上，
   **物化模式 W/B = 1.7–2.0（方向 1–5/204），去掉物化的 cons 模式仍有 1.2–1.5（方向 22–83/204）**。
   即：WIDE 的扫描代价主要在遍历侧，结果字符串的构造只是把它放大（mat/cons 倍率：B ≈ 5.5–10，
   W ≈ 7–12），不是主因。
4. **同轮定位到既有"扫描回归"的主体是一次性停顿（one-time stall），并把它与稳态代价分开。**
   lits/same/mixed 25%×limit16 的主聚合在三个进程里给出 W/B = 11.09 / 12.84 / 10.59，
   而同一状态、同一查询队列的**稳态**逐调用计时是 0.74（W 更快）。逐调用探针（
   `bench_firstscan`，2 进程 × 2 重复）显示：每个样本里**恰好一次调用**吸收了一次
   0.1–0.7 ms 的停顿（位置随样本在 start 0/4/10 之间变化），计数器在该调用上没有任何
   对应工作量；ctx16/grow/tranco 200% 的同一现象量级 2.0–3.5 ms，且四次样本都落在
   **第一个 limit=256 调用**上。B 臂在同样两格基本没有该停顿（>20× 离群：B 0 次、
   W/WC 每样本恰好 1 次）。
5. **无"消除 W 回归"的候选。主因是一次性停顿 + 稳态遍历代价，两者本轮都不可修；
   物化不是主因；S（缩短起点推进）是两臂共同的通用优化，入口证据完整，另行立项。
   按计划 3.3 的退出规则停止本扫描轮，转下一项（阶段 D 或 S，见第 7 节与状态文档）。

1. 正确性与机制执行：通过（见上）。

   W 侧落在主块、B 侧落在溢出，两侧合计相同）。这段走行有明确可省空间（子块秩序 + 容器有序，

→ 综合：**不把 S 作为"消除 WIDE 扫描代价"的候选**（回归的两个成分 S 都覆盖不到）；
但把 S 的入口证据按完成态登记（第 4 节），它是一项**两臂共同的扫描起点推进优化**，
可由下一轮以自身的 A/B 立项。

## 2. 阶段 B2：物化 vs 遍历判别器

### 2.1 装置

`bench_scanconsume`（新目标，`-DE25_SCAN_CONSUME` 只由它定义；`bench_combo` 的产物逐位不变）：
在每个检查点上，对 B、W 两臂，用**同一批起点/limit**并排计时两种消费方式，交替先后
（(起点序号+遍号) 为偶数时先物化），每次调用单独一行：

- `mat`：`index.scan(start,limit)` —— 现行路径，构造结果字符串；
- `cons`：`Index::scan_consume(start,limit,sink)` —— **逐行镜像 `scan()` 的遍历**（同样的定位、
  组序、子块推进、溢出推进、合并比较、块跳过），行以 `string_view` 交给 sink，不构造结果字符串。

`scan_consume` 位于 `index.hpp` 的 `#ifdef E25_SCAN_CONSUME` 块内，没有任何现有目标定义该宏，
现有计时目标看不到它（`bench_combo` 重建后产物逐位不变，已核）。验证：每次运行后在计时外
重放两种模式并逐行对照参考表，另用 capture sink 重建全键逐字节比较；不一致计数写入 verify 行。

装置修正（必须知情）：首版 `Index::scan_consume` 传"剩余预算"给区域，跨区域时（tranco/limit=4096）
返回行数偏少——由 verify 行抓住（680/2040 行 `mismatches=1`），修正为与物化路径一致的
"全局目标"后全绿（6,120/6,120 verify 行，3 网格 × 3 进程）。修正前后的原始行都保留：
`results/scanconsume_20261010/`（有效）与 `superseded/`（含无进程标识的首轮输出与 pilot）。

### 2.3 判定

- 物化不是主因（去掉物化后 ctx16/grow/tranco 100–200% 的 W 惩罚仍在，1.2–1.5×，方向显著）；
- 起点推进不是（第 1 节）；
- 计数工作量不是（组/块/行/分配相同或更少）；
- 剩下的可解释面是"同一组操作在 W 的状态下单位成本更高"（内存系统层面：记录分布、缓存行为），
  以及第 3 节揭示的"第一批"效应。二者都**不是本计划意义上的可修环节**（无法指认一段可省的代码）。

## 3. 第一批扫描的解剖：一次性的停顿，不是持续的工作量

lits/same/mixed、25% 检查点、limit=16，同一批进程：

| 测量 | B | W | W/B |
|---|---:|---:|---:|
| 主聚合（维护段之后紧接的扫描；combo/scanconsume 轮口径） | 157,845 ns | 1,778,718 ns | 11.09 / 12.84 / 10.59（三进程） |
| 首批逐调用合计（pass0+pass1，firstscan 装置） | 196,430 ns | 690,122 ns | 3.51 |
| 稳态逐调用（判别器：主阶段之后） | 6,213 ns/调用 | 5,508 ns/调用 | 0.74（方向 152/204） |

**逐调用探针把差额定位到单次调用上**（`analyze_firstscan.py` / `results/firstscan_20261010/`）：
- 每个（进程 × 重复）样本里**恰好一次**调用吸收一次停顿；位置随样本变化
  （lits/25%：start=0、4、10 都有出现，四次样本中三次落在 start=10）；
- 量级：lits/same/mixed 0.14–0.71 ms；ctx16/grow/tranco 200%×L256 为 **2.0–3.5 ms，
  四次样本全部落在第一个 limit=256 调用（start=0）上**；
- 停顿调用在**计数器上与正常调用无法区分**（stage A 数据：rows=16/256、groups=1/36、
  合并比较=16/157，四个重复逐位相同）；
- 离群普查（>20× 该格中位调用）：在**两个回归检查点上**，W 与 WC 都是 4/4 样本各恰好 1 次
  （lits 落在 start=10/9/4，ctx16 四次全部落在 start=0/limit=256）；同检查点上 **B 与 C 为 0 次**。
  frac=0（无维护段）时四个臂都会偶发同类停顿（0.1–0.3 ms，位置 start=0/4/9/10）——说明这类停顿
  作为环境事件本来存在，但**维护之后的 W 状态让它变得必然且量级更大**。

**两个组成部分必须分开引用**：

1. **一次性停顿**（本节主体）：每（样本，检查点）一次，量级 0.1–3.5 ms，随状态（W 的维护量）
   放大；机制未定——现有观测无法在 分配器（大块 free 后的 trim/consolidate）、页错误/局部性、
   宿主机/虚拟化 停顿之间做出区分，且按计划不再追查这一层。
2. **稳态遍历代价**（第 2 节）：ctx16/grow/tranco 100–200% 上真实存在，cons 模式 1.2–1.5×、
   物化模式 1.7–2.0×，方向显著（最坏格 1/204、2/204）；lits 上更小；lits/same/mixed 的
   25% 格子稳态没有代价（W 更快）。

含义（报告与状态文档的表述规则）：
- 历史上"WIDE 扫描回归"的数字（combo 2.9–3.6×、本轮 11×）由**一次性停顿 + 稳态代价**共同构成，
  其中 lits/same/mixed 25% 格的复现数字**几乎全部**来自停顿；
- 对"写突发→扫描"交替的负载两者都要付；对"写一次、扫描很多次"的负载只有停顿留在第一批；
- 稳态单次成本在多数格子里与 B 持平，lits/same/mixed 上多数格子更快。

## 7. 装置缺陷与修正记录（引用本文件时必须知情）

1. **`scan_consume` 跨区域预算错误**（首版）：区域收到"剩余预算"而循环按全局行数比较，
   跨区域时提前停止；verify 行抓住（tranco/limit=4096，680 个 mismatch=1），修正后才进行
   正式扫描。首轮输出（无 run_tag，且含该缺陷）整目录移入 `superseded/`，不作为证据。
2. **判别器行缺进程标识**（首版）：三进程写入同一文件后无法在"同一进程内"配对；全部重跑
   （run_tag 入库，本文件只引用带 run_tag 的版本）。
3. **`pilot` 文件**：`sc_pilot_*`、`sc_pilot2_*` 是装置调试产物（pilot1 含缺陷 1），
   保留在 `results/scanconsume_20261010/` 内但不作证据。
4. **手检门首次注册漏了 `SAN_TARGETS`**：`san_check_scan_entry` 用普通编译器构建，与
   `check_scan_entry` 产物哈希相同，"sanitizer 验证"是一次空转；比对两条构建记录后修正
   （登记进 `SAN_TARGETS`），san 版重跑通过（哈希 `e4685b07…`）。
5. **计划文档的两处状态漂移**（复核时发现，已在本轮修正）：适配包带 `index_hpp_sha256` 的
   manifest 是 **4 份**（含两个 routing 包），不是 2 份；`implementation_version` 字符串
   与 manifest 的同步要求适用于全部四个包共用的 `our_index_adapter.cpp`。本轮已把四处
   manifest 与该字符串一起更新到 `cad9673b…`。
