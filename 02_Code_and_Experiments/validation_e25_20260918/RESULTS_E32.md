## 1. 扫描起点定位缓存（清单 §7.1，清单自称"最小改动"）

**改了什么**：`Index::scan` 原本把 `locate(start)` 写在循环条件里、又在循环体里再算一次，跨 R 个区域就是 **R+1 次外层搜索**回答一个已知答案。新开关 `Config::scan_cache_start`（默认 false）把第一次求值缓存下来复用。

**测量装置**：新程序 `bench_scan_s2`（由 `bench_scan.cpp` 派生，**后者与其构建记录未改动**——它产出的是 E27 的 `e27_scan_time.jsonl`）。四臂 `{S0, S1, ARR, S2}`，S2 = S1 + `scan_cache_start`，臂序按重复轮换；5 进程 × 3 数据 × 5 重复 × 3 状态 × 3 长度 = **2,700 条记录**。写入 `results/main/e27s2_scan_time.jsonl`（**不与 E27 的文件混**）。

**结果（S2 ÷ S1，两臂都做结果物化，只差这一个开关）：**

| 数据 | 最好格 | 最差格 | 方向 |
|---|---|---|---|
| 混合字符串 | 0.960（replace25 n=128，4/5） | 1.010（insert25 n=128，1/5） | 多数 3–4/5 |
| 重复前缀 | 0.971（insert25 n=16，3/5） | 1.021（replace25 n=16，1/5） | 多数 2–4/5 |
| 百万域名 | **0.917（insert25 n=16，5/5）**、**0.932（initial n=128，5/5）** | 0.997（insert25 n=1024，3/5） | 多数 4–5/5 |

**读数**：真实收益但**小**（最大约 8%，且只在百万域名上方向稳定）。**跨进程离散度 1.03–1.34**，所以 1–3% 的格子不报成"更快"。

**顺带的一致性检查**：新程序里 `S1÷S0 = 0.746–0.928`、**几乎每格 5/5**，复现了 E27 的 `0.758–0.937`（27 格全同向）✓ —— 说明这个派生程序与 E27 的装置一致，S2 的读数不是装置差异造成的。

## 2. 迟滞与最小间隔（清单 §4.3）：**负结果**

**清单的原话是两件事**："设置最小操作间隔；失败后记录'布局版本＋失败原因'，在状态未实质改变前不反复尝试"。我把它做成两个开关分别测，而不是合成一个：

- **`Config::reclaim_hysteresis`（E31H）**＝间隔（同一组 64 次放置内不重试）**且**垃圾未增长则跳过；
- **`Config::reclaim_skip_repeat`（E31P）**＝**只**看"垃圾未增长则跳过"，**无**间隔。

**测量装置**：新程序 `bench_long_hyst`（由 `bench_long_art.cpp` 派生，后者未改动）五臂 `{C2, E31, E31H, E31P, ART}`，E31↔E31H 与 E31↔E31P 各自断言"只差一个开关"。**5 进程 × 3 数据 × 3 重复 × 4 检查点，`same` 模式**（900 条）。**注意**：5 臂 3 重复时旋转只覆盖 5 个位置中的 3 个，所以本节的臂间比较**不与** E31/ART 那两次 5 重复的轮换运行逐格对照。

**结果一：两个变体都更差（÷ 冻结版本）：**

| 数据 | 检查点 | E31 | **E31H** | **E31P** |
|---|---:|---:|---:|---:|
| 混合字符串 | 25% | 0.826（5/5） | 0.987（4/5） | 1.023（1/5） |
| | 100% | 0.998（3/5） | 1.003（2/5） | **1.062（0/5）** |
| 重复前缀 | 100% | 0.968（4/5） | 1.006（1/5） | **1.069（0/5）** |
| 百万域名 | 25% | **0.445（5/5）** | **1.166（1/5）** | **1.125（1/5）** |
| | 200% | **0.491（5/5）** | 0.993（3/5） | **1.132（0/5）** |

**除以 E31（同一个对照更干净）：`E31P ÷ E31` 在百万域名上是 2.31–2.63，方向 0/5。**

**结果二：机制在结构量上看得见**（200% 检查点，`same`）：

| 数据 | 臂 | 溢出 | 压缩次数 | 索引 MiB |
|---|---|---:|---:|---:|
| 百万域名 | 冻结 | 127,330 | 35,987 | 34.87 |
| | E31 | **25,437** | **1,801** | 26.45 |
| | E31H | 69,626 | 37,235 | 30.85 |
| | E31P | 48,150 | **43,026** | 28.66 |

**机制（诊断构建 `diag_hyst` 的计数器，200% 检查点，累计值）：**

| 数据 | 臂 | 因"间隔未到"跳过 | 因"垃圾未增长"跳过 | **压缩次数** | 溢出 |
|---|---|---:|---:|---:|---:|
| 混合字符串 | E31 | 0 | 0 | 4,277 | 39,878 |
| | E31H | 98,549 | 40,481 | 8,834 | 65,291 |
| | E31P | 0 | 70,005 | 8,936 | 53,878 |
| 百万域名 | E31 | 0 | 0 | **1,801** | **25,437** |
| | E31H | 113,745 | 39,606 | **37,235** | 69,626 |
| | E31P | 0 | **77,159** | **43,026** | 48,150 |

**怎么读这张表（三件事分开）：**
- **跳过的两类次数**是分开计的（`reclaim_skipped_gap` 与 `reclaim_skipped_unchanged`），不是加在一起的一个数。
- **代价的出口是压缩**：跳过回收后，工作被推给 `compact`，百万域名的压缩次数从 E31 的 1,801 升到 37,235／43,026（**比冻结版本的 35,987 还多**），这正是耗时更差的结构侧原因。
- **"永久"这个说法收紧**：跳过一次回收后记录留在溢出，而该组的垃圾并不因此增长，于是**在已测序列里这些组没有恢复**；但**本轮没有跟踪"某组在跳过之后又恢复到允许尝试"的事件**，所以不能断言控制流上永久。要下这个结论，需要给 `reclaim_allowed` 的每次判定附一个"该组上次被跳过、这次恢复允许"的计数器。
- **没有单独统计"实际跑了的回收次数"**：`bench_long_hyst` 只输出 `helped` 与两个跳过计数，没有输出 `subblock_reclaims`，所以"跑了多少次／多少次促成放置"这两个数本轮拿不到。

**结论**：清单这条规则的前提（"失败状态未改变"）在这套结构里不成立——**抑制重试改变的是系统状态本身**（记录进了溢出），所以"不反复尝试"直接变成了"不恢复容量"。**这条分支应当从清单里划掉**，而不是再调参数。

## 3. 尾延迟（清单 §9 的"高分位停顿"缺口）：首次测量

`bench_long_hyst` 在计时段内**逐操作**读时钟。**样本单位说清楚**：负载是"删除一个活跃键、插入一个不同键"，而**每个 erase 与每个 insert 各自是一个样本**（分别计时），**不是一个替换周期**。其余限定：**`same` 模式、长期替换负载、5 进程 × 3 重复、检查点如表中所示**，样本数即该检查点区间内的操作数。时钟读数被所有臂均摊，所以**臂间比值可用，绝对 `cum_ms` 不与无逐操作计时的构建对比**。

**维护单操作延迟（ns，5 进程 × 3 重复共 15 个格的中位数）：**

| 数据 | 检查点 | 臂 | 样本数 | p50 | **p99** | **p99.9** | max |
|---|---|---:|---:|---:|---:|---:|---:|
| 混合字符串 | 100% | 冻结 | 131,072 | 282 | **35,205** | **73,362** | 557,410 |
| | | E31 | 131,072 | 325 | 36,723 | 74,410 | 496,377 |
| | | **ART** | 131,072 | 268 | **811** | **1,852** | 171,072 |
| 重复前缀 | 100% | 冻结 | 131,072 | 285 | **44,902** | **83,137** | 498,248 |
| | | **ART** | 131,072 | 423 | **768** | **1,617** | 189,229 |
| 百万域名 | 100% | 冻结 | 262,144 | 250 | **28,595** | 70,577 | 681,295 |
| | | **E31** | 262,144 | 241 | **1,095** | 33,828 | 300,652 |
| | | **ART** | 262,144 | 105 | **394** | **728** | 179,964 |
| 混合字符串 | 200% | 冻结 | 262,144 | 261 | 2,834 | 13,649 | 268,660 |
| | | **E31** | 262,144 | 217 | 2,282 | **5,936** | 248,772 |
| | | **ART** | 262,144 | 103 | **723** | **1,051** | 380,903 |

**三点，各自限定在自己的格子里：**
1. **"p99 是 ART 的 20–73 倍"这句只在上面这几行成立**：混合 100% 35,205 对 811（43×）、重复前缀 100% 44,902 对 768（58×）、百万域名 100% 28,595 对 394（73×）——**都是 `same` 模式、都是 100% 检查点、都是单操作样本**。p99.9 的倍数更大（70,577 对 728）。**p50 反而同量级**（217–615 对 103–444），所以差距**全在尾部**。
2. **E31 的改善是另一件事，单独一行**：百万域名 100% 的 p99 从 28,595 降到 **1,095（E31 那一行）**，p99.9 在 200% 从 13,649 降到 5,936。**这是 E31 此前没被量到的一面**，但**不要把 E31 的这一格与上面 ART 的倍数并成一句**——两者的臂、检查点、样本数都不同。
3. **尾巴的来源有旁证、但不是本轮直接测的**：一次整组压缩在 **E30（另一轮、另一构建）**实测约 16 µs/次，而 p99 落在 28–45 µs，量级对得上"某次 insert 触发压缩、或落在很大的溢出容器前部"；**E32 §4 的容器规模分布（单容器最多 1,365 条、每次 erase 平均搬 1.9–6.8 KB）是同一现象的另一个侧面**。**本轮没有把 p99 直接归因到压缩**——那需要给压缩与溢出路径分别加计时。

**这是全项目第一次报告高分位停顿**，也是"维护暂停"第一次有分布而不是只有均值。

## 4. 溢出容器成本（清单 §5 的前置诊断）

**清单规定**：在"确认溢出向量的移动／构造／分配仍占主要时间"之前，不得在 O1（稳定槽位＋有序槽号数组）、O2（小增量缓冲）、O3（块式有序容器）之间选型。**此前从未隔离测过**。

**测量装置**：新诊断程序 `diag_ov_cost`（`-DE25_DIAG -DE30_TIME`，源码对两个宏都带 `#error` 兜底），同一长期替换负载，报告逐检查点的溢出插入／删除时间与计数、容器自身搬移的字节数、活跃容器的规模分布，以及同一负载下主块路径的对应数字作分母。写入 `results/main/ov_cost_diag.jsonl`。

**200% 检查点（冻结配置，`same` 模式，单进程单重复）：**

| 数据 | 溢出插入 ms | 溢出删除 ms | **占维护总时间** | ns/插入 | ns/删除 | **每次 erase 搬移字节** | 活跃容器 | 平均条数 | **最大单容器** |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 混合字符串 | 59.6 | 35.1 | **37.6%** | 259 | 349 | **4,361** | 6,784 | 19.2 | **1,365** |
| 重复前缀 | 44.7 | 65.6 | **37.3%** | 171 | 502 | **6,779** | 961 | 136.3 | 824 |
| 百万域名 | 26.2 | 19.2 | **12.2%** | 136 | 243 | **1,880** | 3,273 | 35.5 | 686 |

**判定：前置条件成立，而且代价集中在 erase 的搬移上。**
- **删除比插入贵**（重复前缀 502 对 171 ns；混合 349 对 259），因为 `vector::erase` 要把后面的记录整体前移：混合在 200% 期间搬移 **913 万条记录 / 438 MB**，重复前缀 **1,846 万条 / 886 MB**。
- **插入几乎不搬移**（混合与重复前缀的 `ov_shifted_records_insert = 0`，即新键总是排在容器末尾；只有百万域名有 2,630 次搬移）。
- 所以 **O1（移动槽号而不是记录）直接针对的正是这条最贵的路径**，而 O2/O3 针对的是插入侧——**按本轮的证据，三者里应当先做 O1**。这是清单要求的那一步"先诊断再选型"，现在有数了。

## 5. 本轮新增的开关与装置（冻结版本未改动）

| 新增 | 默认 | 说明 |
|---|---|---|
| `Config::scan_cache_start` | **false** | §7.1 扫描起点缓存 |
| `Config::reclaim_hysteresis` | **false** | §4.3 间隔＋状态（负结果） |
| `Config::reclaim_skip_repeat` | **false** | §4.3 只看状态（负结果） |

三个开关**都已登记进 `switches.hpp` 的四处**（含曾经漏过的那张字段表）。`check_freeze` 在改动后重跑**通过**，开关串里三个新开关都印 `=0` ✓。

**新程序**：`bench_scan_s2`（派生）、`bench_long_hyst`（派生）、`diag_hyst`（同源诊断构建）、`diag_ov_cost`（新诊断）、驱动 `run_scan_s2.py`、`run_hyst.py`、`run_ov_cost.py`。

**三个必须一起读的记账项：**
1. **`sizeof(Region)` 真的增加了 56 字节，开关关着也存在。** 迟滞状态是 `Region` 的**成员**（两个 `std::vector` 头 24+24 字节 + 一个 `std::uint64_t` 8 字节 = 56），而 `Node` 只持有 `unique_ptr<Region>`，`memory()` 通过 `regions_self ← sizeof(*this)` 把 Region 对象本身算进来——所以这是**常驻对象体积增加**，不是口径修正。实测：百万域名 128 个区域 → **+7,168 字节**（`check_e31` 逐检查点上**冻结臂与 E31 臂同时 +7,168**）。
   - **开关打开时另有堆上开销**：两张每组的表（`vector<uint64_t>` + `vector<size_t>`），按 `groups_` 分配，已计入 `tables`。
   - **因此本轮的冻结配置不再与 E31 之前的完全同尺寸**：多 **56 B/区域**。**已发布的历史数字不做追溯修改**（它们描述的是 E32 之前那个二进制）——这一条必须与数字一起引用。
   - 若要"关着时零成本"，把这两张表挪到一个 `unique_ptr` 后面即可（每区域 8 字节）；那是 O1 轮的取舍，本轮不改。
2. **`diag_hyst` 与 `bench_long_hyst` 是同一份源码**，所以诊断构建写自己的文件 `long_hyst_diag_<mode>.jsonl`，**不与计时文件混**。
3. **`bench_scan_s2` 是派生程序而非改 `bench_scan.cpp`**：E27 的程序与它的构建记录是那份结果的凭据，且它追加写 `e27_scan_time.jsonl`，混两个二进制进一份配对文件是这轮之前已经出过的事故。
