# E24 结果：更新路径、空间分解与回收机会诊断

日期：2026-09-18。目录：`validation_e24_20260918`（继承 E23）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**本轮不做计时、不改任何结构、不报任何加速。** 它只回答审阅定的三个问题，然后据此选定下一轮改什么。

**三个问题的答案，一句话各一条：**

1. **增删改走的是慢路径，而且与负载状态无关。** 指标是**完整字符串比较的调用次数**（不是字节、不是时间）：主块命中下 `update` 做 **34×–93×** 于 `find`，溢出命中 **41×–130×**，**未命中 5,949×–34,155×**（`find` 0.004–0.012 次，`update` 仍走 68–287 次）。**这个比值是"值得改"的理由，不是原因的解释**——两次查找只让执行次数翻倍，解释不了四个数量级的差距；"重复查找"需要调用计数，并入 E25。
   **首版曾写"计数随更新上升"，该表述撤回**：分组后是**有升有降**。但这也**不能反过来证明完整更新成本没有退化**（桶内键组成变了、搬移与分配未计入）。
2. **垃圾只在替换后出现**（0 → 2.36／1.78／0.65 MB），溢出容器元素数组常年多留 **22%–30%**；主块账本恒等式**12 格全部精确成立**，无重复计费。
3. **"整组有空位"不等于"这个键放得进去"——而且组级判据几乎没有分辨力**：有溢出的组里 **90%+ 同时有空槽和空字节**，合法迁回却仍是 **0 / 0 / 256**（**压缩前**试放，用既有边界目录判据）；同时**总空闲的 98%–99.6% 躺在没有溢出记录的组里**，组内维护用不到它。

## 0. 方法与本轮的证据边界

- **不做计时。** 全部是**计数**，固定种子，**重跑可复现**，因此没有噪声地板、也不跨进程取中位数。
- 计数器在 `-DE24_DIAG` 下编译（`tools_build.py`）；正式计时不存在本轮，所以计数器与测量调用同处一个二进制没有代价问题。
- **探测键的回答一律以参考表为准**，不看被测索引自己的说法；任何不一致**直接抛异常终止**。因此一条记录存在，就意味着那一格里每个探测键都被交叉核对过。
- 探测表**去重**：`find`／`update` 对重复键无害，但同一个键 `erase` 第二次**本来就该返回 false**，会与"`find` 找到了两次"冲突。
- **探测表不预设"全部存在"**：`replace25` 会删掉部分原始键，所以存在与否由**该状态的参考表**决定，命中数**报告**而非**断言**。
- 继承门在**关闭** `-DE24_DIAG` 的构建下重跑，输出与 E23 一致（见 §5）。

## 1. 增删改走的是慢路径

E23 的源码审查发现：`Region::find`（及 `insert` 的查重）用**指纹 tag 过滤 + 长度预检 + 边界目录 + 溢出 Hybrid**；而 `Region::update` 与 `Region::erase` **一个都没用**——它们逐子块、逐条目做 `compare(suffix(...), s) == 0`，然后线性扫溢出向量。

**本轮把这个差距量了出来，并按命中来源分开**（三条路径的代码不同，合在一起会掩盖写路径到底差在哪）。

### 1.1 按 `find` 的命中来源分组

**这张表在比较什么，必须先写清楚：**

| 项 | 是什么 |
|---|---|
| **被比较的两个操作** | `Region::find(key, qmode)` **对** `Region::update(key, 同值)`；`erase` 走 update 同一段线性搜索，故同列 |
| **指标** | **完整字符串比较的调用次数**（`compare(...)` 的调用数）。**不是逻辑比较字节数，也不是时间** |
| **分子** | `update` 在同一批键上的比较总次数 ÷ 该桶键数 |
| **分母** | `find` 在同一批**同一顺序**键上的比较总次数 ÷ 该桶键数 |
| **绝对值** | 每格都给出：`find` 0.004–2.3 次／键，`update` 28.8–290.6 次／键（见下表） |

比较次数的绝对值在 `E24_TABLES.md` §1 的每一行里；下表把它与比值并列。

**混合字符串**

| 来源 | 键数 | `find` | `update` | update ÷ find |
|---|---:|---:|---:|---:|
| 主块命中 | 4,019 | 1.27 | 70.4 | **55×** |
| 溢出命中 | 24 | 1.67 | 216.2 | **130×** |
| 未命中 | 4,096 | **0.004** | 141.8 | **34,155×** |

**重复前缀**

| 来源 | 键数 | `find` | `update` | update ÷ find |
|---|---:|---:|---:|---:|
| 主块命中 | 3,904 | 1.57 | 145.6 | **93×** |
| 溢出命中 | 139 | 1.24 | 66.7 | **54×** |
| 未命中 | 4,096 | **0.012** | 286.6 | **23,957×** |

**百万域名**

| 来源 | 键数 | `find` | `update` | update ÷ find |
|---|---:|---:|---:|---:|
| 主块命中 | 3,878 | 1.01 | 34.3 | **34×** |
| 溢出命中 | 195 | 1.06 | 43.5 | **41×** |
| 未命中 | 4,096 | **0.011** | 68.3 | **5,949×** |

（替换 25% 的完整表见 `E24_TABLES.md` §1。）

**三点值得单独指出：**

1. **未命中最刺眼**：`find` 几乎免费（**0.004–0.012 次**比较，指纹／组过滤当场拒绝），`update` 仍要走 **68–287 次**。
2. **溢出命中不是一律更贵**：重复前缀上它反而**比主块命中便宜**（66.7 对 145.6）——该数据的溢出向量小，线性扫在它上面并不吃亏。**不能笼统说"溢出查找更慢"。**
3. **删除与更新的代价几乎相同**（同一个线性搜索加一次描述符搬移），所以下表只列 `update`。

### 1.1b 这个比值**是改的理由，不是原因的解释**

**几千到几万倍的差距，不能只用"查了两次"来解释。** 两次查找只让执行次数**翻倍**，与 34,155× 差了四个数量级。这里同时至少有三个因素在起作用，而**本轮只能确认其中第一个**：

| 因素 | 本轮能否确认 |
|---|---|
| 写路径**完全绕过**指纹 tag 过滤与长度预检，逐条目做完整比较 | **能**（源码审查 + 计数一致） |
| 参照路径 `find` 在未命中时的比较次数**接近 0**（0.004–0.012），分母极小 | **能** |
| `upsert` 未命中时**重复查找** | **不能**——需要调用计数，见下 |

**"`upsert` 重复查找"的直接证据应当是：同一次普通 `upsert` 中实际执行了多少次查重、外层定位、模型预测、指纹计算。** 本轮没有这些计数，因此**不把这张表当作"两次完整查找"的证明**；它证明的是**写路径值得改**。调用计数并入 E25 的诊断构建（见 E24-4）。

### 1.2 撤回一条此前的表述

**本轮首版曾写"写操作计数随更新上升 1.5×–2.3×"，该表述撤回。** 分组后看到的是**有升有降**：替换 25% 后主块命中在三个数据上**全部下降**（70.4→67.5、145.6→108.6、34.3→28.8），未命中在混合上下降（141.8→136.4），在重复前缀／百万域名上基本持平。

**但这不能反过来证明完整更新成本没有退化**，原因有三，本轮都未计入：

1. **桶内键的组成会变**：替换 25% 删除了一部分原键，剩下的是另一批键，"每键平均比较次数"是不同键集上的平均值。
2. **只数了字符串比较**，没有计入**描述符搬移、字符串分配/释放、压缩**——这些正是删除与插入的开销所在。
3. **布局退化的代价可能体现在别处**（溢出增长、容量压力），而不一定体现为比较次数。

**因此本轮只声称：写路径缺少已有搜索优化，且这个缺口与负载状态无关。** 完整操作是否随负载退化，要 E25 的完整操作耗时回答。

### 1.3 三种负载不是同一条混合负载的分解

`只改值`／`插入 25%`／`替换 25%` 是**各自从全新初始状态独立构建**的三个状态，在相同计数检查点上对比。**它们不是一条混合更新流的时间分解**，也不能相减当作各阶段的贡献。

## 2. 空间：两层分解

**容量与活跃字节分开报。** `memory_breakdown()` 数的是 **capacity**，把它的总数当成"占用空间"会高估每一个数字。

### 2.0 账本恒等式（**本轮逐格核对，全部成立**）

方案要求主块的分解**互不重复**。子块内 `bb = sizeof(Header) + slots × sizeof(Entry) + 后缀区`，因此

> **块头字节 + 预留描述符区 + 整个后缀区 = 主块分配字节**

**12 个格子全部精确成立**（`E24_TABLES.md` §2.1 的 `closes` 列）。这一条同时排除两类重复计费：

- **未用槽位已在"预留描述符区"里**（槽位是预分配的），不再另加一份；
- **"整个后缀区"已含活跃＋空闲＋垃圾三者**，三者是它的划分，不是它的加项。

**对齐余量不在块内**：块按 64 字节对齐，对齐发生在分配粒度上，不出现在这个恒等式里。

### 2.0a 后缀区的三项也构成一个恒等式——但**只有两项是独立核算的**

> **活跃后缀 + 垃圾后缀 + 未用后缀区 = 整个后缀区**

**各项的来源必须说明，否则"顶层几何等式成立"不能代替分项正确**：

| 项 | 怎么来的 | 是否独立 |
|---|---|---|
| 整个后缀区 | `bb − start_of`（几何量） | 几何 |
| **活跃后缀** | **逐条累加活跃条目的 `length`**（记录范围） | **独立核算** |
| 未用后缀区 | `bottom − start_of`（分配水位） | 独立核算 |
| **垃圾后缀** | **由上面三项相减得到** | **不是独立测量** |

**即：垃圾是减法结果，它正确与否取决于活跃项与水位项都对。** 活跃项确实来自记录范围（不是减法），水位项来自块头，两者独立于彼此；但**没有第三条独立路径去验证垃圾本身**。这一限制在引用垃圾数字时必须带上。

### 2.0b 另列项与 RSS 是**不同口径**

| 数据 | 状态 | 模型 | 目录 | 表 | 外层 | 索引自身总计 | **进程峰值 RSS** |
|---|---|---:|---:|---:|---:|---:|---:|
| 混合字符串 | 初始 | 1.01 | 0.65 | 0.28 | ≈0.03 | 22.84 | **181** |
| 重复前缀 | 初始 | 1.01 | 0.87 | 0.27 | ≈0.03 | 22.61 | **221** |
| 百万域名 | 初始 | 2.02 | 0.72 | 0.26 | ≈0.04 | 25.13 | **153** |

（MB。完整 12 行见 `E24_TABLES.md` §2.4。）

**RSS 比索引自身大一个数量级**（153–221 MB 对 22–25 MB）。差的部分来自参考表、键向量等**不属于索引**的常驻对象，也可能包含分配器保留。**两个口径不互相印证，也不相加**；本轮的结论一律建立在索引自身的计数上。

**目录（E11 的边界目录）不是零成本**：0.65–0.87 MB，与模型同量级。

## 3. 回收机会：合法迁回几乎为零，卡在字节上

一条溢出记录**只能**迁进**按键序选中的那一个子块**（M1），且该子块必须**同时**有**空槽位**和**够放的字节**。

| 数据 | 状态 | 溢出记录 | 多块组 | **合法迁回** | 卡槽位 | **卡字节** | 卡键序 | 粗判据说"能" |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 混合字符串 | 初始 | 751 | 155 | **0** | 0 | **751** | 0 | 0 |
| | 插入 25% | 33,486 | 6,752 | **0** | 27,073 | 6,413 | 0 | 0 |
| | 替换 25% | 12,877 | 3,318 | **0** | 819 | 12,033 | 0 | **1,089** |
| 重复前缀 | 初始 | 4,901 | 607 | **0** | 0 | **4,901** | 0 | 0 |
| | 插入 25% | 37,578 | 953 | **0** | 13,941 | 23,637 | 0 | 0 |
| | 替换 25% | 36,178 | 826 | **0** | 4,564 | 31,481 | 0 | **4,910** |
| 百万域名 | 初始 | 11,759 | 1,104 | **0** | 903 | 10,856 | 0 | 537 |
| | 插入 25% | 76,963 | 8,836 | **0** | 52,688 | 24,275 | 0 | 593 |
| | 替换 25% | 39,817 | 1,732 | **256** | 2,468 | 36,952 | 0 | **4,640** |

**两个结论：**

1. **合法迁回在 12 个格子里 11 个为 0**，最好的一个也只有 **0.6%**（百万域名／替换 25%：256 / 39,817）。**卡住的主要是字节，不是槽位**——初始状态三个数据**全部 100% 卡字节**（751/751、4,901/4,901、10,856+903）。
2. **粗判据会大幅高估。** 现有的 `group_has_room(g, len)` 问的是"**组里有任何一个子块放得下吗**"；替换 25% 时它说"能"的记录有 **1,089 / 4,910 / 4,640** 条，而按键序的合法数是 **0 / 0 / 256**。**"整个组还有空闲空间"确实不等于"这个键能够放进去"**——这正是审阅预先指出的那一点，现在有了数量。

3. **"有溢出记录的组里，几乎每个组都有空槽＋空字节"——但合法迁回仍是 0。** 这把上一条钉死到子块粒度：

| 数据 | 状态 | 有溢出的组 | 其中**同时有空槽和空字节** | **合法迁回** |
|---|---|---:|---:|---:|
| 混合字符串 | 初始 | 155 | **152** | **0** |
| 百万域名 | 初始 | 1,104 | **982** | **0** |
| 百万域名 | 替换 25% | 1,732 | **1,603** | **256** |

**组级的"有位置"在 90%+ 的组上都成立，却几乎从不转化成一个记录真的放得进去**——因为卡住它的是**那一个按键序选中的子块**。**组级判据在这个布局上基本没有分辨力。**

4. **空闲空间大多不在欠账的组里。** 没有溢出记录的组手里握着大量空闲后缀字节：

| 数据 | 状态 | 无溢出组中的空闲字节 | 占主块空闲的比例 |
|---|---|---:|---:|
| 混合字符串 | 初始 | 7.02 MB | ≈99% |
| 重复前缀 | 初始 | 6.26 MB | ≈98% |
| 百万域名 | 初始 | 12.51 MB | ≈99.6% |

**"总空闲很多"几乎全部来自不需要它的组。** 按审阅 §2.3 的第四问——**空闲是否来自其他逻辑组**：**是**。因此首版**组内**维护**不能**动用这部分空间，把它算进可实现收益就是虚报。

### 3.1 这个 `0／0／256` 界定的是什么（**必须与数字一起读**）

**它是压缩前试放，不是压缩后试放。** 采用的试放算法是**当前布局的既有判据**，不是任何一种重排：

1. 用**已有的边界目录 `locate_subblock`**（M1 不变量）取出该键顺序上唯一允许的子块；
2. 要求该子块**同时**满足 `count < slots_of(g)`（有空槽）**且** `len ≤ bottom − start_of(g)`（有足够后缀字节）；
3. 不驱逐任何原主块记录，不做跨子块重划，不清垃圾。

**因此这个数字界定的是"当前算法在现有布局上的机会"**：

- **不能当作所有重排方法的上限**——压缩后再试放，第 2 步的字节条件会放宽（垃圾被回收），机会可能多于 256；
- **也不能当作迁回机制的总收益**——它只数了"结构上放得进去"，**没有计入迁移的时间、峰值空间与目录维护成本**。

**压缩后的试放留给 E26**（按审阅 E26 的判据：在**发生容量压力的子块**里，清掉垃圾之后能否让原本失败的插入成功）。

### 4.1 E25：分离验证"快速定位"与"消除重复查找"

**E25 只做两项改动，并把两者的收益分开测。** 变体（若最新版已实现某项，删除对应变体，不重复开发）：

| 变体 | 改动 | 要回答的问题 |
|---|---|---|
| **V0** | 冻结 R1 | 当前基线 |
| **V1** | 更新、删除复用已有的高效定位：标签过滤、SIMD、溢出策略 | 写路径缺少搜索优化，究竟损失多少 |
| **V2** | 在 V1 之上，插入／`upsert` 复用**本次定位已经产生**的组号、标签和判重结果 | 重复定位又损失多少 |

另保留 ART 对照。正常路径的目标：

- **已存在键的 `upsert`**：一次定位后直接改值；
- **不存在键的 `upsert`**：一次判重后继续放置，复用已经得到的信息；
- **压缩后可以重新求物理插入位置**；**前缀或模型变化后可以重新预测**——这些必要工作**不能为了满足"一次"而省掉**。

**定位结果仅在本次操作内有效**；压缩、描述符移动、容器扩容后，旧指针与旧槽号必须失效。

**诊断计数按四类记录**（并入 E25 的**独立诊断构建**，与正式计时分开）：

| 类别 | 记录内容 |
|---|---|
| 定位 | 路由、预测、指纹、**查重次数**，子块访问，完整比较及比较字节 |
| 删除 | 移动条目、实际复制字节、分配与释放次数 |
| 插入 | 槽位不足／字节不足／键序约束等失败原因，压缩尝试与成功次数 |
| 完整操作 | 干净构建中的 update、insert、替换周期耗时 |

**这些计数正是 §1.1b 缺的那一项**：`upsert` 重复查找的直接证据是"同一次普通 `upsert` 中实际执行了多少次查重、外层定位、模型预测和指纹计算"，本轮没有，E25 补。

**检查点**：`0%／5%／10%／25%` 沿同一负载采集，**插入与替换各一条**；**只改值继续作为控制组**。长期替换（50%／100%／200%）留到 E26。

**本轮先回答完整操作有没有变快**，不把"比较量降低几万倍"写成相应的加速比。

### 4.2 E26：方向**尚未确定**

**排除迁回，不等于已经证明压缩划算。** 本轮支持的是"迁回不是首选"，**不是**"压缩是首选"。压缩的判据要更具体：

> **在发生容量压力的子块里，清除垃圾之后，是否能让原本失败的插入成功，或减少后续溢出和重复整理？**

本轮的数据**还没有回答这一问**——它只给出了全局垃圾量（0.65–2.36 MB），**没有按子块的压力状态拆开**，也没有验证垃圾是否真的妨碍了写入。按 §2.3，**垃圾主要也在不缺空间的组里**的话，这条线就应当暂停。

**E25 顺手记录三件事**（不额外开轮）：

1. 现有 `compact` **在什么条件下触发**，是否反复无收益地执行；
2. **有容量压力的子块内**究竟有多少垃圾字节——**不是全索引垃圾总量**；
3. **压缩后可成功放入的记录数**，以及为此需要**复制多少字节**。

**如果压力子块确有大量可回收垃圾，E26 才做压缩策略；否则暂停这条线。** 并且要记住：**压缩不会减少已经分配的主块字节**，它的价值必须体现在**可用容量或后续操作成本**上。

**溢出容器收缩**（元素余量 22%–30%）优先级更低——它是保留容量问题，不是"记录放不下"问题。

### 4.3 对照判据（本轮数据支持到哪一步）

| 观察到的主要问题 | 本轮数据支持吗 |
|---|---|
| 更新/删除绕过了已有快速查找 | **支持**：计数一致（§1.1），且与负载状态无关 |
| 插入重复定位 | **未证**：缺调用计数，并入 E25 |
| 主块存在合法空位，但记录仍在溢出区 → **迁回** | **不支持**：合法迁回 11/12 格为 0，最好 0.6%（且为**压缩前**试放） |
| 主块垃圾很多，整理后才能容纳记录 → **压缩** | **未证**：垃圾确实存在，但**是否妨碍写入未测**，E26 决定 |
| 溢出记录已减少，但容器容量仍然很大 → **收缩容器** | 支持但优先级最低 |
| 只是空闲空间较多，短期还会再插入 | 部分：空闲后缀字节多，但那是**预算内的**空闲，不是垃圾 |

## 6. 适用边界

1. **不测时间。** 本轮的"贵不贵"全部由**计数**回答；**计数下降不自动等于性能提升**，那要 E25 在同进程 A/B 里测。
2. **只测单线程、静态状态**；并发、游标复用、反向扫描未测。
3. **状态是四个，不是方案的 0/5/10/25% 检查点。** 本轮取 `初始／只改值／插入 25%／替换 25%`；**方案 §2.2 要求的四个百分比检查点未逐点采集**，**长期替换（50%／100%／200%）未测**——那属于 E26 的评估计划。
4. **垃圾的定义限于主块后缀区**（已占用区域内无活跃条目引用的字节）；溢出记录的字符串分配、容器元素数组**另列**，不与它相加。**账本恒等式只覆盖主块**（块头＋描述符＋后缀区＝blocks），未用槽位与后缀区内的三类字节都只计一次。
5. **RSS 与索引自身是不同口径**，本轮两者不互相印证也不相加；RSS 里包含参考表、键向量等**不属于索引**的常驻对象，因此**不能用它评估索引的空间**。
6. **回收机会是结构可行性，不是收益预期**：它只回答"按槽位、字节、键序能不能放进去"，**没有**计入迁移本身的时间、峰值空间与目录维护成本。
7. **探测表是约 4,000 个存在键 + 4,096 个合成缺失键**；不是全键扫描，代表性有限。**溢出命中的样本很小**（混合 24、重复前缀 139、百万域名 195），那两行的结论比主块命中那行弱。
8. 继承门通过**不等于**任意输入正确；**本环境仍无 sanitizer**。
