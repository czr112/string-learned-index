# E14 结果：构建成本分解

日期：2026-09-16。目录：`validation_e14_20260916`（继承 E13）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**这一轮不改任何结构、不做任何优化、不报任何加速。** 它只回答一个问题：**S 的构建时间花在哪里。**

E12 测到 S 建索引 138–182 ms、ART 只要 47–94 ms；E13 把查询侧的故事讲完了。构建侧此前只有总数，没有构成。本轮补上构成。

> **2026-09-16 追加（E15 之后，原文未删改）**
>
> E15 实现了本轮指出的结构性改造并实测了它。结果见 E15 §2.1：**本轮 §3 的「做完不进入最终结构的工作 55.6%–66.3%」应读作阶段成本估算，而不是任何意义上的界**；真正可移除的量是 `bulk_load` 本身，因为一遍构建**仍然要做同一次区域切片**——`region_all` 是被**替换**而不是被省掉。
>
> 另一个措辞更正：**E12／E13 所报的 `build_ms` 只覆盖最终索引构建阶段**，不含探针、需求统计与容量规划。本轮 §4 首次给出完整流程口径。E12／E13 目录内已加更正说明。
>
> 本轮的分解、阶段占比与"放置是主导项"的结论**均不受影响**。

## 0. 结论摘要

| 问题 | 答案 |
|---|---|
| 构建时间主要花在哪个阶段？ | **初始放置**（`place`），占 Region 构造 45%–66% |
| 其次呢？ | **存储与块头/槽初始化**（`storage`，11%–35%）、**需求统计**（`demand_pass`，11%–17%）、**模型训练**（`model`，6%–18%） |
| 目录生成贵吗？ | **不贵**：0.5%–3% |
| 布局推导（容量表/偏移表）贵吗？ | **不贵**：≤0.5% |
| **S 的计入构建里有多少不进入最终结构？** | **55.6%–66.3%**（阶段成本估算，不是界——见 §3） |
| 整条构建流水线相对 ART 是多少？ | **2.58×–6.15×**（E12 按只含构建阶段的口径报的是 1.87×–4.36×） |

**两句话**：

1. **成本是分散的，但放置是主导项**——没有哪一处是"一个坏循环"，`place` 一个人吃掉一半，`storage` 与需求统计各占一至两成。
2. **更大的问题在结构上，不在常数上**：S 的计入口径里**有一大半工作不进入最终结构**——先按默认容量建一遍完整索引，再把它整段替换掉。

## 1. 方法

### 1.1 两个目标，同一份源码

`bench_e14.cpp` 编成两个可执行文件：

| 目标 | 编译参数 | 用途 |
|---|---|---|
| `bench_e14` | 无 | 干净的阶段计时 |
| `bench_e14_phase` | `-DE14_PHASE` | 同样的阶段计时，**外加** `index.hpp` 里 Region 构造函数的阶段计数器 |

`index.hpp` 的插桩全部包在 `#ifdef E14_PHASE` 里，**不带宏时完全编译掉**。

### 1.2 插桩是惰性的——三重证据

这不是"应该没问题"，是**被验证过的**：

1. **目标文件逐字节相同**：把 E13 与 E14 的 `index.hpp` 各编成一个 TU（不带 `-DE14_PHASE`），两个 `.o` 的 SHA-256 一致（`16091aaece0fc877…`）。
2. **四个继承门输出与 E12 逐字相同**：`check`／`check_e8_hetero`／`check_e9_multiblock`／`check_e11_locate` 在 E14 上重建重跑，与 E12 的日志逐文件 `diff` 无差异。
3. **布局摘要一致**：两个目标各自对每个结构算一个**规范布局串行化的 SHA-256**（覆盖分区、区域前缀、三张容量表、派生的子块结构、边界目录、以及按扫描序的全部 `(key,value)`）。**30 条实测记录里，6 个 (数据, 结构) 组合的摘要各只有 1 个取值**——跨进程、跨两个目标全部相同。

哈希函数自带 FIPS 自检（`SHA-256("abc")` 的期望值），不符即抛错——否则"摘要相同"可能是哈希坏了而不是布局相同。

**因此"保持模型输出不变"这一条本轮是满足的**：不但没改模型，连非模型的部分都没有可观测变化。

### 1.3 阶段划分

口径沿用 E12/E13：一个结构的 `build_ms` = `bulk_load(keys)` + 每个区域一次 `rebuild_with_caps`。本轮称为 **`s_counted`**，**它必须与 E12 的数字对得上**。在此之上，把同一条流水线真正跑过的、此前没被命名的阶段也单独计时：

| 阶段 | 是什么 |
|---|---|
| `probe` | 为拿分组统计而建的那个完整索引 |
| `stats` | `group_stats()` 逐区域统计 |
| `alloc` | `demand_single` + `demand_strict` 两个容量分配器 |
| `d_bulk` / `s_bulk` | 计入口径里那次 `bulk_load` |
| `d_rebuild` / `s_rebuild` | 计入口径里那次逐区域 `rebuild_with_caps` |
| `pipeline_total` | `probe`+`stats`+`alloc`+`s_counted`，即"从有序键向量得到一个 S 索引"的真实代价 |
| `art` | 原生 libart 构建 |

`Region` 构造函数的阶段计数器（仅在 `bench_e14_phase` 里有效）：`prefix`／`model`／`suffix_scan`／`demand_pass`／`layout`／`storage`／`place`／`dir`。

### 1.4 协议

- 数据集与规模**沿用 E13 不改**：`mixed` 131,072 键、`skew` 131,072 键、`tranco` 262,144 键（Tranco 固定快照 `…/validation_e5_20260913/data/tranco_XN6XN.csv`）。
- **5 个独立进程**，每个进程先跑一次小数据集热身（按 run tag 剔除——刚构建的二进制第一次执行要付自己的页入成本，那不属于被测量的构建），然后每个数据集连跑两个目标。
- **两个目标的先后顺序在偶数进程上翻转**，避免"哪个二进制先跑"与目标本身完全混淆。
- 表中每个格子是**跨进程的中位数**，不跨进程池化原始值。

## 3. 计入口径里的工作，有一大半不进入最终结构

这是本轮最重要的发现，而且它是**结构性的，不是调优问题**。

### 3.1 事实

S 的计入口径是两步：

```cpp
s->bulk_load(keys);                                        // ① 完整建一遍索引
for (i ...) s->rebuild_with_caps(i, s->region(i).all(), …); // ② 逐区域整段替换掉
```

`Index::rebuild_with_caps` 的实现在 `index.hpp`：

```cpp
nodes_[i].region = std::make_unique<Region>(data, config_, sg, bb, nb_cap);
```

**它构造一个全新的 `Region`**——重新算前缀、重新训练模型、重新统计需求、重新放置每一条记录。① 建出来的那些 `Region` 对象，除了在被替换前调一次 `all()`，**没有任何东西被复用**。

而 `all()` 返回的是该区域那一段**已排序的键**，也就是输入 `keys` 里的一段连续区间——**`keys` 本身就在手上**。

### 3.2 量有多大

`E14_TABLES.md` §3（跨进程中位数）：

| 占 `s_counted` 的比例 | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| `s_bulk`（第一遍完整构建） | 57.1% | 58.5% | 47.7% |
| `region_all`（被替换掉的那个切片） | 9.0% | 8.3% | 6.7% |
| **合计：不进入最终结构的工作（阶段成本估算）** | **66.3%** | **65.7%** | **55.6%** |

即：**S 的计入构建时间里有 55%–66% 没有进入最终结构。**

**这三行是"时间去了哪"的分解，不是"去掉能省多少"的估计，也不是任何意义上的界。** 去掉一遍的路径与它相比，在切片、对象替换与销毁、缓存与分配器状态上都不同，成本不能简单相减。E15 实现后的实测口径修正见 §3.4。

### 3.3 同样的问题也吃掉了 `probe`

`probe` 是第三个完整构建（44–75 ms），只为拿 `group_stats()`。它不在 `s_counted` 里，所以在 E12 的对照中**从未被计入**——但它在 `pipeline_total` 里。

### 3.4 E15 的实测修正（2026-09-16 追加）

E15 实现了这里的改造并做了同进程 A/B。结论：**可移除的量应记作 `bulk_load` 本身，而不是 `s_bulk + region_all`。**

原因是一遍构建**仍然要把每个区域的键物化成一个 `vector<Pair>`**——同一次切片。`Region::all` 是被新路径自己的切片**替换**掉的，不是被省掉的。实测降幅 54.0%–56.2%，与"`bulk_load` 占 `s_counted` 的 46%–54%"更吻合，而不是 55.6%–66.3%。

§3.1 与 §3.2 的事实陈述**全部成立**；收窄的只是 §3.2 表尾那行合计的**读法**。细节与两种估计量见 E15 §2.1 与 `E15_TABLES.md` §3b。

## 4. 整条流水线相对 ART

E12 拿 `s_counted` 与 ART 比；但 ART 一次调用就建完，S 还要探针、统计、分配器。同一比较放到完整流水线上：

| | 混合字符串 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| S（E12/E13 口径） | 116.42 | 136.60 | 192.44 |
| **S（完整流水线）** | **164.03** | **195.64** | **272.68** |
| ART | 50.10 | 75.69 | 44.00 |
| **完整流水线 ÷ ART** | **3.49×** | **2.58×** | **6.15×** |
| `s_counted` ÷ ART（E12 的比值） | 2.49× | 1.87× | 4.36× |

**按完整流水线口径，S 建索引是 ART 的 2.6–6.2 倍，比 E12 报告的 1.9–4.4 倍更差。** 百万域名上 6.15× 尤其突出：那里的 `probe`（74.7 ms）本身就比 ART 建整棵树（44.0 ms）还慢。

统计与容量规划**不是**瓶颈：两者合计 3.3–5.2 ms，占完整流水线约 1.6%–2.0%。

## 5. Region 构造函数的阶段分解

完整表见 `E14_TABLES.md` §5。以 S 的两个阶段为例（占 `ctor_total` 的比例，跨进程中位数）：

| 阶段 | `ph_s_bulk` 混合／重复／域名 | `ph_s_rebuild` 混合／重复／域名 |
|---|---:|---:|
| `place` 初始放置 | 45.2%／45.4%／55.9% | 53.7%／58.2%／65.8% |
| `storage` 存储与块头/槽初始化 | 30.7%／34.9%／20.6% | 18.0%／14.6%／11.2% |
| `demand_pass` 需求统计 | 11.5%／11.4%／10.7% | 17.4%／17.4%／11.2% |
| `model` 模型训练 | 8.7%／6.2%／9.8% | 9.8%／8.5%／10.4% |
| `dir` 目录生成 | 3.1%／1.8%／1.5% | 0.6%／0.8%／0.5% |
| `layout` 容量表与偏移表推导 | 0.4%／0.3%／0.3% | 0.5%／0.4%／0.2% |
| `prefix` 公共前缀 | ≈0% | ≈0% |
| `suffix_scan` 后缀字节合计 | ≈0.2% | ≈0.2% |

三点：

1. **`place` 是主导项**，且在较深的布局上更主导（百万域名 66%）。
2. **`demand_pass` 只在 `multiblock` 模式下非零**——`ph_probe`／`ph_d_bulk`／`ph_d_rebuild` 里它是 0.00，那些阶段走的是单块默认路径。这正是 E9 加入的那一遍。
3. **`dir` 与 `layout` 都不值得优化**：合计不到 4%。E13 已经确认边界目录在查询侧是可开关组件；这里确认它在构建侧也不是成本来源。

### 5.1 账是平的

八个阶段是 `ctor_total` 这一个区间的**不相交**划分，所以它们必须加得起来：

| 阶段 | 混合 | 重复前缀 | 百万域名 |
|---|---:|---:|---:|
| `ph_s_bulk` 八项和 ÷ `ctor_total` | 0.9995 | 0.9996 | 0.9994 |
| `ph_s_rebuild` 八项和 ÷ `ctor_total` | 0.9993 | 0.9994 | 0.9993 |

其余三个阶段同样在 0.9991–0.9994。八项是 `ctor_total` 的**不相交**划分，所以和必然略**低于**它；**这 0.04%–0.09% 的差额本轮没有归因**——预期是计时调用本身（每次构造约 8 次，每次约 10 ns），但本轮没有测量它，因此它只是预期而不是结果。差额小到不影响任何结论。

> 实现上踩过一次：`layout` 最初被写成**跨越** `demand_pass` 的一个区间，于是需求统计被计了两次，八项之和比 `ctor_total` 高出 16%。改成前后两段累加后才闭合。**如果没做这个闭合检查，这张表会把最大的一项读成两份。**

## 6. 怎么读这组数字

1. **这不是"某处有个坏循环"。** `place` 占一半，`storage`、`demand_pass`、`model` 各占一到三成，没有单一热点能靠一处改动拿掉。
2. **真正的杠杆是结构，不是常数。** 55%–66% 的计入时间花在**不进入最终结构**的工作上。这不需要优化任何算法，只需要不去做它。
3. **但那一半也确实付了钱。** `s_counted` 的绝对值与 E12 对得上，说明那两遍构建都真实发生了。
4. **`dir` 与 `layout` 可以排除在优化目标之外**（合计 <4%）。
5. **统计与容量规划也可以排除**（合计 3.3–5.2 ms，占完整流水线约 2%）。

---

## 7. 适用边界

1. **本轮不做优化、不报加速。** 报告里的比例是"当前实现花在哪"，不是"改完能快多少"。任何收益都必须由下一轮实现后实测。
2. **§3 的 55.6%–66.3% 是阶段成本估算，不是界。** 它说明时间去了哪，不构成"去掉就能省这么多"的承诺：两条路径在切片、对象替换与销毁、缓存与分配器状态上都不同，成本不能简单相减。E15 实测后的口径修正是 `bulk_load` 本身。
3. **§5.1 的闭合差额未归因**：八项和 ÷ `ctor_total` 落在 0.9991–0.9996，说明分段基本完整；差额预期来自计时调用，**但本轮没有测量**。
4. **`probe` 的可消除性本轮未验证**：它只为 `group_stats()` 服务，但统计是否能在不完整构建的前提下算出，本轮没有考察。（E16 的方向；E15 已确认分配器只读四个每组的量。）
5. **绝对耗时跨进程漂移约 10%**，个别阶段更大；结论建立在跨进程中位数上，不建立在单次测量上。
6. **与 E12 只可比量级，不可逐位比对**：E12 的构建时间是单次测量，本轮是 5 进程中位数，且机器状态不同。表 2 已列出差额。
7. **E12／E13 的 `build_ms` 只覆盖最终索引构建阶段**，不含探针与容量规划；本轮 §4 才是完整流程口径。
8. **不与 E4 拼接**（另一台机器、另一套 `-march`）。
9. **无 sanitizer**（工具链与 WSL 侧均不可用）。
10. **只测构建，不测查询。** 查询侧的数字以 E12／E13 为准，本轮没有重跑计时。
11. **ART 只接受无 NUL 的 ASCII 键**（E12 已写明该守卫是承重的），只在 ASCII 子集上被评估。
