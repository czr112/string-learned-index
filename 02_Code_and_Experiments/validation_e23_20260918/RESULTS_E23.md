# E23 结果：冻结版本的范围扫描

日期：2026-09-18。目录：`validation_e23_20260918`（继承 E22）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**功能评估的最后一块。** 语义固定且各方共享：

> **从第一个 `key >= start` 的记录开始，按键序返回至多 `n` 条，形式为完整键值对。**

两个排名方案产生**相同的结果形式**——都复制键到 `std::vector<Pair>`。返回视图而不复制的方案衡量的是另一件事。

## 0. 结论摘要

| 数据 | 状态 | n=16 | n=128 | n=1024 |
|---|---|---:|---:|---:|
| 混合字符串 | 初始 | **1.28×** | **1.83×** | **1.68×** |
| | 插入 25% | 1.83× | 1.78× | 1.76× |
| | 替换 25% | 1.62× | 1.91× | 1.72× |
| 重复前缀 | 初始 | 1.49× | 1.68× | 1.51× |
| | 插入 25% | 1.69× | 1.87× | 1.56× |
| | 替换 25% | 1.98× | 1.84× | 1.57× |
| 百万域名 | 初始 | 1.68× | 1.96× | **2.21×** |
| | 插入 25% | 1.56× | 2.00× | **2.19×** |
| | 替换 25% | 1.71× | 1.80× | **2.34×** |

（表中是 **原型 ÷ 全局有序数组**，>1 表示原型更慢。）

**一句话：原型相对有序数组的点查优势没有延续到范围扫描——在已测的状态与扫描长度下，原型扫描均慢于全局有序数组（1.28×–2.34×），说明当前结构更偏向点查优化；扫描开销的具体来源仍待分解。** E21 里它比同一个基线快 1.5×–2.4×。

**这是取舍的结果，不是异常。** 点查主要受益于快速缩小候选范围；范围扫描则要连续输出多条记录——有序数组天然适合顺序访问，而原型可能还要跨组、跨子块、归并溢出记录并恢复完整键。**这些开销来源都尚未被本轮逐项测量**，上面只是候选解释。**也不能据此推导所有范围查询场景都会如此**：本轮只覆盖点起点、单次、单线程扫描。

**另三件事**：

- **正确性**：每一行 4,096 次扫描**全部**与参考表**逐条全等**比对（不是校验和）。**替换状态在混合字符串与重复前缀上确实含中间空子块**（6 个／55 个）——E9 扫描缺陷的那个形状被覆盖到；**百万域名上没有生成**，故这条覆盖是两张数据上成立。
- **方向结论在噪声之上**：三个进程**分开来看**，**81 个比值没有一个低于 1.0**（最小 1.165）。"扫描更慢"是每个独立进程都复现的；而**格子之间比值的差别落在噪声里，不作为结论**（§2.1）。
- **ART 不进排名**：libart 没有 seek-to-key 迭代器，全树遍历适配器慢 **40×–3,823×**，随键数而非 `n` 增长。**那是适配器的代价，不是 ART 范围定位能力的结论。**

## 1. 正确性

**每一次扫描都在计时区之外与参考表逐条全等比对**（不是校验和）；计时那一趟保留校验和，不符即抛异常终止。因此一条记录存在，就意味着那一行 4,096 次扫描全部通过。

覆盖的情形：跨区域边界、主块与溢出记录的**有序归并**、以及**起点落在两个键之间**（五分之一的开点是任何桶里都不存在的合成键）。

### 1.1 中间空子块

E9 的扫描缺陷是：中间出现一个**空子块**时，归并循环会 `break`，**该组后面所有子块的记录被静默丢弃**。修在 E11，E11 自己的门覆盖它。

本轮把那个形状**事实地纳入被测量的状态**：

| 数据 | 状态 | 多块组数 | **中间空子块** | 最大子块数 |
|---|---|---:|---:|---:|
| 混合字符串 | `initial` | 223 | 0 | 30 |
| | `insert25` | 223 | 0 | 30 |
| | `replace25` | 223 | **6** | 30 |
| 重复前缀 | `initial` | 582 | 0 | 22 |
| | `insert25` | 582 | 0 | 22 |
| | `replace25` | 582 | **55** | 22 |
| 百万域名 | `initial` | 1,413 | 0 | 15 |
| | `insert25` | 1,413 | 0 | 15 |
| | `replace25` | 1,413 | **0** | 15 |

**替换状态在两张数据上生成了中间空子块，因此 E9 曾经走坏的那条扫描路径在本轮被实际执行——而它上面每一次扫描都验证通过。** 百万域名上**没有**生成（它的多块组更短、最大 15 个子块，替换没能打出中间空洞）。**因此这条覆盖是"混合字符串与重复前缀上成立"，不是"三个数据上都成立"。**

**这不是对 E9 缺陷的重新测试**（修复在 E11，E11 的门负责那件事），而是"**现在被测量的扫描，是在那个形状上被测量的**"这一陈述。

### 1.2 不足 `n` 条不能被当成完整扫描

五分之一的开点靠近键空间末尾，因此返回不足 `n` 条。这些运行**被单独计数并报告**（例如混合字符串 `initial`／`n=16`：6 次；`n=1024`：436 次），并给出**最小返回条数**（3）。

## 2. 扫描成本

完整表见 `E23_TABLES.md` §2。中位数（ns/每次扫描）：

| 数据 | 状态 | n | 原型 | 有序数组 | 比值 |
|---|---|---:|---:|---:|---:|
| 混合字符串 | 初始 | 16 | 1,847 | 1,442 | 1.28× |
| | 初始 | 1024 | 67,187 | 40,022 | 1.68× |
| 重复前缀 | 替换 25% | 16 | 2,835 | 1,430 | **1.98×** |
| 百万域名 | 替换 25% | 1024 | 69,733 | 29,785 | **2.34×** |

**原型在 27 个格子上全部更慢**，比值区间 **1.28×–2.34×**。（按数据集看的区间——百万域名 1.56×–2.34×、混合字符串 1.28×–1.91×——**仅作描述**，格子之间的差别落在噪声里，见 §2.1。）

### 2.1 噪声地板，以及方向结论为什么在它之上

比值的**跨进程离散**（每个格子 3 个进程的比值 max ÷ min）：**中位 1.11，最坏格子 1.56**（绝对耗时的跨进程 max ÷ min：中位 1.07／1.09，最坏 1.45／1.51）。**因此单个格子的具体比值只能读到约 10% 的精度，最坏的格子上远不止。**

**但方向结论不落在噪声地板里**：把三个进程**分开来看**，**27 个格子 × 3 个进程 = 81 个比值，没有一个低于 1.0，最小的是 1.165**。所以"原型在扫描上更慢"是**每一个独立进程都复现**的，不是靠取中位数才成立的。

**相反地，格子之间比值的差别（例如 1.28× 与 1.68×）落在噪声里，不作为结论。**

**方向与点查相反**：E21 里原型比同一个有序数组基线快 1.5×–2.4×，扫描上则落后。**这是同一个结构在不同访问模式下的取舍，不是异常**；扫描开销的具体来源仍待分解（§5）。

**负载状态的影响很小**：三个状态之间的比值变动在 1.28–1.98× 里，没有系统性的恶化方向。**E22 观察到的溢出增长没有把扫描成本推高到基线之上。**

## 3. ART 全树遍历诊断——**不进排名**

**这不是对 ART 范围定位能力的测量。** libart 只提供 `art_iter`（全树遍历）与 `art_iter_prefix`，没有 seek-to-key 的接口，所以这个适配器**从树头开始遍历**，收集到 `n` 条 `>= start` 的记录后停止——**起点之前的一切都被访问并丢弃**。

| 数据 | n | 诊断（ns） | 原型（ns） | 诊断 ÷ 原型 |
|---|---:|---:|---:|---:|
| 混合字符串 | 16 | 2,815,944 | 2,143 | **1,314×** |
| | 1024 | 2,944,424 | 73,506 | **40×** |
| 重复前缀 | 16 | 3,412,723 | 2,761 | **1,236×** |
| 百万域名 | 16 | 6,583,549 | 1,722 | **3,823×** |
| | 1024 | 6,885,802 | 65,649 | **105×** |

**慢两到三个数量级，且随键数而非 `n` 增长。** 成熟的 ART 范围扫描实现不会是这个样子。

**该诊断按每 64 个起点采样一次：每个格子只有 64 次采样**（4,096 ÷ 64），**不是 4,096 次**——§1 的"每格 4,096 次扫描"指的是两个排名方案，**不覆盖 ART**。按每次约 3 ms，跑满全部起点会让它主导整轮墙钟时间两个数量级（实测 138 s/数据集 vs 13 s）。采样只改变精度，不改变量级——**而量级就是这个数据唯一的用途**。采样结果同样在计时区外与参考表逐条核对。

## 4. 适用边界

1. **ART 不进排名**（§3）。表中它的数字**只是适配器的成本**，不能读成 ART 的范围扫描能力。
2. **只测点起点、单次扫描、单线程**；并发扫描、游标复用、反向扫描未测。
3. **两个排名方案都返回复制后的完整键值对**，因此字符串复制成本在两侧都存在。
4. **状态只取三个**（初始／插入 25%／替换 25%）；只改值已由 E22 证明结构不变，本轮未重复。
5. **不足 `n` 条的扫描已单独计数**（§1.2），不会与完整扫描混同。
6. **样本量**：两个排名方案每个格子 **4,096 次扫描 × 3 进程**，扫描成本的中位数跨进程取；**ART 诊断每格只有 64 次采样**（§3）。**两者的样本量不可互相读出。**
7. **不与 E4 拼接**（另一台机器、另一套 `-march`）；**无 sanitizer**。
8. **跨进程离散已实测**（§2.1）：绝对耗时 max ÷ min 中位 **1.07–1.09**、最坏 **1.45–1.51**；比值 max ÷ min 中位 **1.11**、最坏 **1.56**。**结论建立在比值上，且方向结论在每一个独立进程里都复现。**

## 5. 下一步

按审阅给的顺序，**功能评估到此完整**：构建（已冻结）、点查（E21）、更新负载（E22）、范围扫描（本轮）。**接下来定为：更新项目总览 → 完成空间诊断 → 只选一个维护机制做对照。暂不新增优化机制。**

**动态优化的下一候选，两个问题要分开**（审阅指出，不能混为"溢出只增不减"）：

| 问题 | 问的是 |
|---|---|
| **活记录仍在溢出区** | 主块删除后腾出了容量，**是否能把溢出记录迁回主块** |
| **记录已删除但内存仍保留** | 后缀垃圾、溢出向量容量、字符串分配**是否被回收** |

**溢出记录本身可以被删除，但容器容量未必随之缩小；总空间增长也未必全部来自未回收的垃圾。**

**空间分解分两层记录。四项不是完整且天然互斥的分解，不能直接相加当作总空间**——它们可能遗漏元数据，也可能把溢出中的活跃后缀重复计算：

- **主块内部**：块头与描述符区、活跃后缀、删除留下的垃圾、尚未使用的后缀空间；
- **溢出部分**：活跃记录数量与后缀长度、记录容器容量、字符串容量余量；
- **另列**：容量表、模型、外层对象。

**沿用当前空间记账口径，并注明是否包含字符串内联存储与分配器开销**，避免重复计费。

**用已有的替换检查点决定改哪个机制**：

| 观察到的主要问题 | 优先候选 |
|---|---|
| 主块存在可用容量，仍有适合迁入的溢出记录 | **迁回主块** |
| 主块垃圾很多，整理后才能容纳记录 | **压缩主块** |
| 溢出记录已减少，但容器容量仍然很大 | **收缩或重建溢出容器** |
| 只是分配的空闲空间较多，短期还会再插入 | **先保留**，评估收缩后的再次扩容成本 |

**"能否迁回"必须按记录所属组、子块键序及实际容量判断，不能只看全局空闲字节总量。**

**本轮未测**：并发扫描、游标复用、反向扫描。
