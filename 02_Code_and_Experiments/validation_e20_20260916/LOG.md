## E20-4 一个被追到底的数字（2026-09-17）

诊断数据显示 **R1 与 R2 的分配次数完全相同**，这与"R2 每区域多一个 id 数组"矛盾。没有把它当成噪声放过，而是写了 `probe_alloc.cpp` 单独测两个入口：**473 → 537 次（+64 = 每区域一次），id 总数 131,072 = 每键一个**——说明统计阶段确实分配了它们。

于是回到 bench 找那 64 次差在哪里，答案是 **R1 的构造里也分配**：`Config::reuse_group_ids = true` 时构造函数会 `group_of.resize(sorted.size())`。所以

> **R2 是把 id 数组从构造阶段搬到统计阶段**：构造少 64 次、统计多 64 次，**净额为零，只有生存期变长**——这也正好解释了峰值为什么恰好增加「一个 `uint32`／键」。

这条写进了 `E20_TABLES.md` §4，并附上探针的数字。

## E20-7 冻结前修订：映射身份检查（审阅后，2026-09-17）

审阅指出守卫的**实质缺口**：本轮证明了"长度相同、逻辑组数不同"会被拒，但**"前缀相同、逻辑组数相同，而模型或输入不同"**这一类**会被放行**——构建按缓存组号放置、查询却按新模型预测，可能出错。

### 修法：不重新预测，给上下文加一个映射身份

映射 = （前缀，**训练后的模型表**，逻辑组数，路由模式）。四者相同，映射就按构造相同。因此 `RegionDemand` 增加 `model_digest`：对训练后的 `Model::cumulative`（16×258 个 `u32` ≈ 16.5 KiB／区域）连同 `kind`／`groups`／`canonical` 做一次 FNV 摘要。

**只在真的有预设传入时才计算**（`&&` 短路放在最后）——默认路径与 R1 路径一分不付。

**接口性质**：这是审阅列出的第二种做法（**可复用上下文，显式记录并校验身份**），不是第一种（内部上下文）。选前者是因为它的约束**可以被测试直接验证**。

### 新增的两组针对性反例

| 类别 | 构造方式 | 结果 |
|---|---|---|
| (ii) **模型不同** | 同一份键、同一前缀与组数，换模型类型（`Context16` ↔ `Unigram`；`derive_groups` 不依赖模型，所以组数天然相同） | **48/48 被拒** |
| (iii) **键集不同** | 另一份键集，**只改中间一段且保持每键长度**，因此首尾键不变（前缀不变）、后缀字节总数不变（组数不变） | **16/48 被拒**，其余 32 组被前缀/组数检查提前拦下 |

第 (ii) 类的设置本身也被断言（必须真的"形状相同、摘要不同"），**不让测试因为设置没做到而悄悄通过**。第 (iii) 类只有 16/48 真正触发新检查，**如实标注，不写成 48**。

## E20-8 三处表述修正（审阅指出，2026-09-17）

1. **降幅口径统一。** 先前写"7%–13%"，是把两种估计量混用了。现在**一律用配对比值 `1 − R2/R1`**（修订后 6.2%／9.6%／5.6%，即 **5.6%–9.6%**），并在表与正文中写明"两个耗时中位数直接相除会得到另一组数，两者不得混用"。
2. **ART 比值方向写反过。** "最终原型比 ART 慢 1.51／1.17／3.41 倍"对应的是 **`T_R2 ÷ T_ART`**（原型时间 ÷ ART 时间），**不是 `ART ÷ R2`**。表格行名已改为 `T_R2 / T_ART` 并注明"大于 1 表示原型更慢"。

## E20-10 冻结前修订 ②：键序列绑定（审阅后，2026-09-17）

审阅指出**更根本的缺口**：E20-7 的映射身份只证明了 $f_{\text{旧}} = f_{\text{新}}$，而缓存里存的是 $ids[i] = f_{\text{旧}}(keys_{\text{旧}}[i])$，构建需要的却是 $f_{\text{新}}(keys_{\text{新}}[i])$。

**模型表是数据的统计摘要——不同键集完全可能训练出同一张表**（即便哈希没有碰撞）。**同一个函数作用于不同键，结果可能不同。** 我此前的"不同键集"测试只能说明那些用例被拒了，**不能证明所有不同键集都会改变摘要**。

### 修法：把上下文绑定到键序列

按审阅给的主路径（**内部上下文**）实现两条绑定：

| 绑定 | 作用 | 成本 |
|---|---|---|
| **源数组身份**（地址 + 长度） | 上下文只能在产出它的那个键向量上被接受——把"同一条流水线内部使用"变成**可检查的前置条件** | O(1) |
| **键序列摘要**（每键一步 FNV，混入长度与首尾字节） | 捕获生成与消费之间的**原地编辑或重排**；**地址+长度单独挡不住这个** | 每键一次乘法 |

保留前缀 / 组数 / 模型摘要三项。容量表与物理子块数仍不参与校验。

**新增 `struct BuildContext`**（源地址、源长度、regions），`Index::demand_profile_ctx` 返回它，`bulk_load_with_plan` 消费它。

### 新增 case (iv)：**前三类都覆盖不到的那一个**

> **同一向量、原地交换两个中间键**：模型表不变（训练按多重集累加，**与顺序无关**）、前缀不变（首尾键未动）、组数不变（长度多重集未变），**只有键序列变了**。

**48/48 被拒**，且退回路径的结构与正确结构一致。测试本身还断言"设置必须真的做到映射不变、序列变"，**不让它因为设置没做到而悄悄通过**。

### 事故：护栏比它保护的对象还贵

第一版 `model_identity` 每个表项做 8 次混合 → 每区域 33k 次操作 → **约 3 ms／次构建（两遍）**——**这正好是 R2 全省下来的量**。改成**逐字节** FNV（每字节一次乘法）后降到约 0.6 ms。**护栏不能比它保护的对象还贵。**

> **建议冻结 R1 为默认路径；R2 连同映射身份与键序列绑定一并保留为可选路径，但不作为默认**，直到在安静机器上重测出稳定、可分离于机器噪声的净收益。
>
> **无论选哪条，护栏都要保留**——它是正确性修复，不是可选的优化。

## E20-12 安全结论的收紧（审阅指出，2026-09-17）

**可以保留的**：
* 已测配置下 R2 相对 R1 的完整构建耗时下降（本轮 4.3%–6.0%）；
* 同轮完整构建仍慢于 ART（`T_R2/T_ART` = 1.56／1.23／3.45）；
* 当前测试**未观察到**结构或查询结果差异。

**暂时不能写的**：**"可复用上下文已经完整保证映射对应正确"**。

理由：键序列摘要混入的是**长度与首尾字节**，理论上存在摘要相同而键不同的构造；**真正的保证来自"上下文只在其来源向量上被接受"这条接口约束**，加上"生成与消费之间不修改键"的纪律。若将来要在**不同构建**之间复用，需要另外校验完整的键序列身份，并把成本计入。

## E20-13 生命周期收紧与表述更正（审阅后，2026-09-17）

审阅指出**首尾字节摘要只是辅助检查，不是键序列身份**：

> `aaba` 与 `abba` —— 长度相同、首字节相同、尾字节相同。摘要在 FNV 混合**之前**就已经分不开。源地址与长度同样看不见原地修改。

**这不是"理论上的哈希碰撞"，是构造本身就不携带那个信息。** 所以**不再要求弱摘要承担它给不了的保证**。

### 修法：把正确性移到生命周期上

* 新增 `Index::bulk_load_reusing_ids(pairs, stats_cfg, plan_for)` —— **唯一文档化的用法**：统计、规划、构造在**一次调用**内完成，`ctx` 是普通局部变量，**不会逸出**，因此无法被存下来、复制出去、或对着另一份数据重放。
* 原来那个"调用方拿上下文再传给构造"的入口**取消**，改名为 `bulk_load_with_context` 并标注 **INTERNAL**，仅供验收门构造反例使用。
* `CapacityPlan` 由调用方通过 `plan_for` 回调提供，因此 `index.hpp` 不必依赖分配器。
* 四项检查（源身份 / 键摘要 / 前缀+组数 / 模型摘要）保留为**纵深防御**，不再是正确性的来源。

### 新增验收：**单次调用入口**

## E20-15 冻结收尾：R2 的两条接口约束（审阅后，2026-09-17）

审阅指出单次调用本身**不自动排除回调修改输入的可能**。两条约束落实如下：

1. **`bulk_load_with_context` 真正设为私有**。此前我只在注释里写了 "INTERNAL"——**注释不是约束**。现在它在一个 `private:` 区段内，加上 `friend struct IndexTestAccess;`；类之后定义 `IndexTestAccess::build_with_context`，**仅供验收门构造反例使用**。普通调用方**拿不到上下文**，这正是"靠生命周期保证"应有的形态。
   *（事故：访问器第一次被插到文件里**第一个** `} // namespace validation` 之后，那里 `Index` 还没声明 → 编译失败。移到最后一个。）*
2. **`plan_for` 的契约写明**，两条都由调用方承担、单次调用不自动强制：
   * **不得修改 `pairs`**，且直到本次调用返回前任何东西都不得修改它——组号是按那些键算出来的；键序列摘要是**辅助检查**，不能指望它发现；
   * **不得保留**交给它的统计或组号——它们只活到本次调用结束，保留它们正是这种形式要防止的"跨数据复用"。

**行为不变，重新构建并重跑**：`check_e20_r2` `passed`（48 组配置、48 单次调用核对、48+48+16+48 反例），四个 E13 门与 E12 **逐字相同**。

**冻结完成**。此后汇报以 R1 为主版本，R2 只出现在可选优化与限制部分。
