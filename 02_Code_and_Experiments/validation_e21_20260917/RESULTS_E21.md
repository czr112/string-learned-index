# E21 结果：冻结版本的完整点查对照

日期：2026-09-17。目录：`validation_e21_20260917`（继承 E20）。平台：WSL2 Ubuntu 24.04 + g++ 13.3.0，单核绑定。

**构建阶段已冻结（R1）。本轮换一个问题：冻结版本在查询上处在什么位置。**

四个方案同轮对照，数据、查询序列、叶配置、路由与溢出策略完全相同：

| 方案 | 是什么 |
|---|---|
| `sorted_array` | 全局有序数组，`std::lower_bound`，**不复制键** |
| `ART` | 原生 armong/libart |
| `S_original` | 两遍构建（`bulk_load` + `rebuild_with_caps`） |
| **`S_frozen`** | **冻结默认**：统计 → 规划 → 直接构造 + R1 |

### 三条结论

1. **相对简单方案的优势保持**：S_frozen 比全局有序数组快 **1.5×–2.4×**，每个数据、每个类别都成立。
2. **相对 ART 仍有差距，但只在"全部查询"这一类上可以直接引用**：耗时高 **24.2%／12.3%／48.8%**（见 §0 的总体列）。**分类列不是它的分解**（§1.1），不能用来解释差距来自哪里。
3. **构建改造没有移动查询成本**：S_frozen ÷ S_original 在 **±1.6%** 以内，九个格子全部。**本轮未观察到明显查询性能变化**——R1 优化的是构建，本来就不该让查询变快或变慢。

## 1. 口径澄清：三类是三种负载，不是分解

**审阅指出**：skew 上总体比 ART 慢，单独命中和未命中却都更快——这需要先澄清测量方式。核对结果如下。

### 1.1 代码：三类各跑一趟独立负载

```cpp
const std::vector<Class> classes{{"all", &all, ...}, {"hit", &hits, ...}, {"miss", &misses, ...}};
for (round) for (cls : classes) for (method) { /* time *cls.q from start to end */ }
```

`hits` 与 `misses` 是**从 `all` 里筛出来的两个独立查询向量**，各自从头到尾单独计时——**不是把混合那一趟切成两半**。所以三列回答的是"**在这类负载上 S 与 ART 相比如何**"，**不是"混合耗时去了哪里"**。

E13 已记录过同一现象（其 §4：`全部查询` 明显慢于 `(仅命中+仅未命中)/2`，因此三类之间不是分解关系）。**本轮报告起初没有把这条沿用过来，是我的疏漏。**

### 1.2 数据：混合负载确实不是两半的平均

| 数据 | 方案 | 全部 | 仅命中 | 仅未命中 | (命中+未命中)/2 | 全部 ÷ 它 |
|---|---|---:|---:|---:|---:|---:|
| 混合字符串 | ART | 321.4 | 259.5 | 235.8 | 247.6 | **1.298×** |
| | S_frozen | 404.7 | 341.0 | 255.5 | 298.2 | **1.357×** |
| 重复前缀 | ART | 489.0 | 442.6 | 403.4 | 423.0 | **1.156×** |
| | S_frozen | 550.3 | **432.3** | **387.0** | 409.7 | **1.343×** |
| 百万域名 | ART | 231.8 | 205.6 | 196.3 | 200.9 | **1.154×** |
| | S_frozen | 345.9 | 326.4 | 270.7 | 298.6 | **1.159×** |

### 1.3 skew 为什么能同时成立

**S 的混合惩罚比 ART 大。**（加权是**精确**的：`hit = (i % 2 == 0)`，每批恰好 50% 命中，运行日志也是 `hits=65536 misses=65536`。）

**"混合惩罚"是描述性指标，不是解释**——缓存状态、分支行为、工作集大小与执行顺序都可能参与，本轮没有把它们分开，**因此不归因于任何单一机制**。能说的只是：**把命中与未命中混在一起执行，对 S 的代价比对 ART 更大**，在重复前缀上最明显。

| 数据 | S 的混合惩罚 | ART 的混合惩罚 | 差 |
|---|---:|---:|---:|
| 混合字符串 | 1.357× | 1.298× | +0.059 |
| **重复前缀** | **1.343×** | **1.156×** | **+0.187** |
| 百万域名 | 1.159× | 1.154× | +0.005 |

**重复前缀上 S 在两种同质负载里都快**（仅命中 432.3 vs 442.6 = **0.977×**，仅未命中 387.0 vs 403.4 = **0.959×**），**却在混合负载里慢**（550.3 vs 489.0 = 1.125×）——因为它的混合惩罚大得多。另两个数据集上两者惩罚相近，所以混合列的符号与同质列一致。

### 1.4 撤回的表述

**"差距集中在命中类"撤回。** 它至多与 mixed／tranco 的当前分类结果并存，**不能解释 skew**；而且既然三列是三种负载，**由它们反推"总体差距来自哪里"本身就不成立**。

**总体结论一律只引用"全部查询"这一列**（§0 的比值表）。

## 2. 协议

沿用 E12／E13，未做任何调参：

- 每种子 131,072 条查询，**命中率 50%**，由抽取序号奇偶决定；未命中键 = 源键追加 `~missing~`，**生成期用 `lower_bound` 核实不存在**；
- **三类分别计时**（全部／仅命中／仅未命中），避免命中/未命中比例的变化藏在合计里；
- 每种子**先对全部方案的全部查询逐条核对 `found`/`value`**，再计时；轮内乱序、预热 20,000、批校验和；
- 3 种子 × 5 轮 × **5 个进程**；
- 冻结阈值取自 `../validation_e7_20260913/results/main/frozen_ov_<kind>.json`。

**计时来自干净构建**（无任何分配器包装）；ART 的空间来自**单独的诊断构建**，不进任何时间表。

**两个 S 方法在每一行都紧挨着**——它们结构相同，这是应有的样子；**排名的相对位置在两类之间会互换**，正是噪声量级。

**绝对耗时跨进程漂移约 10%**；结论建立在**排序与配对比值**上，不建立在绝对值上。

## 5. 适用边界

1. **只测静态点查。** 插入／删除／扫描未测——**R2（以及全部构建改造）只优化初始构建，不期待更新自动获得同样收益**。
2. **`sorted_array` 与 `sorted_leaf` 不是同一个基线**：本轮只用了前者（不带路由、不带前缀压缩）。
3. **`ART` 只接受无 NUL 的 ASCII 键**（该守卫是承重的，E12 用 ASan 复现过放开后的堆越界读），只在 ASCII 子集上被评估。
4. **空间口径跨行不可比**（§3 末），**不能据此声称 ART 处在同等内存预算下**。
5. **不与 E4 拼接**（另一台机器、另一套 `-march`）；**无 sanitizer**。
6. **绝对值跨进程漂移约 10%**；命中查询覆盖约 63% 的不同键，不是穷举。
7. **没有做显著性检验**。

## 6. 下一步：动态负载

**核心问题固定为：初始空间与查询优势，随着哪些更新事件开始减弱、减弱到什么程度。**

三类负载**各自从相同的初始快照独立开始**，冻结 S 与 ART 使用**相同操作序列**：

| 负载 | 额外明确的条件 |
|---|---|
| **只改值** | 全部键确实存在，只调 `update`；**预期记录数、布局与溢出数量不变** |
| **持续插入** | 新键确实不存在，**记录其分布**；不要无意间全部插到索引末尾 |
| **删除后补入** | 删除成功后插入**不同的**新键，**保持活跃记录数基本稳定**，以观察碎片与容量变化 |

**检查点固定在相当于初始键数 0%／5%／10%／25% 的操作量。**

**检查点查询保留两套，分开报告**：

* **固定查询序列**：每次**重新计算真实答案**，观察同一访问需求在更新后的表现，并报告**实际命中率**；
* **固定命中比例**：从**当前存活键**与**已核验不存在**的键生成，避免命中率变化掩盖布局退化。

**两个必须记录的对应量**（除了溢出、空间与维护次数）：

| 指标 | 用途 |
|---|---|
| 回退统一容量的区域所承载的**记录比例** | 说明多少数据失去了初始需求布局 |
| 检查点查询中**落入这些区域的查询比例** | 说明这种变化是否真的影响了当前查询 |

**少量回退区域也可能承担大量访问——只数区域数量会漏掉这一点。**

范围扫描再随后，比较相同的起点、返回条数与顺序语义；**未实现对应接口的基线不放进排名**。
