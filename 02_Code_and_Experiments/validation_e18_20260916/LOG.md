## E18-1 设计（2026-09-16）

### 两个目标

| 目标 | 编译参数 | 用途 |
|---|---|---|
| `bench_e18` | 无 | 正式计时：三段分解 |
| `bench_e18_diag` | `-DE14_PHASE -DE18_PREPASS -DE18_COUNT` | 构造相位、`grp_prep`/`place` 划分、活动计数 |

### 三段分解

**一个外层区间测完整流程，三个嵌套区间测阶段，全部在同一次重复里。** 占比按 `阶段 / 该次重复的完整流程` 算，再取中位数——**不把阶段中位数相加**。审阅点名要求这一点，因为"用各阶段中位数相加代替完整流程中位数"是上一版报告的问题。

### `place` 怎么拆成两段而不逐键打点

`canonical_group` 与 `Fingerprint::of` 都是键的**纯函数**，所以可以把它们提到一个前置遍历（`-DE18_PREPASS`），得到两个时间跨度：`grp_prep`（算组号与指纹）与 `place`（其余全部）。**每个区域两次时钟调用，而不是每个键两次**——逐键打点的话，131,072 键 × 2 次配对 ≈ 12 ms，与构造本身同量级，会把被测对象改掉。

前置遍历不改变任何放置决策，因此结构不变。**摘要已验证：干净构建与诊断构建的 S 摘要都与 E15 记录的值逐字符相同。**

### 只计数、不计时

`-DE18_COUNT` 在组号计算、`insert_into`、`put_primary`、`put_overflow` 上加**纯自增计数器**（无时钟调用）。这些操作极短，逐个加计时器会比被测量物还贵。计数用于决定下一步该给哪个阶段做粗粒度计时。

## E18-2 事故（2026-09-16）

1. **计数器宏被插进了 `#ifdef E14_PHASE` 里。** 我的插入锚点是 `#define E14_T0()`，它在该 `#ifdef` 块内部，于是不带 `-DE14_PHASE` 时 `E18_INC` 未定义，四种编译组合里有三种失败。语法检查（五种组合逐一试）当场发现，把整个计数块移到 guard 之前。
   **教训**：往条件编译区里插代码，锚点要选在**守卫之外**，否则新功能被悄悄绑到旧开关上。
2. **`bench_e18.cpp` 里留了一个没用的 `struct FnvUnused {};`**——建文件时从旧的 FNV 摘要版本改写过来带下的残骸。清理。

## E18-4 结论与下一步（2026-09-16）

1. **最终流程里构造仍占 66%–79%**，上游两段合计 20%–34%；容量规划 1.2%–1.7%，可排除。
2. **诊断指向重复计算**：最终路径上**组号被算 3 次／键**（统计 1 + 构造 2，其中两次在同一个构造里）。带仪器的相位显示 `grp_prep`（24.1%／23.0%／15.1%）+ `demand_pass`（18.6%／19.1%／11.6%）= **42.7%／42.1%／26.7% 的构造时间**花在"算这个键属于哪一组"上，而它是同一份输入上的同一个纯函数。
3. **`entry_shifts` 恰好为 0**：构建按有序顺序喂键，搬移循环一次都不执行。**E14 列的"描述符移动"这一类在构建路径上是空的**，只在增量路径上有意义。
4. **子块探测次数差别很大**：重复前缀 7.11 次／键、混合 3.97、百万域名 2.02，与 E13 的"组平均子块深度"方向一致。
5. **下一轮按审阅判据选定的改动：把组号算一次并复用**（"若主要耗在重复预测…"）。上限是从带仪器相位推出的 **≈18%–28% 的构造、≈12%–22% 的完整流程**，**不是承诺**——复用要付临时数组（512 KB／1 MB）与内存流量的代价，本轮都没测。
6. **其余三类本轮不选**：描述符搬移实测为 0；后缀复制是真实写入；子块选择策略改动更大，应排在选定改动之后。
7. **ART 对照仍停在 E15 轮**，本轮未补（`native.hpp` 的包装与"零仪器"相冲）。
