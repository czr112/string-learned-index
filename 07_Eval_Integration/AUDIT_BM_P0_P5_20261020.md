## 1. 二十四格覆盖的是两类写入，不是全部操作组合

独立解析48个rows/ops文件并逐条重放后，P4的480,000次primitive实际为：

| 操作 | 数量 |
| --- | ---: |
| find | 420,000 |
| insert | 30,000 |
| update | 30,000 |
| erase | 0 |
| 负载内scan | 0 |

所有24格轨迹哈希、各类次数、实际命中、新插入/重复数和终态规模均与旧records一致；
10份P4源文件也仍匹配其记录SHA。语义通过结论保留。
“replacement”格实际是**原地值更新**，并没有删除旧键、插入不同新键的键集合替换。
终态scan是校验步骤，不能算作扫描负载覆盖。

## 2. “集中增长更便宜”不能归因于写局部性

生成器中增长写目标是`choice(held)`或`choice(keys)`，没有用声明的hot区间筛选新键。
按冻结源键的热点范围核对，六格增长的真实hot写比例只有8.3%–10.1%，而不是80%。
均匀/集中两方的初始map也不相同，且集中组有大量重复插入。

| 数据 / 比例 | 均匀新插入 | 集中组新插入 | 集中组重复插入 | 集中组实际hot写比例 |
| --- | ---: | ---: | ---: | ---: |
| words 95/5 | 999 | 840 | 160 | 8.4% |
| words 80/20 | 3999 | 3014 | 986 | 10.1% |
| URL 95/5 | 999 | 835 | 165 | 9.2% |
| URL 80/20 | 3999 | 2989 | 1011 | 8.3% |
| phrases 95/5 | 999 | 839 | 161 | 9.0% |
| phrases 80/20 | 3999 | 3003 | 997 | 9.4% |

集中增长组的查询实际命中率为72.4%–74.7%，均匀组为90%。
不同初始map、更少成功新插入、更多低成本重复尝试、不同命中率同时变化，
所以旧计时可以描述各自轨迹，**不能证明集中写减少了维护成本**。该因果结论撤回，原数据保留。
也不能直接用总write_ns除以成功插入数补成“公平插入耗时”，因为重复尝试成本仍混在分子中。

## 3. 每次操作的微秒数包含oracle，不是纯索引吞吐

`replay_bm_dynamic.cpp`从switch之前开始计时，switch内还执行`std::map::find/emplace/update`和结果比较。
因此0.84–1.67µs更新、10.6–35.9µs插入是含校验及逐次计时开销的观察均值。
当前记录只有BM，没有同轮ART/Context16，也没有多独立进程、配对吞吐和完整尾延迟证据。
“值更新零页重建”是有效结构事实；具体速度倍率和增长主因的比例仍需干净对照及细分。

P1的2.8%–7.4%分母为整个1,000次插入批次，不能等同于每次结构重建的根占比。
其`reclaim_ns`只包住旧根reset，旧Page释放发生在别处；约一半的“other”尚未细分。
后续优先细分叶页路径，而不是据此重新设计根。

## 4. P5验收的包装与空间/动态实验候选不同

| 项 | P5公共验收 | 空间/动态实验入口 |
| --- | --- | --- |
| 包装 | bm_page_adapter.hpp / make_bm_page_index | bm_bounded_adapter.hpp，动态driver直接调用核心 |
| 核心 | bm_page::Index | bm_bounded_page::Index |
| 构建 | 先复制全部contract rows | 按页有界转换 |
| 对外find | Index::find（window路径） | find_base |

P5的acceptance.txt自身明确写着“bulk_load copies contract rows into a temporary core-row vector”。
100/100可证明该包装的接口语义，**不能与有界构建/base查询的历史结果拼成同一最终配置已经全验收**。
这不是说原模型没有运行；两者都使用给定BlockModel，区别在接入路径。

当前重建脚本还用`|| true`忽略验收程序退出码。该次文本确为100/100，没有证据表明该次失败；
下一轮必须按退出状态硬失败，并把实际adapter、查询路径、构建路径及源SHA统一记录。
`p5-fresh-core`这类描述字符串不能代替精确的源码身份。
