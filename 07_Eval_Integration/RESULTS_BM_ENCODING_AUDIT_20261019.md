# 阶段3审计：失辨只在 URL 类键上成立，窗口宽度是共同瓶颈

日期：2026-10-19；起点`eb41d23`工作树。依据[最新长期计划](../docs/LONG_TERM_BM_PLAN_20261018.md)阶段3。
**结论：`memetracker_urls`是唯一同时满足“同坐标簇显著（44.3%）且簇内额外公共前缀≥2字节（中位11）”的真实格，
因此局部前缀细分只在 URL 类键上有登记依据；words/tranco 的簇占比<1%，短语虽有25%但额外前缀中位仅1字节。
四格窗口均值17–26块、p95最高73、max到137（整页），而窗口覆盖率98.2%–98.6%、缺席键落在窗外仅1.3%–1.9%
——代价在窗口**宽度**，不在回退分支。**

## 审计口径

按BM叶页真实构造逐页重建（2048行/页、占位15、页前缀=首尾公共前缀、`fit(fences,1,7,8,1)`），每页拟合一次后统计；
四格各65,536行、32页、4,384块，每页约8段（URL为7.16段），**没有任何一页通过`certified()`（0/32）**，
即每次查询都必须按提案+纠错处理，符合“训练标志不当缺席证明”的约束。

## 判读

1. **窗口宽度是共同瓶颈**：均值17–26块意味着窗内二分约4–5步；URL的p95达73块（≈6步）、最大137块＝整页。
   这与阶段1“完整工厂不优于我们接入、差距在共有预测/验证工作”一致，也解释了为什么预测优先、括号、
   payload探测都失败——它们都在猜“哪一块”，而真正的成本是“窗口有多宽”。
2. **回退不是成本中心**：窗口覆盖98.2%–98.6%，缺席键落在窗外仅1.3%–1.9%，
   所以“整侧搜索”很少发生；调回退门不会有大收益（这也与括号轮“整侧搜索反而更贵”的观测一致）。
3. **失辨有明确目标格**：只有URL类键的簇结构值得动——44.3%的fence与前驱共享7字节码，
   簇内还有中位11字节、p95 37字节的额外公共前缀，说明**第8个字节以后仍有大量区分信息被编码丢掉**。
   短语的25%簇内额外前缀中位只有1字节，细分上限很低；words/tranco几乎没有簇，改编码不解决问题。
4. **预测精度与簇无关**：四格预测块=所在块都在8.6%–9.9%，URL并不比其它格好，
   说明“预测不准”不是簇造成的，而是模型分段精度/半径问题；两件事要分开处理。

## 决定与下一步

- 审计判据`encoding_refinement_justified`＝真，且**只有`memetracker_urls`**；据此，阶段3第2条的
  “一层簇内局部前缀细分”应登记为**URL类键专用候选**（在簇内验证额外公共前缀后再读真正分歧的后续符号，
  保留父区间纠错），并以words/tranco作阴性对照、短语作低收益对照。
- URL格同时是BM最接近ART的一格（完整读1.032），因此它是唯一有现实可能跨到≤1.00的目标格；
  但不预支结论，必须先过工作入口（≥25%定位比较或标签批次减少、另一类不放大、元数据≤5%）。
- 不在本轮建候选、不改模型参数/编码宽度/段数、不计时。

## 边界与披露

- 纯计数审计，不是时间；不把窗口块数换算成纳秒。
- 查询仍是真实键+10%缺席的合成负载，不代表真实访问分布；65k不外推百万级。
- 每页模型由审计按页构造重建，与BM叶页构造逐参数一致（2048/15/`fit(1,7,8,1)`），
  但审计不经过`bm_page::Page`的封装，因此结论绑定“同参数同构造”，不冒充页对象内部计数。
- 复核器在实验后修过两处打印精度容差；运行哈希与当前哈希均记录在`verification.json`。
