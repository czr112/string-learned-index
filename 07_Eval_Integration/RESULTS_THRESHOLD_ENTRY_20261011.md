# 等深阈值目录：入口诊断（下一阶段方向①）

日期：2026-10-11。**本轮不改 `index.hpp`**：诊断在评测入口自己的语料与区域划分上离线测量，
回答「这个映射会给出什么样的组负载、要多少内存、查找要几步」。没有计时，也不把计数折成加速比。

诊断程序：`diag_threshold_entry.cpp`（sha256 `43157a0b8d2412b0…`），目标 `diag_threshold_entry`
（`tools_build.py` sha256 `aa8bb341d67a33be…`），构建记录 build_id `1791714603282013989`，
绑定 `index.hpp` `f553630d5cc31296…`。语料：`datasets/{mixed,skew,tranco}.keys`，各 131,072 键 / 64 区域。

## 0. 判定

**信号成立：分隔符形式的等深阈值目录第一次真正解决了组负载集中**——最大组负载
1366 / 824 / 546 → **12 / 12 / 12**，空组 14278 / 19178 / 5993 → **0 / 0 / 0**，而它的常驻内存
（压缩分隔符）是 **0.6–5.0 KB/区域**，比它要替换的 Context16 参考表（16,512 B/区域）还小。
**63-bit 坐标形式不成立**：skew 上 64/64 区域出现阈值坐标重复，最大组负载与 rank 后端相同（1431），
比 Context16 的 824 更差。

## 1. 候选与两种编码

区域内按**排名等深**放 G−1 个阈值（第 j 个在 rank ⌊j·n/G⌋），键的组号 = 比它小的阈值个数。
两种编码只在「比较什么」上不同：

| 编码 | 阈值内容 | 每步比较 | 致命限制 |
| --- | --- | --- | --- |
| FIXED | 63-bit 坐标（9-bit×7 字节，与 rank 后端同一个坐标） | 8 字节整数 | 共享那 7 个后缀字节的键**无法区分** |
| BYTES | 边界键的**后缀**（区域前缀已剥离） | 长度感知字节序 | 分隔符本身占内存（可压缩） |

## 2. 组负载（同一区域划分，四种映射逐格对照）

| 语料 | Context16 最大/平均/空组 | rank 后端 | FIXED | **BYTES** |
| --- | --- | --- | --- | --- |
| mixed | 1366 / 6.17 / 14278 | 1366 / 19904 | 1366（23/64 区域阈值重复） | **12 / 6.17 / 0** |
| skew | 824 / 6.50 / 19178 | 1431 / 20004 | 1431（64/64 重复） | **12 / 6.50 / 0** |
| tranco | 546 / 11.98 / 5993 | 564 / 7682 | 554（46/64 重复） | **12 / 11.98 / 0** |

最大/平均之比：Context16 是 221× / 127× / 46×，rank 与 FIXED 同量级或更差，**BYTES 是 1.9× / 1.8× / 1.0×**。
空组比例（决定跳表与目录的大小）：Context16 67% / 89% / 55%，BYTES 0%。

## 3. 代价

| 语料 | 分隔符（原样） | 分隔符（按 lcp(prev,next)+1 截断） | 查找步数/查询 | 比较字节/查询 | 子块数 参考→候选 |
| --- | ---: | ---: | ---: | ---: | ---: |
| mixed | 2,121,557 B | **217,012 B**（3.4 KB/区域） | 8.27 | 76.3 | 18,938 → 21,392（+13%） |
| skew | 1,799,334 B | **319,503 B**（5.0 KB/区域） | 8.28 | 127.1 | 14,924 → 20,163（+35%） |
| tranco | 132,069 B | **40,440 B**（0.63 KB/区域） | 7.50 | 21.5 | 10,829 → 10,944（+1%） |

比较字节按 memcmp 的真实行为计费（走到**首个不同字节**为止，不是最坏情况）；
Context16 的参考表是 16×258×4 = 16,512 B/区域 = 1.06 MB（64 区域），所以按截断口径，
**候选的常驻更小**（mixed 217 KB、skew 320 KB、tranco 40 KB）。

**子块数没有改善**（+13% / +35% / +1%）。这一条必须如实说：候选的收益不在「更少的子块」，
而在于**把两次搜索合成一次**——当前每次查询要做 ①模型预测（16.5 KB 表 + 逐字节区间）与
②组内子块目录二分（E11，目录项是完整边界键），而平衡后组的规模小到多数组只有 1–2 个子块，
查找变成**一次等深阈值二分**（7.5–8.3 步），并把参考表整块省掉。

## 4. 边界（不得越读）

- 本轮**没有**：改 `index.hpp`、跑计时、跑 A/B、验证端到端收益。上面的「合成一次搜索」是机制解释，
  不是加速比；子块数是按索引自己的公式（`max(条目约束, 字节约束)`）算的形状量，不是实测值。
- 分隔符截断只算**内存**（标准做法：每个边界只存到 lcp(prev,next)+1），查找在该形态下的真实
  比较成本要等实现轮测；本轮查找成本是对**未截断**分隔符的实测计费。
- 语料是 131,072 键/64 区域；更小或更大的区域划分没有测。
- FIXED 的失败与 rank 后端同源（同一 7 字节坐标），所以这**不是**「阈值比模型好」的普遍结论，
  而是「不截断的边界 + 按真实分布定深度」这两点带来平衡。

## 5. 结论与下一步（预登记）

**方向和编码选定 BYTES（分隔符、等深、lcp 截断）**，理由在 §0/§2：唯一真正消除集中、
并且常驻小于被替换的参考表。下一轮（最小差分实现）预先登记为：

1. 作为**第四个 `ModelBackend`** 接入（复用本轮的 `calibrate_*` / 三处分发 / `mapping_identity` /
   `memory_breakdown` 管道），默认关闭；
2. 正确性门：逐键对照（放置组 == 查询组）、**全域保序**（含空键/NUL/高位字节/4096 字节键）、
   旋转负对照、动态插入/擦除/分裂/前缀重建后的重扫、ASan/UBSan；
3. 同状态入口诊断：在入口自身的查询模式下与 Context16 逐区域配对，判据是主块访问与完整比较的
   下降方向一致，且**构建增量 ≤10%、常驻增量 ≤5%**（若主要收益是空间则单独按空间取舍）；
4. 通过后才是 A/B（5 进程 × 4 平衡重复、同重复内配对）与集成；不通过则如实收口，
   不开参数搜索、不做第二次微调。
