## 1. 分块根的计时臂标签错位，原入口结论撤回

核对`bm_root_chunk_20261019`记录的源码及可执行文件SHA均匹配。实际源码为：

```
names = flat, chunked, flat_AA, chunked_AA
pass(arm >= 2)
```

因此原标签对应的真实路径是：

| 保存的标签 | 实际路径 |
| --- | --- |
| flat | flat |
| chunked | flat的同对象AA |
| flat_AA | chunked |
| chunked_AA | chunked的同对象AA |

原报告的1.005–1.027是在比较两次flat，不能证明分块路由只增加0.5%–2.7%。
本次按真实路径，对原360条计时记录逐轮直接配对，再按原5进程、各6轮规则重新计算：

| 输入 | 真实chunked/flat中位数 | 正确AA观测带 | 结论 |
| --- | ---: | ---: | --- |
| tranco64 | 2.063 | 1.202 | 短键路由明显更慢 |
| skew131k | 0.873 | 1.102 | 此长前缀格数值更快，不能挽救三格入口 |
| tranco262k | 1.992 | 1.056 | 短键路由明显更慢 |

登记条件是三格均满足`abs(chunked/flat−1)≤0.05`；原通过判定无效，**不能据此进入集成**。
路由零失配仍成立。条目减少43.8%/68.8%/81.3%仍是算式给出的复制量估计，但诊断类型
只有`vector<vector<string>>`和块首键，没有实际共享块更新、发布、回收或分配峰值测量。
它们是研究线索，不是已实现COW的写性能收益。

旧`raw.json`、`decision.json`、`verification.json`全部保留；新的审计单独保存，不覆盖旧身份。

旧runner用`snapshot/dynamic≤1.15`判读，预算实际应是`dynamic/snapshot≤1.15`。
动态计时臂与真实对象对应正确。本次从原480条记录按正确方向重新直接配对，

旧runner还包含一个带`or True`的终态行数断言，必须在下一正式版本换成独立终态不变量检查。

## 3. 干净重建的“校验和差28”未在精确复验中出现

使用原先已重建的clean二进制，SHA仍与原空间轮一致；输入SHA也匹配。
本次保存原始stdout/stderr，并用Python整数比较，两个独立进程的10个确定性字段均与历史记录一致，
checksum均为十进制字符串`507521454403758928`。

旧比较记录中的`507521454403758900`，恰好可由以下V8 Number往返产生：

```
JSON.stringify(JSON.parse("507521454403758928"))
// "507521454403758900"
```

旧复建stdout没有保留，因此无法严格确定当时哪一步引入差异；证据与比较链的大整数精度损失一致，
不能继续把“差28”作为已证实的索引非确定性问题。后续校验和必须保存原始输出、用精确整数或十六进制字符串比较。
这仍只是已有重建二进制的一格两次语义复验，不是本次重新从零构建全部依赖，也不是整轮性能复现。
