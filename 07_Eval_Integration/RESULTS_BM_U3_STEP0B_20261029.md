# U3 第 0b 步：重建成本里 **scan 占 64%–77%**，`split_half` 的收益上限被上调

日期：2026-10-29。承接 [U3 第 0 步](RESULTS_BM_U3_STEP0_20261029.md)（拟合仅 3.7%）。

## 测量

`rebuild()` 的实际流程是：`scan("",SIZE_MAX)` 把整页物化成 `std::string` 行 → 插入新键 →
构造新页。分别计时这三段：

| 指标 | words | urls |
|---|---:|---:|
| 全量 `scan`（32 页） | 5,964 µs | 6,208 µs |
| **折算每页 scan** | **186 µs** | **194 µs** |
| 构造 2,048 行页 | 56 µs | 109 µs |
| **重建估计合计** | **242 µs** | **303 µs** |
| **scan 占比** | **77.0%** | **64.1%** |

与 U1b 实测的重建单价（140–334 µs）**同量级**，互相印证。

## 判读

1. **重建的大头是 `scan`**——把 2,048 行物化成 2,048 个 `std::string`（每个都分配），
   而不是页构造（56–109 µs）、更不是模型拟合（3.7%）。
2. 因此"页分裂不重编码"的收益上限**远高于**第 0 步的保守估计：
   若省掉 scan 与重复构造，重建单价可降 **60%–75%**；
   折算到插入时间（重建占 75.5%–95.6%），**总写耗时潜在下降 45%–70%**。
3. 这条也解释了为什么"块分裂"只占 0.3%–9.5%：它绕过了 scan，
   但只覆盖了"块满"这一小部分触发，页满仍走全量重建。

## 实现顺序调整（比原规格更省力的一步）

原规格要先写 `split_half`。现在多了一个**更小的第一步**：

**让 `rebuild()` 不再调用 `scan()`**——直接遍历源页的块，把 `(suffix_view, value)` 交给新页的
"按 suffix 构造"入口。这需要给 `Page` 加一个接受 `std::vector<std::pair<std::string_view,uint64_t>>`
的构造函数（与现有构造逻辑相同，只是跳过 `std::string` 物化）。

- 预计收益：省掉 64%–77% 的重建成本 → 写耗时降 **48%–74%**（按重建占比折算）；
- 风险：`split_half` 的记账（offset 重写）仍需要，但可以分两步走：
  先做"不 scan"版本（改动集中在 `rebuild()` + 一个构造函数），再考虑整块搬运；
- 门与停止线不变。
